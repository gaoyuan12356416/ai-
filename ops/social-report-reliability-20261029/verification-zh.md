# 社媒效果分析报表修复记录

日期：2026-10-29（北京时间）。范围：现有“社媒效果分析”页面及其报表查询、Facebook 归属采集模块；UTC 自然日、租户与人员权限、冻结归属、整数金额口径保持不变。

## 已复现的问题

1. 截图中的 YouTube 2026-10-01～28 源数据实际覆盖全部 28 天。广日期查询接近原单条 8 秒上限，叠加 SQL 门禁与连接开销容易超时；读取失败又被误标为“28 个日期未同步”。
2. X 广范围包含 4,712 个历史归因 ID，旧分批方式需要反复建立大量连接，在 HTTP 预算内难以完成。
3. Facebook 旧自动发布源带有 15,772 组冻结 Campaign/Page/素材 ID 的大列表，实测出现 MySQL 3024 超时。各渠道串行读取还会挤占后续渠道的共同查询预算。
4. Facebook 归属采集器曾 SIGBUS 退出后自动恢复，账本 quick_check 正常；发现 SQLite 活连接期间额外开关 WAL/SHM 文件描述符的锁风险，已修正。该风险与具体崩溃的因果关系尚无 core dump 证明。

## 修复

- YouTube/X 使用有界日期窗口与精确 ID 批次；相同 SQL 的重复请求合并并短期缓存，失败不缓存。
- Facebook 以最多四天一窗读取候选 Page 数据，始终按三个二进制 ID 分组；汇总前使用冻结三元组集合精确校验，避免跨素材、跨 Page、大小写或历史同 Campaign ID 串数。原查询 9,748 行与新查询逐行一致。
- HTTP 最多两个渠道并发，各渠道最多两个窗口，每请求最多四条 SQL；继续经过既有连接门禁，保留共享 40 秒查询预算。网页单条查询限制为 12 秒；数据量超限或任一窗口失败均不返回伪完整结果。
- SQL 结果缓存限制为 300 秒、32 条、32 MiB，归属及权限仍逐请求计算；未读到的数据继续保持未知，不作为零。
- 真实缺失日期与查询失败“待核实”日期分开展示。浏览器提前断开时不再重复写错误响应。
- WAL/SHM 权限通过元数据操作收紧，避免破坏 SQLite 持有的文件锁。
