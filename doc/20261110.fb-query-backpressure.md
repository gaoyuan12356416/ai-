# FB publishing query backpressure and explicit recovery

Concurrent publication reservations could overwhelm the two SQL and identity
mapping slots. Temporary 503 responses became terminal native failures. The FB
bridge now admits at most two publication preflights, defers excess work before
claiming native tasks, and returns a temporary read failure to the original
queue with a 30-second coordinator cooldown. Credential selection shares the
same query capacity, waits up to 30 seconds and attempts a busy SELECT at most
six times. Waiting credential requests take priority over new preflight reads.
Receipts and platform uploads do not take this semaphore. Permissions, frozen
source identity, Page serialization and unknown-write guards remain enforced.

Identity responses retain the safe `mapping_busy`/`mapping_unavailable` code in
logs. No identity response body, actor, credential or driver exception is logged.
The existing deployed Page pool policy overlay is retained. Native attempt
numbers now increase across explicitly recovered generations, retaining all
previous attempt evidence.

## Validation

Run `python -m unittest tests.test_fb_query_backpressure
scripts.test_pipeline_fb_source_locks scripts.test_pipeline_fb_task_isolation
scripts.test_pipeline_claim_handoff.ClaimHandoffTests.test_native_account_conflict_waits_without_changing_appointment
scripts.test_pipeline_claim_handoff.ClaimHandoffTests.test_late_credentials_after_lost_heartbeat_never_enter_platform_write -q`.
The tests cover deferred preflight without a platform attempt, permanent
permission denial, concurrency, late receipts, current-generation fencing,
credential selection retry and evidence-preserving exact-task recovery.
The 48 relevant tests passed locally and on the CPU server. An authorized
recovery event prevents old rejected attempts alone from becoming a new unknown;
new operations, real unknown flags and published object IDs retain their fences.

## Deployment and rollback

Push the exact commit, fetch it into an isolated CPU checkout, then run
`python -m scripts.deploy_fb_query_backpressure prepare --source SOURCE
--commit COMMIT --folder DEPLOYMENT` followed by the same module's `apply`.
The helper verifies the live baseline, preserves other runtime overlays,
backs up both ledgers, drains only accepted work and restores the FB and
coordinator scheduler baselines. It checks candidate file access as each service
user before changing admission or releases. Main API and GPU nodes do not need a restart.

Rollback: `python -m scripts.deploy_fb_query_backpressure rollback
--folder DEPLOYMENT`. This swaps code only after draining; never restore a
database backup over new publication receipts.

## Operator-authorized task recovery

`scripts/recover_fb_unpublished.py` requires an explicit JSON list of job IDs.
Its default is a read-only plan. `--apply` additionally requires the plan hash,
an unused backup directory and paused FB admission. It verifies all native
attempts and permits, excludes accepted/unknown/competing outcomes, keeps the
original task, media, caption, schedule, links and historical attempts, and
records an audit event. Never remove attempt or operation rows to allow replay.
Preserved old generation callbacks cannot acquire the new claim.
`scripts/repair_fb_recovery_observation.py` is a separate exact-ID, hash-checked
repair for a stale historical-attempt observation after that authorized recovery.
It requires unchanged native rejection evidence and no newer operation, and does
not reset native tasks or authorize any unknown platform outcome for replay.

For an unknown response whose original short link is positively found in a
published Page video, `scripts/settle_fb_observed_video.py` records GET evidence
only. It requires a unique exact short-link match in the original attempt time
window, a published platform status and a matching dry-run hash. Objects that
remain inaccessible retain unknown status and are never re-posted.
