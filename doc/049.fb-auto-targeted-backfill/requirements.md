# 049.fb-auto-targeted-backfill 需求与技术设计

## 背景

2026-08-25 08:44（北京时间）的 FB Page 自动发布运行 `run_id=20` 只发布了 8 个 Page，另 5 个 Page 因运行在修复发布前已冻结，被终态标记为 `fb_page_missing_eligible_token`。运行 20 已完成且这 5 个任务均为 0 次尝试；直接执行现有 `run-now` 会把整模板重新建单并导致另外 8 个 Page 重复发布。

## 目标

为指定历史运行提供一次性、可审计、默认只校验的定向回补工具。仅为显式 Page 白名单新建手动运行，复用现有素材选择、GPU 预制、Graph 发布、凭证实时重读、凭证故障切换、未知结果保护和发布账本。

## 范围

### 包含

- 来源运行固定为 `run_id=20`，来源计划时间固定为 `2026-08-25T00:44:00+00:00`。
- 目标 Page 固定为：`1009871948881047`、`1014456238423538`、`1069327366257056`、`761697440365789`、`957642277435629`。
- 新增仅供运维命令行使用的定向回补入口；默认 validate-only，真实建单需提供 dry-run 指纹和独立审计报告路径。
- 新建运行后由现有定时器异步预制和发布；当前仍无合格凭证的 Page 保持跳过并给出明确原因。

### 不包含

- 不修改来源运行 20 或其历史任务。
- 不回补或改写 2026-08-25 20:40 的运行 21。
- 不重发运行 20 已成功发布的另外 8 个 Page。
- 不直接调用 Facebook Graph API，不绕过现有任务状态机。
- 不修改 Page Token 状态、模板配置、发布时间或素材池。

## 用户故事 / 业务规则

1. 运维人员先执行 validate-only，确认来源、目标、模板版本、当天日期、0 尝试事实、实时凭证计数及去重状态。
2. validate-only 输出规范化快照及 SHA-256 指纹，不创建运行、任务或发布尝试。
3. apply 必须复用完全相同的来源运行、日期、目标 Page、操作号和 dry-run 指纹；任一状态漂移即拒绝。
4. 相同操作号幂等返回同一回补运行；同一来源运行的不同回补操作号默认拒绝，防止重复回补。
5. 仅目标白名单可进入新运行。目标 Page 已移出模板范围、来源任务不再满足跳过/0 尝试条件、模板停用或版本变化时，全部拒绝建单。
6. 新运行计划时间为 apply 当下；有实时合格凭证且有可用素材的 Page 为 `planned`，无合格凭证的 Page 为 `skipped/fb_page_missing_eligible_token`。
7. 已有到期积压、未知结果或冲突任务时沿用现有状态机门禁，禁止叠加发布。

## 交互与流程

`validate-only -> 人工核对指纹/5个Page -> apply建单 -> 现有prepare timer -> GPU预制 -> 现有execute timer -> Graph发布/凭证切换 -> reconcile/ledger -> 终态报告`

## 技术设计

### 影响模块

- `features/fb_auto_posts/core.py`：`create_run` 增加仅限手动恢复使用的模板版本锁及 Page 白名单。
- `scripts/fb_auto_post_targeted_backfill.py`：来源校验、去重、指纹、建单和审计报告。
- `scripts/test_fb_auto_store.py`、`scripts/test_fb_auto_post_targeted_backfill.py`：单元与安全边界测试。

### 数据结构

不新增表、不执行 DDL。通过现有 `fb_auto_run.slot_key` 唯一约束实现操作号幂等；回补运行仍写入现有 run/task/run_page/attempt/ledger 表。

### API / 接口

不新增公网或后台 HTTP API。命令行参数包括来源运行、来源计划时间、来源北京时间日期、重复 Page ID、操作号、`--apply`、`--expected-fingerprint` 和 `--report-path`。

### 异常与边界

- 目标集合必须正好等于来源运行内全部 `fb_page_missing_eligible_token` Page。
- 来源必须是已完成的自动运行，目标任务必须 0 尝试、无 Graph ID、无 unknown、无尝试行及发布账本。
- 当前模板必须启用且版本与来源运行一致；Page 白名单在素材快照前后均需完整存在。
- validate-only 指纹不承诺具体素材；apply 时仍由现有冷却和指标快照实时选择，找不到素材则安全跳过。
- 审计报告只能写入数据盘专用目录的新 JSON 文件，拒绝软链接、越界及覆盖。

## 验收标准

- validate-only 明确显示 5 个目标、实时可发布数量、阻塞数量、无数据库建单写入，并输出稳定指纹。
- 错误或缺失指纹的 apply 不创建任何 run/task。
- 正确 apply 恰好创建 1 个新手动运行和 5 个任务快照，不包含其他 Page；重复执行返回同一 run_id。
- 4 个当前有合格凭证的 Page 进入既有预制/发布链路；`761697440365789` 若仍为 0 个合格凭证则保持安全跳过。
- 另外 8 个 Page 的今日成功记录不增加，运行 21 不发生改动。
- 最终无 `running/submitted/unknown` 遗留；发布成功需以 ledger 与 Graph post id 为准，非仅以脚本已派发为准。
- 全量 FB 自动发布回归通过，部署可按 GitHub commit 回滚且 SQLite 备份可恢复。

## 风险与待确认

- Graph 或凭证在建单后仍可能变化；由执行时实时凭证重读、确定失败切换和 reconcile 处理。
- GPU 预制耗时不可预测；建单成功不等于外部发布成功，必须持续观察到终态。
- 本次按用户确认只回补上午漏发的 5 个 Page 一次；晚间运行 21 保持原样。
