# CPU Codex 双账号与重置卡

适用 CPU `43.166.187.96`。自 2026-11-20 起，先用新号，再用原号的现有额度。只有两个账号都报 0% 且新号有重置卡时才发起扣卡。

## 行为与实际边界

- 每分钟通过已安装 Codex CLI 的官方 `account/rateLimits/read` 获取当前账号的普通 `codex` 桶，取 primary / secondary 有效窗口的最小剩余百分比。不同模型的额外桶不混入本规则。
- 新号剩余至少 1% 时继续使用。低于 1% 时查询原号，原号有正额度就切过去。原号为 0%、新号还有少量额度时继续用新号。
- 从 2026-11-24 起，Gmail 为主账号，QQ 为备用账号。使用备用账号期间，每轮先读主账号，主账号恢复至既定 1% 阈值即切回。备用账号耗尽时，主账号剩余不足 1% 也可先用。主账号读数未知时继续使用已有的可用备用额度。
- 两个账号在同一轮都明确为 0% 时，检查新号的卡数。有卡才用新号凭据调用 `account/rateLimitResetCredit/consume`，优先使用最早到期的有效卡，只有数量时由官方选卡。卡数为零或未知时等下轮检查。原号的卡留作手动使用。
- 收到 `reset` 或 `alreadyRedeemed` 后，官方回读确认新号有正额度才使用新号。写回锁暂忙时留待下轮切号。用量未知或回执暂未反映在额度中时等待核实。
- 发起扣卡前保存幂等键。超时或进程重启后保留同一请求，即使中途先用另一账号的可用额度，也只有两边再次为 0% 才重试扣卡。若官方已显示恢复的额度和减少的卡数，可使用新号并保留原键核对扣卡结果。`nothingToReset` 或 `noCredit` 是明确的未扣卡回执，等待用量窗口或可用卡信息变化后再尝试。
- 新账号独立授权到数据盘。初次切换前保存原账号最新凭据；切回前也保存新账号最新凭据。两个账号都不执行 logout。
- 原有截图服务存在隔离凭据写回：切换时持有它们已经使用的凭据同步锁，仅等对应服务正在处理的请求结束。新请求在同一锁后读取新凭据。没有全局停调度、服务重启、清队列或打断 Codex 任务。
- 活动凭据位于 `/root/.codex/auth.json`。用量检查在访问令牌到期前一天请求官方续期，活动凭据写回沿用截图服务的同步锁。每轮结束后，`sync_youtube_cover_auth.py` 以封面节点的服务用户原子更新私有登录文件。文件仅包含当前账号的短期访问凭据，任务隔离目录无法轮换主凭据。新启动的封面生成直接读取新身份，在途生成继续使用自己的目录。已启动的其他常驻 app-server 仍沿用安全重连流程。

## 文件与验证

- 程序：`/opt/codex-account-watch/releases/<git-sha>/scripts/codex_account_watch.py`，`current` 指向部署版本。
- 私密状态：`/mnt/data-disk/codex-accounts/state.json`、`accounts/{original,new}/home/auth.json`，目录 0700 / 文件 0600，不进 Git。
- 部署备份：`/mnt/data-disk/codex-accounts/deployments/<timestamp>/`，含初始原账号备份和部署清单。备份不能替代切换前保存的最新刷新凭据。
- 定时器：`codex-account-watch.timer`；脚本 `status` 和 `journalctl -u codex-account-watch.service` 仅输出脱敏状态。

```bash
python3 /opt/codex-account-watch/current/scripts/codex_account_watch.py status
systemctl status codex-account-watch.timer --no-pager
journalctl -u codex-account-watch.service -n 15 --no-pager
```

测试使用虚构凭据与官方接口响应，不在生产消耗重置卡；实际读回两个账号身份与额度，再验证初次切换及定时器。检查本次服务外的业务进程 PID 保持不变。

## 停用与回退

代码停用只停止本监控，保留当前账号、最新凭据及在途任务：

```bash
systemctl disable --now codex-account-watch.timer
```

需要回原账号时执行下面命令。若对应写回请求正在执行，命令会报告 `switch_deferred`；等该请求结束后重执行，不能杀任务。返回后通过 `status` 确认 `active=original`。已有 app-server 会话安全重连。

```bash
python3 /opt/codex-account-watch/current/scripts/codex_account_watch.py return-original
```

本次升级的备份目录包含可执行的 `rollback.sh`，在监控自身的锁下将 `current` 原子切回上一版本。定时器在下一轮读取该版本。保留最新凭据、当前账号和扣卡回执。

## 当前已有连接的安全重连（0.161.0 已验证）

2026-11-16 已完成一次旧账号共享后台的安全重连。通过 Unix 控制接口读回：旧后台为原账号且无加载任务；重连后账号与活动新账号一致，CLI / app-server 版本均保留 0.161.0。其他工作连接及业务服务未重启。操作记录：`/mnt/data-disk/codex-accounts/deployments/safe-reconnect-20261116T093754Z/manifest.json`。

- 必须区分 `unix://` 共享后台与 `stdio://` 工作连接。该版本仅前者支持等候在途回合完成的 SIGHUP 排空；不能给 stdio 工作连接发送 SIGHUP。已经在切号后启动、读取新凭据的工作连接保留运行。
- 使用 Unix 控制接口先查询 `account/read`、`account/rateLimits/read` 与 `thread/loaded/list`。控制接口是 WebSocket，`codex app-server proxy` 透传的是 WebSocket 字节，不能直接向它写 JSONL。
- 普通 `codex app-server daemon restart` 有排空超时后强杀的路径，不满足用户“不打断任务”的要求。实际使用经当前安装版本源码确认的 SIGHUP：停止该后台接收新回合，等已接纳的请求和正在跑的回合自然结束；不追加 TERM/KILL、不因等待超时清理任务。
- 发送前校验目标是原生 Codex Unix 后台，保存 PID、进程启动标识、原启动参数、工作目录、日志路径及相关服务 PID。原环境仅在重连助手内存中沿用，不把环境值写入记录。等原后台真正退出，再按原参数、原环境、原目录和原日志路径启动同版本替代进程。
- 重连后再次通过控制接口确认账号与活动凭据一致、版本未变，并核对业务服务 PID。原号凭据和用量监控不变。以后的凭据切换如需更新共享后台缓存，也沿用这一安全流程；不得把固定旧 PID 或旧账号身份当成永久配置。
