# 043.x-post-manual-clear-errors 需求与技术设计

## 背景

X 素材池“手动发布”任务失败时，页面直接拼接后台 `error_code` 和英文
`error_message`。生产任务 #15/#16/#17 分别出现素材不存在、时长数据为 0、
修复后文件大小不合规，但页面只显示笼统技术文本，运营无法直接判断如何处理。

## 目标

- 页面只显示简短中文“拦截原因”，不展示技术错误码。
- 素材不存在、非视频、已删除、时长缺失、时长超限、文件超 512MB、文件为空等原因必须区分。
- 尽量带上失败素材 ID；后台仍保留结构化错误码供日志审计。

## 范围

### 包含

- 手动发布 exact-ID selector 的源数据原因拆分。
- GPU 修复结果的大小/时长中文明细。
- 手动 runner 将粗粒度 worker 错误归一为具体 run 错误。
- 素材池手动发布弹窗的中文原因映射及历史任务兼容。

### 不包含

- 不修改 X 发布门禁、账号会员判断、队列、去重或重试规则。
- 不改写历史 run/queue/log。
- 不创建手动任务，不发送真实 X Post。

## 用户故事 / 业务规则

运营看到失败任务时，应直接看到类似：

- `拦截原因：素材 6194023：视频时长缺失或为0秒`
- `拦截原因：素材 6179846：修复后视频超过512MB上限`
- `拦截原因：素材 99：视频超过140秒，所选账号没有长视频会员资格`

同一批仍保持整批发布前检查：任一素材失败时零建队列、零 X 写入。

## 交互与流程

1. runner 完成源数据和媒体检查。
2. 第一条失败记录具体 `error_code/error_message`，并尽量附带 `material_id`。
3. 浏览器按错误码输出一个简短中文原因；未知错误只显示“发布前检查失败，请联系技术人员”。
4. 页面不显示英文原文、内部错误码或堆栈信息。

## 技术设计

### 影响模块

- `features/x_posts/selector.py`
- `features/x_posts/media_repair.py`
- `scripts/x_post_manual_runner.py`
- `static/x-post-material-pool.html`
- 对应离线测试与本需求文档

### 数据结构

无 schema 变更。继续使用 `x_post_manual_run.error_code/error_message`。

### API / 接口

响应结构不变；同一字段改为更具体的错误码与简短中文消息。

### 异常与边界

- 旧 `material_not_found_or_ineligible` 只能显示兼容性说明，不能重写历史记录。
- 旧 `repaired_media_invalid + size...` 在页面归类为 512MB 超限；新任务由 worker 中文明细和 runner 归一代码准确区分空文件与超限。
- 未知错误不回显原始英文，避免让运营阅读内部实现细节。

## 验收标准

- #17 形态的旧响应显示“修复后视频超过512MB上限”，不显示 `repaired_media_invalid`。
- `video_duration=0` 的新任务记录并显示“视频时长缺失或为0秒”。
- 不存在、非视频、已删除、超过4小时分别得到不同错误码和中文原因。
- 修复后空文件与超过512MB分别得到不同的手动 run 错误码。
- 相关单元/UI 契约测试通过；生产验收期间 queue/log/Post 数量不因部署增加。

## 风险与待确认

无产品决策阻塞。生产部署需要 CPU/GPU 同 commit、静态页同步和无发帖验证。
