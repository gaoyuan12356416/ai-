# BUG-005 指标缓存跨 content 排序语义不一致

## 现象

2026-08-18 closed-gate 生产部署后，首次 `fb-auto-post-metric-hourly.service` 在只读刷新 2026-08-17 指标时安全失败：`fb_auto_metric_row_invalid`。失败前未切换 active pointer，发布操作库六张业务表仍为 0。

## 根因

MySQL 原查询按列默认 collation 排序 `content_id`，流式 SQLite writer 则按 Python/Unicode 顺序检查全局严格递增。生产第 49 行出现 MySQL 顺序 `0aIr8mVcdZ` → `0AKMvhVoCz`，与 Python binary 顺序相反，导致误判无序。素材 ID 长度+字符串排序与无前导零 ASCII 正整数的数值序一致，不是根因。

同时发现 `.isdigit()` 会错误接受 `01` 和 Unicode 数字，直接写入路径的身份约束弱于 MySQL `REGEXP`。

## 修复

- 指标 SQL 的 `GROUP BY/ORDER BY` 均增加 `HEX(CONVERT(TRIM(content_id) USING utf8mb4))` binary canonical key，区分大小写并冻结确定顺序。
- writer 使用 UTF-8 bytes + 素材 ID 长度/字符串作为同语义严格递增键。
- repository 与 store 统一素材 ID 为 `[1-9][0-9]*`。
- 增加混合大小写、1/2/10/超大 ID、重复身份、前导零/Unicode 数字、事务回滚与 active pointer 保留测试。

## 验证

- 修复 SQL 对生产 2026-08-17 只读流式查询返回 23,765 行，binary 顺序和身份检查均通过。
- FB auto 专项 80/80 PASS；GPU 15/15、X/TT 合并基线 66/66 在同一候选上通过。
- 生产重新刷新和 30 日 repair 结果记录在 `test-report.md`，真实发布开关保持关闭。
