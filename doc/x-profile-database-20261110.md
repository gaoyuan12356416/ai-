# X 三级画像数据库读取与列表布局

完整画像原来约 62 MB，线程解码并常驻缓存曾导致只读 API 超出内存限制。现在使用 `ads_ai.x_channel_revenue_profile` 按 `(profile_version, x_user_id)` 保存每个频道的列表摘要、无剧目明细的画像树和完整明细。列表只读取有权限频道的摘要；发布选择只读取所需频道的画像树；题材详情通过 JSON 路径只取每页 50 部剧。服务不再有全量 JSON 缓存。

小时刷新沿用原统计口径。固定表写入走 63353，读取走 63350 和 FIFO Gate。一次性部署建表，运行时不执行 DDL。分批写入后，在只读库验证行数、收入金额与全量载荷校验和，再切换同表的当前版本指针；失败保留此前已发布版本。保留当前和上个成功版本；页面详情请求固定版本，过期明确提示重新读取。磁盘 JSON 仅保留为回滚/导出副本。

列表拆为剧类型、受众方向、题材三列，使用独立占比条。受众展示最高收入类型内部的前两项，题材展示该类型最高收入受众内部的前两项；单元格明确父级范围。点击任意列进入相应层级，仍可回到全部类型。零收入保持“暂无占比”，不虚构百分比。

权限仍由现有频道列表接口核验，越权频道在数据库读取前返回 404。数据库故障明确显示不可用，不用零收入冒充查询结果。画像不可用时，发布选择继续沿用已有降级策略，并记录原因。

发布服务使用原有内部凭证，通过固定回环地址的只读画像接口获取指定频道的画像树，接口代其经过 FIFO Gate 读取数据库。发布用户不直连 SQL Gate，不扩大 OS 权限；外部入口不暴露该内部路由。该接口拒绝无凭证及超过 200 个频道的请求。

验证：47 项画像、分类、存储/分页/权限测试通过；309 项画像与原发布能力相关回归通过（其中已含 35 项画像/分类测试）；合计 321 项。浏览器验证加载、错误重试、三列展示与逐级详情。服务器部署继续执行 Linux 回归及真实数据校验。

部署：先将提交推送 GitHub，服务器获取精确提交后运行 `scripts/deploy_x_profile_database.py prepare`，保存输出的备份路径。`reader --backup PATH` 切换只读 API、小时刷新和静态页面；`runtime --backup PATH` 在新自动发布及素材池现有任务完成后切换新运行时。只重启画像 API、新自动发布和新网关。原发布服务与新上传服务不重启，不修改模板、排期、队列、占用或回执。

回滚：从同一已提交来源运行 `scripts/deploy_x_profile_database.py rollback --backup PATH`。核对后续文件/版本变更并等待受影响任务完成，只恢复代码和指针，保留 SQL 画像、业务数据库、发布回执和用户配置。不能恢复旧业务数据库备份来回滚代码。
