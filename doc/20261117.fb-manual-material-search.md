# FB manual material search repair

The picker returned HTTP 503 for complete drama codes, full drama titles and
space-separated material IDs. The source log recorded MySQL 3024: the old
substring predicate scanned the material catalog with a correlated drama and
product lookup. Increasing the SQL deadline would retain that expensive plan.

Complete material IDs (including several separated by spaces/commas), complete
source content IDs, complete material names and complete drama titles now use
their existing primary/name/source-content indexes. Exact code/name matches
take precedence, and the picker states which match was used. Source eligibility,
product identity, language matching, permissions and publication behavior stay
with the original repositories. An existing identity with no eligible results
does not fall back to an unrelated full scan.

Other text retains substring matching but scans at most 1,000 source IDs per
page, newest first. The original maximum ID is frozen in the cursor. Pages with
no match but remaining history explicitly show a continuation message and an
enabled Next button; they do not claim the complete search is empty. Numeric
lookups and the separate Moboreels text path retain their existing pagination.
The text scan fetches a bounded source range first and then matches drama names
through batches of indexed content IDs, retaining the product/language tuple.
The SQL cap stays at 8 seconds and every runtime read uses the existing FIFO
broker on port 63350.

## Validation

`python -m unittest discover -s tests -p test_fb_manual_material_search.py -v`
checks indexed identities, multi-ID results, retained product/language matching,
empty-page continuation, stable boundaries and page-full continuation. Execute
against the assembled production-compatible runtime, which includes the
existing `features.fb_auto_posts.languages` module. Also check changed Python
syntax, `node --check static/fb-video-publish.js` and `git diff --check`.

## Deployment and rollback

Push this branch, fetch the exact SHA into a clean CPU checkout, then execute
`python3 ops/fb_manual_material_search/deploy.py prepare DEPLOYMENT`.
The helper copies the current FB release and replaces only the reviewed search
methods. The main API's different Page-pool policy overlay is retained. It
backs up the FB ledger, affected files and current release pointer, updates the
three HTML cache versions without replacing other page changes, and prepares
the real-runtime unit test. Validate the candidate through the authenticated
read-only broker before switching.

`python3 ops/fb_manual_material_search/deploy.py activate DEPLOYMENT` uses the
already deployed, GitHub-verified FB HTTP drain helper, switches only the FB
owner, restores its dependent schedulers, and installs public/main static copies.
The main API does not restart. No test Posts, queue resets or retries are made.

`python3 ops/fb_manual_material_search/deploy.py rollback DEPLOYMENT` drains the
same owner and restores only code/static files. It refuses to overwrite later
changes and never restores an old database, receipt or credential.
