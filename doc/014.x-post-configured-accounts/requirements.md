# 014.x-post-configured-accounts 需求与技术设计

## 背景

当前 X 账号列表中有 9 个活跃账号，但每日任务仍把账号数量写死为 3，因此自然批次只生成并发布 3 条 Post。账号列表也没有展示账号是否已进入每日自动发布配置，管理员无法直接核对实际调度范围。

## 目标

- 每日任务由 `X_POST_DAILY_ACCOUNT_IDS` 的有序账号列表驱动，不再写死 3 个账号。
- 本次生产配置账号行 ID 为 `2,3,4,5,6,7,8,9,10`，下一次尚未生成计划的自然批次按 9 个账号执行。
- X 账号列表逐账号展示“已配置/未配置”自动发布状态。
- 当天已冻结的三账号计划不扩容、不补发另外 6 条。
- 保留现有素材池 FIFO、全局去重、完整预检、顺序发布和未知结果禁止盲重试规则。

## 范围

### 包含

- daily runner、X sidecar 对 1 至 50 个配置账号的解析、校验和批次处理。
- 两份服务端 env 中同名账号配置的一致性门禁。
- 账号列表 DTO 新增逐账号布尔字段 `daily_auto_publish_configured`。
- 管理员 X 账号列表新增“自动发布”列。
- 动态批次数量对应的单元测试、契约测试和部署验证。

### 不包含

- 不新增页面内编辑自动发布账号的功能；账号范围仍由 root-only env 维护。
- 不改变账号授权、Token、X API 权限或定时执行时间。
- 不修改素材池选取、违规过滤、GPU 修复、短链、文案或发布日志合同。
- 不创建数据库表或字段，不清理历史 run/queue/log。
- 不手工启动当天 daily service，不为当天新增的 6 个账号补发。

## 用户故事 / 业务规则

1. `X_POST_DAILY_ACCOUNT_IDS` 是每日自动发布账号范围的唯一配置来源，账号顺序也是计划和顺序发布顺序。
2. 配置必须包含 1 至 50 个互异的正整数账号行 ID；空值、重复、零、负数、非整数或超过 50 个均启动失败、fail closed。
3. `/etc/x-post-automation.env` 与 `/etc/x-post-daily.env` 必须保存完全相同、顺序一致的 `X_POST_DAILY_ACCOUNT_IDS`。部署前后均需解析比对，不允许只更新一份。
4. 新批次需要先完成全部 N 个配置账号的身份/可发布性校验，并取得 N 个互异、合规且完成媒体/文案/链接预检的素材，才可在一个事务中创建 N 条 queue。
5. 任一账号或候选在计划创建前失败时，整批记为预检失败，不创建部分 queue，不调用 X。
6. 当天一旦存在已冻结且有 queue 的计划，其 queue 数量、账号身份和顺序以历史计划为准；配置扩容不得向该计划追加账号或素材，也不得补发新增账号。
7. 当天重入只读取并按原恢复策略处理已冻结计划；已发布项幂等返回，未知结果或未解决的 `post_creating` 不得自动重试。
8. 全局素材排重、`account_id + run_date` 唯一约束、queue 绑定永久占用和未知结果停批策略保持不变。
9. `daily_auto_publish_configured` 只表示账号行 ID 是否属于 sidecar 当前解析成功的配置集合，不代表账号一定活跃、Token 一定有效或当天已发布。
10. 账号列表响应只逐账号返回上述布尔值，不返回完整配置 ID 数组、env 内容、用户名清单或任何凭证。
11. 管理员页面严格按布尔值显示：`true` 为“已配置”，`false` 为“未配置”，不能根据账号活跃状态猜测。
12. 本次配置扩容后只等待下一次自然 timer；部署当天 queue/log/Post 数量不得因部署增加。

## 交互与流程

1. 管理员打开 X 账号列表。
2. 页面通过 `GET /api/admin/x-accounts` 获取实时列表。
3. 每行根据 `daily_auto_publish_configured` 显示自动发布配置状态。
4. 自然 timer 触发时，runner 先查询当天是否已有冻结计划。
5. 已有计划则按历史计划幂等读回，绝不按新配置追加 6 条；无计划才按当前配置的 N 个账号执行全批预检和事务预留。
6. 预留成功后继续沿用现有逐账号顺序发布和停止策略。

## 技术设计

### 影响模块

- `scripts/x_post_daily_runner.py`：配置解析、动态候选数量、全批预检、计划响应校验和汇总。
- `features/x_accounts/oauth_service.py`：动态 daily scope、计划/发布授权和账号 DTO 配置状态。
- `features/x_posts/service.py`：移除固定三条的批次校验，继续依赖现有事务和唯一约束。
- `static/x-account-list.html`：新增状态列，并同步空表/加载态 `colspan`。
- `deploy/x-post-automation.env.example`、`deploy/x-post-daily.env.example`：记录 1 至 50 个账号的配置合同。
- 相关 X 账号、daily、ledger、页面契约测试。

### 数据结构

不变更 SQLite schema。`daily_auto_publish_configured` 是请求时根据当前 sidecar 配置派生的 DTO 字段，不落库。

### API / 接口

- `GET /api/admin/x-accounts`：每个 `items[]` 增加严格布尔字段 `daily_auto_publish_configured`。
- 共用账号 DTO 的 `GET /api/x-accounts` 同样返回该字段，且不暴露完整配置集合。
- 既有内部 daily plan/query/publish 路由改为支持配置数量 N，鉴权与响应脱敏不变。

### 异常与边界

- 两份 env 不一致：阻止上线/启动，不运行发布。
- 配置账号不存在、非活跃、身份不一致或不可发布：全批预检失败，零 X 写入。
- 可用素材少于 N：`failed_preflight`，零 queue、零 X 写入。
- 当天已有三账号计划后扩容到九账号：只读回三账号计划，新增六账号等待下一自然日。
- 账号处于停用状态但仍在配置中：列表仍显示“已配置”，daily 全批预检失败，提醒运维修正账号或配置。
- 配置达到 50 个时仍须满足请求体、存储空间和任务超时边界；超过 50 个直接拒绝。

## 验收标准

- 1、9、50 个互异正整数配置均能被两端按原顺序解析；0 个、重复、非法或 51 个配置均 fail closed。
- 两份 env 的账号列表完全一致；生产安全核对只记录数量与 ID，不输出真实用户名或 Token。
- 9 个活跃账号的列表行均显示“已配置”，未进入配置的账号显示“未配置”。
- API 对每个账号只增加布尔字段，不返回完整配置数组或凭证。
- 当天既有三账号批次和 Post 数量在部署前后保持不变，没有新增 6 条。
- 下一次无既有计划的自然批次必须先完成 9 账号和 9 素材全批预检；成功时原子创建 9 条 queue，失败时创建 0 条 queue。
- 原素材全局排重、账号日唯一、发布日志、未知结果停批和禁止盲重试回归通过。

## 风险与待确认

- 账号数由 3 增至 9 后，素材池每天至少需要 9 条可用互异素材；不足时会按安全合同整批不发。
- 顺序发布总耗时和 GPU 修复次数可能上升，需要在测试及首个九账号自然批次中确认仍落在 oneshot 超时内。
- 本次生产将单批 GPU 修复上限同步设为 9，并将 oneshot 超时提高到 360 分钟；仍需以首个九账号自然批次的实际耗时复核。
- 本文不代表已完成代码或生产验证；实际结果写入 `sa-code-review.md` 和 `test-report.md`。
