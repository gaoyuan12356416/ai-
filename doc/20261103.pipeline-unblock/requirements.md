# GPU 空闲与历史回执阻塞修复

2026-11-03 用户授权尽快修复。保持前端当前保存容量，不终止在途制作或发布，不重发结果未知任务。X 恢复由同时进行的独立工作负责，本改造不切换 X 开关、不覆盖其运行代码。

## 已确认的问题

- 监控把 worker 分为 busy / idle / draining / offline，但服务器卡片只有 busy / idle / alive，导致排空时显示 0 / 0 / 8。
- GPU 当前空闲的实际条件包括 X 暂停接单、FB 和 TT 原生未知发布占用账号。不能以清锁方式制造并发。
- FB 29162、29303 的平台视频已发布，旧请求响应中断后本地没有回执。只读 Page videos 查询找到冻结文案、短链、时长匹配的视频，二次对象回读已确认所属 Page 及 published 状态。
- TT 有 publish_id 的三条回查成功仍处于平台 PROCESSING_DOWNLOAD，本地 pending 分支遗留旧连接错误。修正错误展示，不释放其账号。
- TT 987 的历史发布领取全部在 creator_info 前置检查被拒绝。仅在完整审计、无 init/发布回执、任务 CAS 均通过时终结为已知失败，不重发。

## 设计与边界

1. 仅部署静态监控修复，兼容线上既有 DTO，明确显示排空人数和未结束任务。
2. 回填工具默认只读，冻结任务清单和证据哈希；变更前备份原生账本，事务检查状态、身份和历史尝试未变化。平台只读查询。
3. 回填沿用原生事实表，中央采集器自然收敛并解除历史锁，禁止直接改中央锁或制造新发布任务。
4. 未被证据证明的未知结果继续保护，历史记录和素材身份保留。当前容量以部署前实时配置为准。

## 验收

排空显示完整且人数恒等；两条 FB 回执各计一次，重复执行不重复记账，漂移拒绝；TT pending 清旧错误但保留核对锁；TT 前置拒绝不重发历史；GitHub 精确版本窄部署及原生事实回读。
