# X material-pool language shortage alerts

After each ordinary material-pool selection, notify the configured Feishu group
when a verified usable language/account scope was not filled. Each language shows
required, selected and missing videos. Locked/unauthorized accounts excluded by
normal account preflight are not counted as missing material. Long-video membership
capacity rejection counts and the bounded scan limitation remain explicit.

The scheduler freezes the language/count snapshot used by that selection. It emits
one structured journald event after confirmed reservation (including successful
readback of an ambiguous reservation), or after zero-candidate preflight failure.
It does not infer yesterday's language from today's account configuration. Shared
query failures, unknown reservations, drama schedules and failed X writes do not
become material-shortage alerts. Candidate selection, queues and publication are
unchanged. Nothing calls Feishu in the publisher process.

`x-material-shortage-alert.timer` consumes these events approximately every minute.
It stores event content and a journal cursor atomically in its own data-disk SQLite
ledger, using run date/time/config version as the deduplication identity. Explicit
send failures may retry up to three times with the same request UUID. Uncertain
results remain for read-only receipt reconciliation; they never block other alerts.
Restart/replayed journal entries do not send the same batch twice. Installation
starts from activation time, without replaying historical shortages.

Recipient IDs and Feishu credentials stay out of this repository. The root-only
`/etc/x-material-shortage-alert.json` supplies `chat_id`, `mention_id` (the verified
group member's open ID), and `feishu_config` (existing app configuration path).
The installer adds `start_at` and the data-disk `state_dir`. The activation notice
also uses a durable deduplication key and is only sent by explicit `--announce`.

## Validation

Run `python -m unittest scripts.test_x_material_shortage_alert scripts.test_x_post_schedule_runner`.
This covers partial and empty capacity, aliases, confirmed reservation versus
reservation rejection, normal publishing continuity, durable deduplication,
uncertain send isolation and explicit rejection retry. Tests use no external posts.
Use `x_material_shortage_alert.py --config CONFIG --event-file FIXTURE` for a
no-send card preview, and `--config CONFIG` for a read-only journal check.

## Deployment and rollback

Fetch the exact GitHub commit to an isolated source checkout. Run the focused tests
there, then invoke `scripts/deploy_x_material_shortage_alert.py --config PRIVATE_JSON
--runner-before LIVE_RUNNER_SHA256`. The installer copies the current composite X
release, overlays only the scheduler and observation helper, installs the independent
notifier and switches symlinks atomically. Only the new notification timer starts;
no X publisher, planner or in-flight worker is stopped/restarted. An already running
scheduler keeps its existing release; the next natural invocation gets the change.

Read back the notifier timer, its natural execution, next trigger and group receipt.
Verify the X publisher PIDs and prior scheduler states remain unchanged. Save the
printed manifest under the deployment record. Roll back with:

`python3 SOURCE/scripts/deploy_x_material_shortage_alert.py --rollback MANIFEST`

Rollback stops only the notifier timer and waits for an accepted notification to
finish. It restores code/configuration and preserves notification receipts, publisher
databases, queues and tokens. If another deployment has changed the X symlink, review
and restore only the recorded files rather than overwriting that newer deployment.

Feishu mention syntax follows the official
[message content reference](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json?lang=zh-CN).
