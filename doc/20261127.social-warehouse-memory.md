# Social report refresh memory recovery

The hourly and manual social report collector repeatedly hit its 2 GiB systemd
memory limit on 2026-11-27. Kernel logs recorded cgroup OOM kills after warehouse
tables were written and before publishing the SQLite serving snapshot. The last
published snapshot remained at 2026-11-26 20:19:47 UTC; November 27 was missing.

The collector kept both parsed source rows and serialized MySQL batches alive,
then created another full list of serialized rows for each SQLite insert. Release
the verified MySQL batches before building the serving copy, and stream SQLite
inserts. Attribution, monetary values, duplicate handling, replica verification,
atomic publication and refresh locking remain.

The active collector was recovered without restarting it by temporarily setting
only its runtime MemoryMax to 4 GiB. It published version
`20261127T085020175551Z` at 09:07:16 UTC and subsequently exited successfully.
Recovery artifacts are under `/mnt/data-disk/social-warehouse-recovery-20261127`.

Validation:

- `PYTHONPATH=.:tests python -m unittest tests.test_social_warehouse_memory tests.test_social_tiktok_warehouse tests.test_social_iaa_effects`
- `scripts/check_social_snapshot_memory.py --source SNAPSHOT --output SCRATCH`
  runs in an isolated 2 GiB service against the actual published snapshot. It
  recreates write batches, verifies their row counts, creates a separate SQLite
  copy and compares every table's sorted content hash with the original.
- Apply only `features/social_analytics/warehouse_refresh.py` from the pushed
  commit after backing up and checking the current file hash. The source file
  matches the active TT promotion warehouse release's baseline. Do not replace
  other modules from this branch or change publication services.
- Restore the original runtime memory limit after the old collector exits, then
  verify a complete manual refresh through the public report UI under 2 GiB.

Deployment needs no long-running service restart. Each refresh imports the new
collector at process start. Preserve all current warehouse data and manifests.
The scoped rollback script in the recovery folder restores the backed-up source
after checking the deployed hash and keeps 4 GiB runtime headroom for the older
implementation. Do not roll back business data or replay publications.

## Remove the fixed limit at the operator's request

The operator subsequently asked which server owned this 2 GiB limit and to remove
it if feasible. The limit was introduced with the original warehouse service on
2026-11-04; no business rule or capacity calculation requiring 2 GiB was found in
the deployment source. CPU host 43.166.187.96 has 63,202 MiB RAM with 41,032 MiB
available at inspection. The fixed limit has already caused repeated failures.

Set only this unit's `MemoryMax=infinity` and clear the temporary runtime override
created during recovery. Retain the memory optimization, single-instance lock,
timeout, priority, permissions, timer and host monitoring. Applying the resource
property and reloading the unit configuration needs no service restart. Back up
the original unit and keep a separate scoped rollback that restores its exact
contents and 2 GiB property; do not restore other units or snapshot data.
