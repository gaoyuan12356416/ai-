# 文案临近发布优先与三路并发

大量 FB 任务集中入队时，旧队列只按入队时间串行处理剧目/语言分组，造成已到发布时间的任务尚未生成就采用现行文案。

新队列从原生任务读取实际发布时间：FB 自动模板 `planned_publish_at_utc`，FB 视频 `planned_at_utc`，X 池/手动批次的计划时间，X 标签模板 `scheduled_at_utc`。按最早发布时间选择产品/剧目/语言分组，组内也按发布时间排序。缺少有效时间时沿用入队时间。已到期或五分钟内到期的任务无需等待 60 秒凑批；其他任务保留满 100 条或 60 秒的规则。一次领取仍最多 100 条，并把同组填充范围限制到最近发布时间窗口，防止顺带领取翌日文案而挤占当前批次。首次失败依旧进入下一就绪批次或在 60 秒后重试一次，重试项也按发布时间排序。

独立 worker 默认同时生成 3 个批次，可用服务环境变量 `STORY_COPY_CONCURRENCY` 调整正整数，设为 `1` 可恢复串行。每个线程使用独立数据库连接，通过原有 `BEGIN IMMEDIATE` 事务领取任务，模型调用不持有领取锁。启动恢复遗留批次；运行中异常只恢复本线程持有的批次，避免误判其他正在生成的任务。发现任务时只刷新未生成任务的排队时间，不改已冻结事实和已完成文案。人工文案优先、事实/语言/长度校验、一次重试和原生发布回执优先规则保留。

## 验证

```sh
python3 -m unittest tests.test_story_copy
python3 ops/story_copy/check_priority.py /mnt/data-disk/story-copy-deploy/canary-priority-COMMIT
```

单元测试覆盖临近任务优先、同剧远期任务不抢占、凑批窗口、调期更新、四端时间映射、三线程同时生成且无重复领取、单批失败隔离和生成期间发布定稿。canary 使用新的隔离数据库和三条虚构剧情执行三个真实模型调用，核对领取顺序、三路重叠及文案验收；不会发现真实队列、发通知或调用社媒发布接口。

## 部署与回滚

从 GitHub 拉取并检出精确提交，运行测试及 canary 后：

```sh
python3 ops/story_copy/deploy_priority.py prepare /mnt/data-disk/story-copy-deploy/priority-COMMIT
python3 ops/story_copy/deploy_priority.py apply /mnt/data-disk/story-copy-deploy/priority-COMMIT
```

prepare 核对三个线上文件与提交父版本一致，保存旧发布目录、服务状态和中央数据库备份。apply 等待所有在途文案批次完成，持有领取锁切换，仅重启 `story-copy-worker.service`。验收启动日志 `workers=3 priority=publish_time`、线上文件摘要、队列/回执与发布器 PID。设置服务及发布调度不重启。

回滚使用同一检出的脚本和部署目录：

```sh
python3 ops/story_copy/deploy_priority.py rollback /mnt/data-disk/story-copy-deploy/priority-COMMIT
```

仅恢复代码链接并安全切换 worker；保留当前数据库、已完成文案、重试记录及发布事实。备份数据库不直接覆盖生产。新增的 payload 时间字段可被旧版忽略。
