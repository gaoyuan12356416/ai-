# GPU backend assistance

This release stages independent CPU preparation and read/compute services on
the existing 40-core Hong Kong host. It does not replace existing GPU workers.
The CPU preparation dependencies are frozen from the running CPU preparation
release; social analytics dependencies are frozen from the current main API.
Reconciled files are deployed only into the new isolated runtime, never over
existing publishers, coordinators or renderer directories.

The new `hk-cpu-assist` identity only enables prepare adapters, locally clamps
publication to zero and preparation to at most two slots. Register and set
both server-side capacities to zero before starting it. Transfer one existing
CPU preparation slot only after that slot's current task naturally completes.
Use the versioned coordinator capacity API, preserving all other node limits.
Keep the original backend/profile, output contracts, leases and receipts.

The parent assistance slice is capped at 8 CPUs and 16 GiB; the media child at
6 CPUs and 12 GiB. Existing GPU services are outside this slice and are not
restarted. A stop requests natural draining and never SIGKILLs media children.

Rollback: set only the assistance preparation capacity to zero through the
versioned API, wait for its claims and receipts to settle, restore each released
CPU slot, then stop only the assistance service. Preserve state and artifacts.
Database access remains disabled until session read-only enforcement and the
shared 14-query plus one-watchdog budget have been verified. On November 23,
the user identified `10.89.0.108:3306` as a read/write proxy using the CPU
credentials. Its server `read_only` flag is zero; this proxy is an explicit
exception to the original endpoint assumption, not permission for GPU writes.
Only fixed business reads inside read-only transactions may be enabled after
the unified admission and unknown-session accounting are implemented.

## Immutable report stage

`gpu_offload.reader` has no SQL credentials or SQL endpoint. It receives an
already-published social analytics SQLite snapshot, checks its digest and
integrity, and atomically changes the serving version. Incomplete transfers
leave the successful version available. Three complete versions are retained;
each contains the original full historical range. The transfer is limited to
2 MiB/s and performed once per version, with a one-minute manifest check.

The existing report adapters, aggregation, options and CSV contract are reused
from the live main API. A request pins one immutable version. CPU and GPU shadow
comparisons use that same snapshot and never rerun collection SQL.

The CPU gateway checks the current cookie session on every request, then checks
the social module and saved navigation permissions. Cache identities include
tenant, user, role, permissions, filters and data version. Concurrent identical
requests share one refresh. Refresh failures back off and retain a marked stale
response; a cold failure returns unavailable, never fabricated zero totals.
The report percentage is changed through the independent gateway JSON at
10/50/100 only after each observed 30-minute stage. Initial setup is zero.

Monitor caching is local on CPU and adds at most ten seconds. The first stage
caches administrator reads; other actors continue through the existing owner
resolver and authorization on every request. No active ledger is copied.

The read worker and private tunnel share a child slice capped at two CPUs and
4 GiB, within the parent's eight CPUs and 16 GiB. New public routing uses only
six existing read URLs, an independent Nginx include and graceful reload.
Business writes and all original publishers keep their existing routes.

Read rollback: remove only the offload Nginx include, test configuration and
gracefully reload Nginx; or set report percentage and monitor caching to zero
while keeping the gateway. Stop the snapshot timer and independent read units
after route rollback. Preserve the CPU source warehouse and all dispatch state.

Validation includes concurrent refresh deduplication, bounded memory, stale
fallback/backoff, real HTTP permission revocation, cross-owner cache isolation,
snapshot checksum/truncation/path safety, pinned version consistency, and
tenant/owner report and export checks with SQL execution forbidden.
