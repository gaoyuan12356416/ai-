# GPU backend assistance

This release stages independent CPU preparation and read/compute services on
the existing 40-core Hong Kong host. It does not replace existing GPU workers.
The CPU preparation dependencies are frozen from the running CPU preparation
release; social analytics dependencies are frozen from the current main API.
Reconciled files are deployed only into the new isolated runtime, never over
existing publishers, coordinators or renderer directories.

The new `hk-cpu-assist` identity only enables prepare adapters, locally clamps
publication to zero and preparation to at most two slots. Register and set
both server-side capacities to zero before starting it. Transfer one existing
CPU preparation slot only after that slot's current task naturally completes.
Use the versioned coordinator capacity API, preserving all other node limits.
Keep the original backend/profile, output contracts, leases and receipts.

The parent assistance slice is capped at 8 CPUs and 16 GiB; the media child at
6 CPUs and 12 GiB. Existing GPU services are outside this slice and are not
restarted. A stop requests natural draining and never SIGKILLs media children.

Rollback: set only the assistance preparation capacity to zero through the
versioned API, wait for its claims and receipts to settle, restore each released
CPU slot, then stop only the assistance service. Preserve state and artifacts.
Database access remains disabled until session read-only enforcement and the
shared 14-query plus one-watchdog budget have been verified. On November 23,
the user identified `10.89.0.108:3306` as a read/write proxy using the CPU
credentials. Its server `read_only` flag is zero; this proxy is an explicit
exception to the original endpoint assumption, not permission for GPU writes.
Only fixed business reads inside read-only transactions may be enabled after
the unified admission and unknown-session accounting are implemented.

## Immutable report stage

`gpu_offload.reader` has no SQL credentials or SQL endpoint. It receives an
already-published social analytics SQLite snapshot, checks its digest and
integrity, and atomically changes the serving version. Incomplete transfers
leave the successful version available. Three complete versions are retained;
each contains the original full historical range. The transfer is limited to
2 MiB/s and performed once per version, with a one-minute manifest check.

The existing report adapters, aggregation, options and CSV contract are reused
from the live main API. A request pins one immutable version. CPU and GPU shadow
comparisons use that same snapshot and never rerun collection SQL.

The CPU gateway checks the current cookie session on every request, then checks
the social module and saved navigation permissions. Cache identities include
tenant, user, role, permissions, filters and data version. Concurrent identical
requests share one refresh. Refresh failures back off and retain a marked stale
response; a cold failure returns unavailable, never fabricated zero totals.
The report percentage is changed through the independent gateway JSON at
10/50/100 only after each observed 30-minute stage. Initial setup is zero.

Monitor caching is local on CPU and adds at most ten seconds. The first stage
caches administrator reads; other actors continue through the existing owner
resolver and authorization on every request. No active ledger is copied.
Because the page polls every fifteen seconds, an active viewer also registers
a background refresh while the ten-second snapshot is still useful. Only one
background monitor read runs at a time, using the current cookie permissions;
it stops forty seconds after the last view, after revocation or refresh failure,
and pauses when CPU utilization reaches 75% or available memory falls below
8 GiB. This reads the CPU local ledger and never adds a business SQL query.
Configuration can disable prefetch immediately. The independent gateway handles
termination by finishing accepted requests; the first upgrade uses a second
loopback port and graceful Nginx reload so the older gateway can finish its work.

The read worker and private tunnel share a child slice capped at two CPUs and
8 GiB for Campaign staging, with media separately capped at 8 GiB, within the
parent's eight CPUs and 16 GiB. New public routing uses only
six existing read URLs, an independent Nginx include and graceful reload.
Business writes and all original publishers keep their existing routes.

Read rollback: remove only the offload Nginx include, test configuration and
gracefully reload Nginx; or set report percentage and monitor caching to zero
while keeping the gateway. Stop the snapshot timer and independent read units
after route rollback. Preserve the CPU source warehouse and all dispatch state.

Validation includes concurrent refresh deduplication, bounded memory, stale
fallback/backoff, real HTTP permission revocation, cross-owner cache isolation,
snapshot checksum/truncation/path safety, pinned version consistency, and
tenant/owner report and export checks with SQL execution forbidden.

## Shared SQL admission (candidate, not activated)

The candidate retains the existing CPU socket protocol and child/session
protections from the production gate (source SHA-256
`6970445f80659c84410996a028a6a7728339a80b5e3e9bba1814ed6d85bb31d2`).
Local queries, conservative old-gate occupancy and durable GPU leases consume
one total of fourteen. One independent watchdog remains unchanged. Initial
remote occupancy is limited to one, with no token-bucket burst above two query
starts per second including initialization statements. GPU SQL remains disabled.

A reservation cannot open TCP until a separate durable, single-use connect
permission is acknowledged. It binds the server UUID, MySQL connection ID and
read-only flags. Lost heartbeats or a broker restart mark issued connections
unknown and keep their occupancy. Only observed server EOF or a bounded query
proving absence on the same server UUID releases an issued connection. Absence
on a different proxy backend is insufficient. Unidentified interrupted connects
remain visible and reserved. Recovered CPU leases are also retained, without
running the old gate's process-termination recovery routine; legacy CPU clients
still use their established local process identities and protocol.

The Linux handover test uses independent temporary Unix sockets and no SQL.
It keeps an accepted old lease open across an atomic listener replacement,
then verifies that it finishes normally while a subsequent request uses the
new gate. A status reply on the retained old socket establishes an accept
barrier. Until it passes, new admission reserves the entire old budget. After
the barrier, old active/queued state and accepted Unix sockets provide a
conservative occupancy bound. Remote admission waits until the old gate drains.
The production stop path is not used to force that drain.

Candidate tests also cover concurrent CPU/GPU admission, daemon recovery and
graceful admission shutdown. Deployment still requires Linux test results,
versioned socket/unit ownership, rollback and a real bounded read-only canary;
staging this candidate does not enable business SQL or migrate a refresher.

### November 23 activation and runtime-directory recovery

Candidate `ec0791b36066584bc5e473af5a156e70b1aebba3` passed fifteen Linux
lease/socket tests. At 10:58 UTC a bounded read-only live canary kept the same
MySQL connection ID and TCP socket across the admission switch, then observed
server EOF before releasing its existing budget slot. GPU business SQL remained
disabled. Existing API, coordinator, renderer and publisher processes stayed up.

The old daemon drained, but stopping its systemd unit removed its owned runtime
directory, including the newly replaced socket path. This exposed a gap in the
original handover test, which did not emulate systemd directory cleanup. At
11:05:22 UTC admission was restored with a second compatible listener while the
first shared daemon kept its two already-accepted leases and drained. Their
occupancy was deducted from the new listener's fourteen-slot total. No task
ledger was reset, no publication was replayed and no active query was killed to
restore the path. A temporary local helper retires that reservation only after
admission is closed, active/queued counts are zero and the durable local session
ledger is empty. The new unit is `ai-backend-shared-sql-green.service`, with
the original `sql-connection-gate.service` name aliased to it. SQL remains off
for GPU workloads pending client and reconciliation validation.

The fix explicitly preserves the old runtime directory through retirement and
gives the replacement service the same persistent runtime-directory ownership.
An added test emulates systemd cleanup and checks that the new socket survives.
Do not claim this rollout had no admission interruption; any final acceptance
must include this incident and subsequent checks. Source/report snapshots and
original service state remain available for rollback. To disable GPU admission,
set `gpu_queries_enabled` to false in `/etc/ai-backend-offload/shared-sql.json`;
keep the shared gate running and preserve both lease ledgers. Never restore an
old empty ledger or force-stop a gate with active or unknown connections.

### Reconciliation without an additional watchdog connection

Unknown remote leases are checked by the existing SQL watchdog on its existing
controller connection, at most two identities per minute. The server UUID,
connection ID and authenticated database username must match. A different
backend, invisible account, live session or failed readback keeps the slot.
The watchdog's original timeout policy remains intact. Requests and proofs are
bounded local files; reconciliation adds no persistent database connection.

Further shared-gate upgrades stage a second listener with all fourteen slots
reserved, atomically switch only new admissions and keep previous connections
alive until the old active/queued state and durable ledger are empty. Both
units preserve the canonical runtime directory and disable forced termination.
An accept-barrier failure restores the previous listener while the candidate
has admitted no work. Keep GPU admission disabled throughout upgrades.

The internal read/write proxy passed an explicit read-only transaction canary,
but distributed sessions among reader UUIDs different from the watchdog's
dedicated endpoint. GPU business SQL therefore does not use that proxy yet.
The initial path forwards the originally approved `101.32.56.53:63350` endpoint
through the existing CPU host's private SSH connection. Query execution and
report computation remain on Hong Kong; CPU only transports encrypted bytes.
No additional DB privilege or write endpoint is introduced. One tunnel serves
admission and data and is capped at 20% of one CPU inside the two-core read slice.

Reconciliation first verifies that a particular live session is visible on the
same server UUID and account, and durably retains that evidence. Only a later
absence can release an unknown lease. Sessions never observed alive remain
reserved for investigation; this affects their slot, not unrelated CPU work.
At most two connected or unknown sessions are checked each minute on the same
existing watchdog connection. Normal peer-EOF receipts release immediately.

### Campaign Copy staging

The existing service's latest durable seed was generated on November 14. On
November 23 its process held 1,018 `/dev/null` descriptors against a 1,024 limit.
An isolated no-SQL reproduction confirmed that this Python runtime leaks the
duplicated descriptor when `socket.fromfd` is called on a non-socket. The frozen
fallback source now inspects descriptor type first; the GPU refresher uses the
new bounded driver and does not use that scan at all.

The new refresher reuses the exact source arithmetic, pagination, date selection,
mapping rotation, 15-second statement limit and 840-second SQL budget. Its seed
must already exist, so missing cache cannot initiate a new full-history scan.
Refresh and local indexing run in separate child processes to avoid overlapping
their memory peaks. A local immutable SQLite index streams complete historical
rows into compressed views, rather than retaining the entire report as Python
objects in the serving process. The existing JSON v2 and browser CSV contract
are retained. The public gateway rechecks the current login for every request,
including cache hits; the private reader enforces the exact source tenant.
The original organization-wide report has no `ad_control_v3` entitlement, so
migration does not add that unrelated permission. Full current permission
scope remains part of the actor-specific cache key.

This code remains staged until the old CPU refresher is disabled after its
current query completes. Do not start the new refresh timer concurrently with
the original service. Public routing, single-executor cutover and resource
profiling remain separate deployment steps; a successful fixture test alone is
not proof of a completed production migration.

The first complete seed was checked row by row: 584,089 Campaigns, 1,187,705
daily rows, 6,188 extra entities and 19,960 extra daily rows matched. Indexing
took 36 seconds; the historical merge's no-SQL full-seed test took 62 seconds.
Both peaked at approximately 3.8 GiB. Read/report and media child slices now
have 8 GiB each, within the unchanged shared 16 GiB and eight-CPU cap. Media
remains limited to six CPUs; readers and refreshers share two CPUs.

Campaign routing is at ten percent and social reporting at fifty percent.
Neither may advance based only on elapsed idle time. Actual reads and the
minimum observation windows are still required. The media helper has completed
four real preparations as of 20:32 China time; the required twenty examples for
a second slot have not been met. Cache-hit monitor samples are below one
second P95; full-page improvement and a representative peak remain unverified.

The CPU Campaign fallback receives the exact compressed immutable index, capped
at 2 MiB/s, validates its checksum and SQLite integrity, then publishes it
atomically. It runs no business SQL and does not rebuild the full JSON index.
Failed transfer preserves the previous version. This lets the original CPU
refresher retire independently of percentage-based page routing, with just one
HK refresher retaining the original cadence and query scope. Local snapshot
sync is checked every sixty seconds. Refresh SQL must stay disabled until the
old owner is confirmed idle and its service is disabled.

At 20:47 China time the old Campaign process (4040736) was confirmed idle,
with no established connection or shared SQL lease, then retired and disabled.
Both serving paths now use the verified immutable index. The first HK refresh
was aligned with the original next attempt, at 20:53; it failed with MySQL 2013
while receiving a copy-log page. Its old snapshot stayed published and further
refreshes were explicitly paused for investigation. No CPU SQL fallback ran.
The candidate reduces only that page size from 250,000 to 50,000 rows, preserving
the disjoint primary-key scan, existing filters, entire history, 15-second query
limit and 840-second refresh budget. Query count can increase with smaller
pages; the two-starts-per-second limiter and shared connection budget remain.

This short failed connection also exposed a reconciliation gap: it ended before
the minute-based watchdog ever sampled it alive. Reconciliation now accepts a
fresh absence proof only when server UUID and authenticated database user match
and the same observation verifies the watchdog's own visible session. MySQL
permits nonanonymous users to see their own account's threads; see the
[official process-list documentation](https://dev.mysql.com/doc/refman/8.0/en/processlist-access.html).
Otherwise the prior positive-visibility requirement remains. A small local
consumer reads that proof without SQL and without restarting the active gate;
it uses `recover=False`, never resets live/reserved leases, and only releases
proven-ended unknown sessions. Tests cover missed short sessions, wrong accounts,
missing visibility and preserving an unrelated live reservation.

At 21:09 China time the smaller-page attempt failed with the same connection
loss. Smaller pages did not resolve it and are reverted to the original
250,000-row setting. Inspection found that the old report explicitly negotiated
MySQL compression, whereas the migrated PyMySQL connection did not. The new
Campaign connection uses pinned mysql-connector-python 9.4.0 with compression
and the same shared lease, read-only snapshot, deadlines and query-start rate.
The pure-Python transport permits COM_QUIT followed by observed peer EOF before
locally closing its socket. A local abort or driver close error still retains
the occupied slot for the existing watchdog to reconcile. Light metadata
queries keep PyMySQL. This is a transport correction, not permission to relax
query budgets or run parallel refreshers. The pure wheel's SHA256 is
`56e679169c704dab279b176fab2a9ee32d2c632a866c0f7cd48a8a1e2cf802c4`.

Campaign rollback after retiring port 8831 must not restore the old Nginx
target on its own. First run `python -m features.gpu_offload.campaign_rollback hk`
in the HK release to disable future refreshes without interrupting the current
one. Then run `python3 -m features.gpu_offload.campaign_rollback cpu` in the CPU
release: it routes all reads to the already verified CPU immutable snapshot.
It never enables the old SQL refresher, rewinds data or clears leases. Returning
SQL ownership to the old CPU process is a separate drain-and-owner transfer.
