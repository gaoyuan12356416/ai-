# YouTube cover generation under a historical publishing hold

The distributed adapter used the same `youtube:channel:<channel_id>` resource
for both cover preparation and video publication. An old unresolved upload
therefore prevented unrelated new covers from even starting.

Cover preparation now reserves `youtube:cover:<preparation_id>`. It still
requires the frozen channel identity, uses the existing atomic job claim,
native task/version lease and shared generation-intent journal, and writes
only its own private image for owner review. Different tasks on the same
channel may prepare concurrently within the existing node capacity.

Video publication retains its channel resource, approval requirements and
all historical unknown-outcome holds. This change does not resolve, reset,
retry or publish historical tasks.

The next normal canonical scan refreshes an old cover resource only for a
never-claimed, queued preparation with no hold, external intent, claim or
receipt, when the current native state is executable `queued_generation`.
Running and previously claimed jobs keep their original resource contract.

Deployment ownership must be coordinated with the ongoing pipeline release.
Only the coordinator needs the changed `adapters.py` and `core.py`; node and
native bridge changes for slow handoffs/unstarted generation are a separate
preceding patch. Install from the verified GitHub commit after backing up
the two files and the live dispatch SQLite database. Preserve unrelated
runtime changes and current channel admission settings.

Rollback: stop new preparation claims and drain active work, restore the
two pre-deployment files, then restart only `pipeline-coordinator.service`.
Keep the current database, cover assets, approvals, reservations, upload
receipts and unknown holds. Do not restore the pre-deployment database or
rewrite a live resource reservation. If restoring old channel-level cover
serialization is required, rebind only still-unclaimed queued cover rows
after the drain and a fresh canonical identity check.

Regression coverage in `scripts/test_pipeline_youtube_cover_resources.py`
uses real temporary SQLite databases and checks: a cover can start under a
historical upload hold while a new upload cannot; old unclaimed cover rows
are refreshed without changing the hold; active/paused jobs are unchanged;
two nodes cannot generate one task simultaneously; separate covers may
prepare together; publication and missing-channel identity rules remain.
