# BUG-002 临时管理员本人别名未扩展

## 发现时间与环境

生产首轮只读验收，2026-07-17。

## 现象

王鹏和凌云柯为了测试暂时被授予 admin。页面和规则列表可以加载，但 `/meta` 的 `actor.optimizer_ids` 为空；管理员选择自己的小号时，原逻辑只保存所选单个优化师，不能保证本人两个范围同时生效。

## 影响

- 王鹏选择 387 或 686 时可能只调控一个范围。
- 凌云柯选择 404 或 687 时可能只调控一个范围。
- 两人恢复普通优化师后原多别名逻辑正常，但测试期 admin 状态不满足业务要求。

## 根因

服务端管理员分支只加载全部可选优化师，刻意跳过当前用户身份解析；前端管理员选择也只更新单个 `optimizer_id`。

## 修复

- 管理员 best-effort 解析本人强身份别名，并通过 `/meta` 返回本人 `optimizer_ids`。
- 管理员选择本人任一别名时，创建、更新和范围估算自动扩展完整本人集合。
- 选择其他优化师保持单选，不扩大原管理员权限。
- 本人身份未解析、姓名冲突或超过上限时返回空集合，但不阻断管理员功能。
- UI 在选中本人别名时明确展示全部会同时生效的名称和 ID。

## 验证

- 后端：选 686 得到 387/686；选他人 404 仅得到 404；身份冲突不阻断 admin。
- 前端：本人别名选择映射为完整数组，选择他人映射为单元素数组。
- 全量 V3 自动化：204/204 通过。
- 生产仅使用 token-safe GET 验证，不创建规则、不试算、不触发 Meta 写接口。

## 状态

本地修复完成，待生产增量发布与双用户只读验证。
