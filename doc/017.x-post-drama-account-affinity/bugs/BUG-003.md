# BUG-003 10:06 未绑定新剧预检失败后未继续 FIFO 补位

## 发现阶段

2026-07-29 10:06 短剧定时批次运行核查。

## 现象

冻结账号集合中某个待分配账号取得一部未绑定新剧后，该剧在确定性源数据、剧集或媒体预检阶段失败。批次直接进入 `failed_preflight`，没有继续选择池内创建时间更晚但可用的新剧。

## 影响

- 本时间点全部账号均未建队列，正常可用的后续新剧也没有被利用。
- 失败时间点不能依靠定时器自动追赶；在修复和安全核查前不得盲目补发。
- 未发现可据此认定已发布的 Post；是否补救必须以批次、队列和发布账本的实时数据为准。

## 期望结果

1. 未绑定且没有任何队列/发布历史的新剧确定性校验失败时，写入 `validation_failed` 和脱敏错误，不绑定、不建队列，并继续 FIFO 扫描下一部未绑定新剧。
2. 已绑定或有任何历史的新剧失败时，保持剧—账号关系，写入 `needs_review` 并停止整批，禁止跳过、换绑或重新分配。
3. 只有全部冻结账号均有合格候选后，才在一个事务内创建全部队列和新归属；无法凑齐时 `failed_preflight` 且零队列、零新增归属。

## 实际结果

旧路径把未绑定新剧的确定性预检失败直接提升为批次级失败，没有先持久化排除该剧并重新读取 FIFO 候选，因此提前终止了 10:06 批次。

## 根因分析

- runner 的候选预检只处理当轮快照；未绑定候选失败后缺少“写入不可分配状态—重新取池—继续补位”的闭环。
- 失败处理没有在入口处明确区分“无绑定无历史，可安全排除”和“已绑定或有历史，必须 fail-closed”两种数据语义。
- 10:06 已过时间点不属于本修复范围；失败批次恢复需要独立的管理员授权与审计设计，不能作为本缺陷修复的内部捷径。

## 修复合同

- `/internal/posts/drama-pool/check` 仅接受未绑定、无队列/发布历史且身份精确匹配的短剧；成功后写 `validation_failed`，runner 重新读取池并继续 FIFO。
- 已绑定或有历史记录的失败不调用跳过逻辑；批次失败记录将短剧置为 `needs_review`，整批停止。
- runner 必须先完成全部候选预检；sidecar 再于 `BEGIN IMMEDIATE` 事务内重算映射、插入全部队列并写入新归属。任一校验或写入失败全部回滚。
- 不提供失败批次恢复接口；timer、catch-up、启动脚本、人工内部调用和数据库改状态均不得追赶 10:06。
- 修复只在后续自然发布时间点生效，仍须经过完整候选、预检、建计划、发布和日志流程。

## 数据安全与幂等

- `validation_failed` 剧不产生账号绑定或队列，后续候选查询自然排除。
- `needs_review` 剧保留原绑定和全部历史证据。
- 10:06 原失败批次保持不变，不新增队列、不改状态、不产生补发。
- 全局素材/剧集排重、未知结果门禁和发布账本规则保持不变。

## 验证范围

- 未绑定、无历史坏剧后有好剧：坏剧 `validation_failed`，好剧 FIFO 补位。
- 已绑定坏剧和有历史坏剧：均 `needs_review`，整批停止。
- 无法覆盖全部账号：`failed_preflight`、零队列、零新增归属。
- 下一自然发布时间点核对同一剧只有一个账号、队列与绑定一致、日志可追溯。

## 部署与 10:06 处置

普通部署不补跑 10:06，并只读确认原失败批次未被恢复、补建队列或补发。若业务决定补发，必须另立需求并至少具备管理员审批、不可变操作审计、停用配置门禁、全局排重和发布结果核对；未完成评审和实现前不得通过内部接口、脚本或数据库操作执行。
