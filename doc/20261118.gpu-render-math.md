# GPU render math optimization and controlled measurement

Scope: reduce repeated CUDA scaling/composition arithmetic while retaining
the current pixels, encoder settings, timestamps and audio. No production
activation is included in the initial measurement revision.

Baseline: `33ce9744034e0ecf82f06fd6d58403cab7ed3cc4`. All 14 files currently
under `features/random_gpu` on the Hong Kong production renderer match this
baseline. Its service points at older release `68407465...` with these later
patches installed, so that older commit alone is not the comparison baseline.

Candidate:

- Cache each pixel's Lanczos normalization using the original accumulation
  order. Keep the rounded weight multiplication separate from addition.
- Calculate common U/V coordinates and weights once while retaining the
  independent accumulation order for both channels.
- Calculate the recipe's sine/cosine on CUDA once with the same functions.
- Preserve full precision, geometry, output profiles and codec settings.

Verification:

1. Existing clock, frame ownership, encoder-budget and cancellation tests.
2. `verify_gpu_render_math.py`: compare raw fitted and composited pixels with
   the baseline across 18 geometry/chroma/bit-depth cases and multiple frames;
   require zero changed channels. Record paired, reversed-order CUDA timings.
3. `benchmark_gpu_render_math.py`: identical frozen samples, H.264 and HEVC,
   decoded video/audio frame hashes; require exact equality. Then four
   16-worker A/B/B/A batches with the same encoder settings. The completed
   run used 90-second outputs to reserve verification time in the window.
4. Report media-only batch throughput separately from projected daily
   production capacity. Do not apply kernel speedup to the full pipeline.

The user authorized a bounded exclusive window: let existing GPU preparation
finish, temporarily stop new GPU preparation claims for about 20 minutes,
leave CPU/COS and publishing active, and restore the original GPU capacity.
Never terminate or replay business jobs. Tests use an isolated GitHub checkout
and output directory. The benchmark watchdog cancels only its owned children
if any external media process appears. Preparation capacity must be restored
on completion or failure. Preserve before/after configuration and running-job
receipts outside Git.

Initial planning baseline is 222.85 output video hours/day, about 1,152 videos
at the observed average 11.61 minutes, based on 2,015 rendered completions over
41.98 hours. A two-T4 projection is 445.70 hours/day ideal or 356.56 with 20%
headroom. These are not promises about current demand or unmeasured hardware.

## Completed measurement: do not activate this candidate

Candidate code: `70b741a6c54d0da89f6bd8cfb10fa4cfa800dbdb`.
The 18 synthetic pixel tests (four frames each) had zero changed channels.
Paired kernel speedups ranged from 5.5% to 19.9%.

All four full-pipeline batches completed, each containing 16 x 90-second
outputs (1,440 seconds of produced video):

| Variant and order | Batch wall seconds | Produced seconds / wall second |
| --- | ---: | ---: |
| Baseline A | 148.7931 | 9.67787 |
| Candidate B | 150.5105 | 9.56744 |
| Candidate B | 147.3938 | 9.76975 |
| Baseline A | 150.7376 | 9.55302 |

Aggregate throughput was 9.61504 for baseline and 9.66754 for candidate:
only +0.546%, below the observed batch variation. No stable production
capacity gain is established. Median encoder utilization was 100% in every
batch; median GPU compute activity was 88/87% for baseline and 85/85% for
candidate. Reduced render arithmetic did not materially increase throughput.
Keep planning capacity at 222.85 output hours/day, about 1,152 videos/day.

Quality acceptance also failed: all three H.264 pairs were byte-identical and
their decoded video/audio hashes matched. HEVC file hashes differed; the first
HEVC pair also had different decoded video hashes (audio matched), so further
HEVC decoding comparisons stopped. The first decoded frame was identical,
which does not excuse the whole-video mismatch as a header-only difference.
Cause and perceptual quality impact remain unresolved. This is not evidence
that the candidate is safe to activate for all formats.

The production admission pause allowed all 16 existing jobs to complete with
their original generation and no errors. CPU/COS and publishers stayed active.
The benchmark yielded to a COS local VP9 preprocessing process and resumed
from completed checkpoints; aborted attempts were excluded from timing data.
The independent controller restored GPU preparation capacity to 16 after
20 minutes (about two seconds of polling/API latency), and 16 new production
prepares were observed running. All 14 production renderer files still match
the baseline; the production worker PID and start time were unchanged.

No candidate code was activated, no production service was restarted, and no
code rollback is required. Keep the candidate isolated. Do not credit its
kernel speedup as production capacity or deploy it without resolving the
HEVC discrepancy and establishing a meaningful full-pipeline benefit.
