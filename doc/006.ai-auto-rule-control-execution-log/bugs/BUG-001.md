# BUG-001 ai-auto-rule-control-execution-log

## 发现阶段

代码评审 / 上线前集成测试。

## 现象

旧实现把每批200显示成总目标；单账户连续请求触发Meta应用限流后停止整批；同时尝试写只读业务库，日志出现“同步业务库失败”。初版改造复核又发现续跑次数跨事件累加、DATETIME无法JSON序列化、migration覆盖runner状态等问题。

## 复现步骤

1. 构造多个账户合计超过200个命中目标。
2. 让首个Meta写请求返回code4/subcode5044001。
3. 观察原逻辑：前200按排序集中选取、事件失败，后续目标与真实失败混在一起。
4. 使用PyMySQL读取DATETIME并直接交给现有json_response，触发not JSON serializable。
5. runner完成后再次执行旧migration，观察状态被upsert回旧值。

## 期望结果

按账户公平选批；应用限流后停止未发请求并续跑；Meta结果、日志存储与本地状态分别展示；回填幂等且API可序列化。

## 实际结果

原逻辑存在效率、可观测性和持久化语义问题。

## 根因分析

- `pause_items[:200]` 只做全局截断，没有每账户配额。
- Graph异常只终止单条/单账户，没有共享应用级熔断。
- 业务库状态同步与Meta成功共用一条结果语义，且服务账号无写权限。
- SQLite日志没有面向审计的流程字段；MySQL适配层未处理datetime和0值。
- migration无“仅插缺失”保护。

## 修复说明

新增独立日志服务和MySQL表；round-robin/20每账户/4并发；code4全局熔断；deferred和retryable分开；owner fail closed；runner fresh preview续跑；轻量日志列表和懒加载详情；安全回填。

## 影响文件

`features/ad_control_execution_log/`、`deploy/apply_ad_control_execution_log_fix.py`、`scripts/ad_control_rule_runner.py`、`scripts/migrate_ad_control_action_logs.py`、`static/ad-control-*`、`tests/`。

## 验证命令与结果

`py_compile`、`node --check`、21项unittest、生产同源app首次patch/二次幂等/compile均通过。

## 回归结论

本地主路径通过；线上建表、回填、API与服务状态在部署阶段补充到test-report。
