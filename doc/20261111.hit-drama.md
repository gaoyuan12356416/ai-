# FB exact-drama publishing

The automatic template list adds **爆款剧发布** beside the existing material
action. Content IDs and drama-resource row IDs resolve within the template's
target product. The ordinary planner then restricts its indexed source query
to that content ID, retains language, material product, launch-window, metrics,
media, cooldown, capacity and reservation rules, and freezes one task per usable
Page. A final transactional filter prevents an adapter from selecting other
dramas. Templates, daily schedules and existing receipts are not changed.

The request and resolved content ID are saved in the run and task snapshots.
Replaying an operation returns its original receipt, including after template
changes. A conflicting use of the same key is rejected. No database migration
or external API change is needed. The shared dialog keeps uncertain submissions
in browser session storage until a receipt is obtained.

Verification: `python -m unittest scripts.test_fb_hit_drama
scripts.test_fb_auto_validation -q`; Chromium dialog checks use mocked writes.

Deploy the pushed source using `python3 scripts/deploy_hit_drama.py prepare
--platform fb --folder /mnt/data-disk/hit-drama-20261111/fb-deployment`, then
`apply` with the same arguments. It copies the current live release, checks
affected baselines, runs candidate tests and backs up the ledger. The established
FB drain helper switches only the FB owner, restores original admission/timers,
and verifies the scheduler baseline. Main API, coordinator and nodes stay running.
Static transformations preserve concurrent template-list layout changes.

Rollback: run the same source script with `rollback --platform fb --folder`
and the deployment folder. Restore code/static pointers only; keep current
business databases, queues, configuration, tokens and platform receipts.
