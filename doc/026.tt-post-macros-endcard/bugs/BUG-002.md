# BUG-002 正式 Direct Post 资格与固定片尾能力分裂

## 基本信息

- 严重级别：P0
- 发现日期：2026-08-03
- 发现阶段：GPU 媒体 profile 与正式发布路径评审
- 当前状态：`direct_outro` 代码修复与自动回归通过，生产 prepare-only 待完成
- 外部影响：本轮未创建真实 TikTok Post

## 现象

基线只有两种媒体语义：

- `direct_clean`：`direct_post_eligible=true`，只规范化源视频，明确跳过片尾、Logo 和 filter-complex。
- `branded_preview`：使用已审核的 Logo/tutorial-outro 和 phone-match transition，但 `direct_post_eligible=false`，正式 publish 会拒绝。

因此无法同时满足“正式 Direct Post eligible”和“保留固定已审核片尾”。直接修改 `direct_clean` 会破坏其已冻结的无片尾合同；直接把 `branded_preview` 标记为 eligible 又会混淆预览/正式 profile 与审核身份。

## 复现步骤

仅使用单元测试/FakeTikTokAPI：

1. 用 `direct_clean` config 调 prepare，捕获 ffmpeg commands 和 health。
2. 观察只有一条源规范化命令，transition=`none`，没有固定片尾/Logo。
3. 用 `branded_preview` config 调 prepare，观察 Logo/tutorial-outro 与 `phone-match-0.9s`。
4. 检查 health/publish validation，发现该 profile 不具备正式 Direct Post eligibility。

不得调用真实 `/internal/tt-post/publish` 或 TikTok API。

## 期望结果

- 新增独立 `direct_outro`。
- 它复用既有已审核 Logo/tutorial-outro compositor 和 transition，但使用独立 profile/manifest 版本，并报告 `direct_post_eligible=true`、`brand_overlay_review_required=false`。
- `direct_clean` 的无片尾命令、profile、transition 和 eligibility 完全不变。
- `branded_preview` 的预览合同和不可正式直发状态不变。
- 固定片尾/Logo/source/trim/transition 参与复用身份；资产变化不能复用旧输出。
- 本轮只 prepare-only，不创建真实 Post。

## 实际结果

基线没有能同时满足上述要求的 mode。正式带片尾发布在修复前应 fail closed。

## 根因分析

基线把两个不同维度耦合在 `direct_post_eligible()` 一个判断中：

1. 是否可进入正式 Direct Post；
2. 是否走 Logo/tutorial-outro 合成 pipeline。

因此只要把某模式标为 direct eligible，prepare 分支就会按 clean path 跳过片尾。缺少独立的 `uses_outro_pipeline()` 和独立 profile，也无法区分 manifest 的内容身份。

## 修复说明

- 新增 `DIRECT_OUTRO_MEDIA_MODE = "direct_outro"`。
- 新增 `tt-post-direct-outro-hevc-720x1280-v1` 和 `tt-post-direct-outro-h264-720x1280-v1`。
- `direct_post_eligible()` 允许 `direct_clean`、`direct_outro`；新增 `uses_outro_pipeline()` 只控制 `branded_preview`、`direct_outro` 的合成路径。
- `direct_outro` 复用现有 Logo/tutorial-outro 和 `phone-match-0.9s`，不改变两个旧模式。
- manifest v4/reuse contract 冻结 mode、profile、outro SHA/size、logo SHA/size、source identity、trim 和 transition。
- `_prepare_response` 与 publish 前再次验证当前资产身份；篡改或漂移 fail closed。
- CPU expected profile 与 GPU profile 必须完全一致；prepared URL 不能等于 source URL。
