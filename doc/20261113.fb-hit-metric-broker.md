# FB 爆款剧指标读取拥堵修复

2026-11-13，模板 1「DramaWave 排重实验」提交资源 30369 时收到“指标查询繁忙”。
旧 broker 的两个名额各执行一次完整聚合，其他请求等待两秒就返回 503；同一天
23,167 条素材指标一次读取实测 7.129 秒。查询最多重试三次，每次 60 秒，超过
HTTP 客户端 65 秒等待时间，离开的客户端也可能继续占用查询名额。

改动仅限独立只读指标服务：

- 相同产品、平台、日期窗口的并发请求共用一个结果或错误。
- 聚合结果按 READY generation IDs 缓存，每次复用前重新查询当前指针；指针变化
  重新聚合，缺日或查询失败仍报真实错误，不回退旧数据、不把未知当零。
- 冷读仍在同一个一致性快照中读取指针和聚合，缓存使用该快照实际版本。
- 最多两个实际读取、八份/64 MiB 缓存；超大结果正常返回但不缓存。
- 排队和数据库重试共享 55 秒预算，早于 HTTP 客户端超时；发送响应不占 SQL 名额。
- 保留生产 FIFO、只读副本验证、精确金额、选材阈值、冷却和原操作回执防重。

验证：`python -m unittest tests.test_fb_metric_broker tests.test_fb_metric_mysql tests.test_fb_hit_receipt tests.test_fb_hit_profile`
共 33 项通过。生产验收对真实指标进行一次六请求并发及一次热缓存读取，核对完全相同
的 generation IDs、素材数量和金额摘要。只读预览资源 30369 的匹配和选材，不创建测试发布。

`fb-auto-metric-broker.service` 的 WorkingDirectory；保留原共享指标刷新目录及所有发布
服务、账本、队列和回执。确认原 broker 没有活动查询再切换。
