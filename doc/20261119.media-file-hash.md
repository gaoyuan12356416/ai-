# Media SHA-256 throughput on the dual-T4 preparer

The production CUDA SHA-256 implementation processes a file sequentially on a
single CUDA thread. A live output-file read advanced at 3.3 MiB/s; host SHA-256
read and hashed a 64 MiB portion at 328 MiB/s. This does not imply a 100x render
speedup: it identifies avoidable time in media verification and GPU contention.

`file_digest()` now defaults to host `hashlib.sha256` independently of
`RANDOM_GPU_COMPUTE`. All media bytes are still hashed, including downloads and
completed outputs; no digest cache, identity bypass, or skipped validation is
introduced. Standard SHA-256 values, frozen recipes, source checks, frame/audio
processing, NVENC options, upload checks and publication receipts are unchanged.
This explicitly supersedes the previous GPU-default media hash policy.

`RANDOM_GPU_FILE_HASH_BACKEND=cuda` selects the existing CUDA implementation
when GPU computation is enabled; its failures still propagate without fallback.
The existing direct CUDA `sha256_file()` validation API remains unchanged.
CPU rendering nodes continue to hash on the CPU. Invalid backend values fail
locally rather than changing the requested implementation silently.

## Validation and activation

Run `python -m unittest tests.test_media_file_hash_backend
scripts.test_immutable_asset_digest scripts.test_native_pipeline_control`.
Validate CPU hashes against recorded production GPU hashes before activation.
The changed runtime file is only `features/random_gpu/gpu_compute.py`, based on
the already deployed catalog-admission version from `33ce9744`.

Fetch the exact GitHub commit into an isolated staging checkout. Use
`scripts/deploy_fb_source_cache.py media-hash --source STAGE --runtime RUNTIME
--backup BACKUP --expected-before HASH` for an atomic, preimage-checked install.
The rollout started at concurrency 20. At 2026-11-19 02:17:49 UTC the operator
changed the target to 32 and explicitly confirmed keeping 32. Preserve that
target, GPU affinity and publisher processes. Label completed samples as
20-only, crossing the change, or 32-only; do not combine those cohorts into a
controlled concurrency comparison.
Use that script's `recycle` action only with fresh coordinator-registered
preparation worker PIDs, first one per GPU, then small groups. Its SIGTERM is a
finish-current-claim request. Observe replacement registration before the next
group; never signal the node parent, publishers, renderer children or schedulers.

Compare completed new-process jobs against the pre-change 20-worker baseline,
separating profile, output duration and render/non-render phases. Do not treat
idle demand periods or a partial hour as a saturated daily capacity benchmark.

Rollback: `python scripts/deploy_fb_source_cache.py rollback --backup BACKUP`,
then naturally recycle only the new preparation processes in small groups.
Do not restore task/receipt databases or replay completed/unknown jobs.
