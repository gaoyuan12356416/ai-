# BUG-002：长时间选材后恢复的账号使语言容量证明失配

- 级别：P1；2026-11-03 已修复并完成本地回归，等待增量部署。
- 影响：素材定时批次已有合法部分候选，但创建计划时整批被 FIFO 容量守卫拒绝。

## 现象和证据

某素材批次在 16:51 开始，18:32:40 以 `x_post_pool_fifo_conflict / 素材语言尚未达到冻结批次容量` 结束，queue=0，`plan_attempted_at` 已写。该状态不能直接重发或清除尝试证据。

守卫仅检查标为 `language_capacity_full` 的跳过语言，不要求每种语言都填满。原规则允许非空健康子集提交。运行时先用健康账号子集扫描，但提交前只重新核对已选候选账号。此前省略的账号在其他任务完成后恢复可用，Sidecar 此时按原冻结全集中当前健康账号重新计算更大的语言容量，旧子集的容量证明即不再成立。

本轮池证据含 366 条当前语言容量证明、599 条需 Premium 的候选拒绝和 7 条未配置语言拒绝；最后复核 28 个候选账号。容量证明语言中，末轮候选数量为 en=7/de=2/ko=4/es=9/zh-tw=5，而随后只读无 hold 账号容量为 en=9/de=5/ko=7/es=11/zh-tw=5。两组观测不是同一原子时刻，不能当作已保存候选计划；它们与可复现的集合恢复 race 一致。素材供给和同语言 Premium 限制仍客观存在，修复不保证全账号都能获得候选。

## 修复

`scripts/x_post_schedule_runner.py` 在素材计划写入栅栏之前重新校验原冻结账号全集。健康集合有增加或减少时，使用同一服务器持有的素材快照重建候选和 FIFO 证明。总计最多三轮选材；若集合继续变化，以明确的账号状态变化错误终止，并且不设置 `plan_attempted_at`、不创建计划、不发布。

没有调整服务端 FIFO、容量或事务守卫。缺料语言仍按原有健康子集规则执行，原冻结账号顺序、日期和配置不改。drama 流程保留原行为。未给来源/媒体判定增加跨轮缓存，避免把账号/relay/来源变化前的结论当作新证明。

## 验证

`python -m unittest scripts.test_x_post_schedule_runner`：75 项通过。

覆盖账号集合增加、减少、稳定部分候选、持续变化有界失败、失败前无 plan/create/publish、真实 SQLite 素材快照上界在两轮间不变且新增素材不进入旧快照。`py_compile` 和 `git diff --check` 通过。

## 恢复边界

已存在 `plan_attempted_at` 的失败批次需要另行精确审计“已知写前拒绝且零队列/日志”，保留原尝试证据。现有 `operator_same_day_codefix_compensation_v1` 针对 drama 的特定媒体修复错误及旧审计链，不适用于此次 material FIFO 冲突。

已补充恢复脚本的仅 1039 精确例外，部署 runner 修复之后方可生成/应用计划。完整原始尝试行保留在审计；代码版本及部署文件内容重新核对通过后，事务内只重置此已知写前拒绝的计划尝试栅栏。SQL trace 与 Post/短链替身测试确认精确错误在写事务前抛出；中断、幂等、未知、已有队列、代码漂移测试均通过。本地组合 91 项通过，未执行线上状态恢复。
