# BUG-003：短剧选材未过滤已取消历史队列的集数占用

- 级别：P1；本地修复与回归完成，未部署或重试历史批次。
- 现象：恢复的两个短剧原时段以 `x_post_drama_episode_already_used` 失败，零 queue/log，计划尝试栅栏已写入。

## 原因

`_drama_assignment_candidates` 仅排除了待处理 duration route 的剧集。其他已存在的队列，包括取消且没有发布日志的历史队列，仍被投影为下一集候选。创建计划在同一事务内按 `episode_key` 检查所有历史队列并拒绝重复，导致一条已占用集数使整个候选批次失败。

2026-11-03 只读诊断中，当前 20 个候选有 6 个集数对应旧 cancelled 队列，均没有 Post/日志。这不意味着它们可重新使用：自动发布的持久占用规则包括取消队列，必须保留。另有 14 个未占用候选应继续正常预检，而不被这些旧占用拖住。

## 修复

`features/x_posts/service.py` 的候选选择按原样的 `episode_key` 排除所有既有队列。已绑定剧目仍占用原账号，不替换剧目、不跳下一集、不移动游标或重播代次。未绑定剧目在 SQL LIMIT 前排除历史相同 key。创建计划的原子重复/未知/归属守卫保持原状。

## 验证

- 既有 store 155 项回归通过。
- 新增测试覆盖 queued/cancelled/failed/published 占用、历史未绑定队列、原绑定及游标不变、剩余健康子集在原完整账号范围下建队。
- 加上新增用例后的完整 store 157 项通过；健康子集建队专项再次通过。
- 补充事务回滚证明和精确恢复后，store 158 项 + 恢复专项 7 项合计 165 项通过。
- `python -m py_compile features/x_posts/service.py`、`git diff --check` 通过。

## 恢复边界

已写 `plan_attempted_at` 的失败批次未自动重置；独立 helper `scripts/recover_x_drama_episode_selection.py` 只接受 1029/1031 的精确失败时间与错误、零队列/日志、完整原身份和首轮审计，并要求已部署 service.py 与包含修复的 Git 提交及内容哈希一致。以新追加审计保留完整旧 attempt，再允许正常预检；旧取消队列和原集数占用保留。操作见 [第二次精确恢复](../drama-episode-recovery.md)。

同次发现的手动任务预检失败原因为只读来源 MySQL 连接错误，不是本问题。其原素材无队列、预约已释放，但当前目标账号另有未知结果队列，必须先核对该回执，不能以来源连接恢复为理由绕过账号隔离。
