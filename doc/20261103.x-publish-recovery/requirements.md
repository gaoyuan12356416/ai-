# 20261103.x-publish-recovery 需求与技术设计

## 背景

2026-11-03 排查发现：X 正常队列仍在推进，但部分自动任务未同步原生成功回执，昨日部分未启动手动任务被切换时间保护规则排除，媒体上传存在长请求失败风险。用户要求恢复昨日积压及今日未完成任务，并明确禁止重复发布和结果不明时直接重发。

## 目标

以可核对的原生发布回执修正展示状态；仅恢复已审计且从未开始发布的旧任务；改善媒体上传传输，保持未知结果和正在执行任务的保护。

## 范围

### 包含

- 自动任务与原生队列、日志、Post ID 的精确核对及本地状态修复。
- 对明确指定的昨日/今日旧手动任务建立有审计记录的切换时间例外。
- 媒体分块及请求超时调整、晚到回执观察、相关回归测试。

### 不包含

- 结果不明的任务重新发送、重新生成幂等键、清空发布尝试或冻结内容。
- 全局取消切换时间限制、修改其他平台或正在部署的独立改动。
- 中断仍在推进的素材扫描、批量重置运行中队列。

## 用户故事 / 业务规则

1. 已成功但显示失败时，先核对唯一原生队列及日志、账号/素材/模板/正文身份、Post ID 与 URL，再修正自动任务、素材账本、运行汇总及审计事件。原生数据库只读，发布尝试次数保持不变。
2. 未知或仍在执行的外部结果只能继续观察回执；不得通过重试创建新帖子。停用/复核状态不能阻止读取已有任务的晚到回执。
3. 旧手动任务恢复必须精确列出 ID 和日期，证明未开始、零队列、零结果、保留的预约归属无冲突。保留原始创建时间、内容、账号素材配对及幂等身份。
4. 恢复脚本先生成只读计划，再备份，在事务内重新校验快照并写入审计授权；同一计划重复执行无副作用。
5. 媒体请求可使用 120 秒超时，创建帖子/转发请求保持 30 秒；媒体请求期间租约心跳独立续租，失去租约后不得开始新操作。

## 交互与流程

只读线上核对 → 精确计划与风险分类 → 本地开发和回归 → GitHub 版本部署 → 私有计划/备份/CAS 执行 → 观察正常调度领取及最终回执。结果不明项留待回执，不直接重发。线上执行证据由部署与测试报告记录。

## 技术设计

### 影响模块

- `features/x_auto_posts/receipt_reconciliation.py`、`publisher.py`：回执修复与晚到回执观察。
- `features/pipeline_dispatch/x_manual_recovery.py`、`scripts/recover_x_unstarted_manual.py`、`features/x_posts/service.py`：旧任务精确授权与正常领取。
- `features/pipeline_dispatch/executors.py`：X 媒体传输参数。

### 数据结构

新增私有手动恢复审计表，记录任务身份摘要、计划摘要、操作者、原因、备份摘要和校验证据。恢复计划保留原始行快照供事务内比较；敏感线上快照、数据库备份和真实账号信息不入 Git。

### API / 接口

无新增公共 API 或界面流程。运维入口为显式 plan/apply 脚本；发布继续使用原有调度器及原始任务身份。

### 异常与边界

身份不匹配、非唯一回执、未知结果、已有发布队列、运行中任务、预约冲突、计划漂移均拒绝恢复。授权表缺失时，正常调度行为保持原状。素材扫描若心跳和查询均在推进，应保留当前快照并观察，避免干扰已执行工作。

## 验收标准

- 回执修复不调用发布接口、不改变原生记录或发布尝试，重复执行无副作用。
- 旧任务仅按精确审计授权跨越切换时间，其他旧任务、未来任务与安全限制仍有效。
- 计划生成后发生的状态变化被事务内复核识别；写入前具备可验证备份。
- 运行汇总、结束时间和子任务终态一致；尚有执行中子任务时不提前标记完成。
- 媒体传输与心跳回归通过，创建帖子超时仍保留未知结果且不自动重发。

## 风险与待确认

线上有独立工作正在执行，部署必须核对实际运行路径和版本。当前慢素材扫描不等于死锁，不据此重置。最终恢复数量、剩余未知任务与线上发布结果必须以部署后回执核验为准。
