# YouTube media isolation and original-video recovery

The final user rule is task-only isolation. Neither a channel nor a source
material can be held by one task to block another task. The due-order scan still
selects eligible work in schedule order, without a second channel FIFO fence.

Each publication owns `youtube:task:<native-id>`. Existing channel/material/source
fences migrate to this task resource without changing generations, claim tokens,
native leases, upload sessions, video IDs or operation receipts. Running old
channel descriptors remain valid only as an identity alias to their own task;
they do not retain an exclusive channel lock. Unknown outcomes keep their own
task fence and cannot silently retry a write. Other tasks, including the same
material on the same channel, remain eligible.

The reviewed enqueue check previously matched source material plus channel. It
now matches preparation ID plus channel, so an unrelated preparation is not
blocked by a historical upload. Operation-ID idempotency, same-preparation
protection, owner/credential checks, approved cover checks and platform limits
are retained. No new business approval or global stop switch is introduced.

After a visibility write, workers perform bounded reads without repeating the
write. Unconfirmed reads retain a safe diagnostic. The bridge reconciles the
typed visibility/schedule failure against the original owner-authenticated video;
it preserves actual platform publication timestamps and CAS-checks the native
row after network reads. Confirmed appointments re-enter the existing read-only
schedule continuation. Confirmed public videos with zero comment attempts enter
a comment-only continuation; ambiguous attempted comments are never retried.
This also handles a UI retry that cleared the native error but left dispatch
unknown. Unrelated historical unknown-write classes are not resumed.

Deployment preserves the current priority policy and CPU X segment setting.
`scripts/deploy_youtube_isolation.py` overlays only affected coordinator files,
starts a separate bridge, and buffers new coordinator TCP connections while
existing control requests drain. Native ledgers and running claims are retained.
Only publication child processes receive SIGTERM, which their existing worker
loop interprets as finish-current-task-and-exit. Supervisors respawn them with the
updated code; preparation processes stay alive. Hong Kong gets only the YouTube
method change, retaining its separate X transport setting.

One-time recovery uses `scripts/recover_youtube_overdue.py`: never-started overdue
tasks can run immediately with their initial schedule retained; an interrupted
task can resume only its freshly probed original zero-byte session, under the
same task mutex and renewed native/central ownership. It cannot create a
replacement session. Backups include current native and dispatch SQLite files.

Rollback: run the deployed `scripts/deploy_youtube_isolation.py --rollback
<backup>/manifest.json` with the same release. Hong Kong rollback additionally
accepts current publication worker PIDs. It rejects later file drift, restores
code and bridge routing, drains publication workers, and never restores an old
database over newer videos, comments, schedules, receipts or claims.

Validation: existing YouTube pipeline, adapter, executor and FB isolation suites,
plus `scripts.test_youtube_isolation_readback` for unrelated-media progress,
same-source aliases, active-owner preservation, real SQLite public readback,
comment-only continuation, uncertain-comment protection, row-race CAS, and a
delayed visibility read with exactly one platform write.

Final rollout uses `scripts/deploy_youtube_task_isolation.py`: a new bridge on
18850, a scoped coordinator overlay, and one native enqueue-query change. The
metadata planner receives its existing graceful stop signal and finishes any
current enqueue before systemd restarts it. API and media executors are not
restarted. A legacy executing descriptor is explicitly covered by a regression.
Rollback uses this script with `--rollback <backup>/manifest.json`; it requires
only affected YouTube claims to finish naturally, restores code/routing and never
restores old ledgers. The first visibility-read fix remains on CPU/HK nodes.

`scripts/finalize_youtube_recovery.py --sync` reads each original owner video and
comment receipt before syncing only tasks 1155–1160 through the existing writer.
It verifies one matching owner comment and one upload attempt per task, and keeps
the original IDs for the three already public videos. No platform write is used
for this final verification/sync step.
