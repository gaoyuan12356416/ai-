# BUG-003 素材池发布设置 PUT 返回 not_found

## 现象

2026-08-11 16:47:53、16:47:57、16:48:02，管理员在生产素材池页面保存
发布设置，Nginx 对
`PUT /api/admin/x-posts/material-pool/schedule` 连续返回 HTTP 404，
页面显示 `保存失败：not_found`。

## 根因

素材池和短剧池页面都使用 PUT 保存 schedule，但上一轮新增
`DramaMaterialHandler.do_PUT()` 时只把短剧高优路径加入了白名单。
因此两个合法 schedule PUT 都在主 API 分发器直接返回 404，请求没有进入
Cookie 鉴权、同源校验、Sidecar 或 SQLite 保存逻辑。

## 状态核对

- 失败请求前后素材 schedule 均为版本 `16`，更新时间仍为
  `2026-08-10T07:09:26Z`，模板仍以 `{{url}}` 开头。
- 三次 404 均没有 Sidecar 保存调用、审计记录或部分写入。
- 已冻结的 2026-08-11 随机计划保持版本 `16`，没有被错误请求改写。

## 修复

- `do_PUT()` 精确放行两个 schedule 路径：
  - `/api/admin/x-posts/material-pool/schedule`
  - `/api/admin/x-posts/drama-pool/schedule`
- 继续放行既有短剧高优 PUT；其他未知 PUT 仍返回 404。
- 合同测试提取完整 PUT 分发器，断言三个合法路由、一次受控委托和最终
  fail-closed 404，禁止退化成所有 PUT 都委托 `do_POST()`。

## 独立自然批次

生产自然 scheduler 在 17:05:15 为当天 09:59 的旧版本 16 冻结批次
`schedule_run_id=99` 建立队列，早于本次 17:05:51 的配置保存 36 秒。
该批次最终产生队列 `158..162`，五行均为一次 attempt、五个不同 Post ID、
`unknown_outcome=0`。它使用旧版本 16 模板，不是部署 canary，也不是版本 17
保存动作触发的发布。最终全局 queue/log/published 为 `162/162/161`，
unknown/active 均为 `0`，SQLite 完整性为 `ok`。

## 回滚

仅从上述备份恢复 `app.py.before` 到
`/root/drama_material_service/app.py`（`0644 root:root`），然后只重启
`drama-material-api.service`。不得切换当前 Sidecar release、恢复 SQLite/Token、
删除版本 17 配置或停止/重放发布 timer。
