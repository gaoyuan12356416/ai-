# BUG-001 手动超长素材被误报为不存在

## 现象

生产手动批次 `#3` 选择素材 `5286820` 和账号 `13` 后，在任何队列或 X 写入前以 `material_not_found_or_ineligible` 失败。

## 根因

素材源只读查询确认该记录存在、属于 Dramawave、类型为视频且未删除，但源时长为 `763` 秒。手动 selector 复用了自动素材池的 `video_duration<=600` SQL 条件，导致该行在进入账号感知媒体预检之前被过滤，并被折叠成误导性的“不存在或不可用”。

服务层同时把 Ads promoted-video 的 600 秒边界错误地当作 token 确认 Premium 账号的有机 Post 上限，无法验证真实的 Premium 长视频 API 能力。

## 生产边界实测

- 账号：`13` / `@_shaniyalanae`，当前 token 回读 `subscription_type=premium`。
- 素材：`5286820`，实际原片 `763.938005` 秒、`162253615` 字节、720×1280、30fps、H.264/AAC。
- 唯一尝试：queue/log `151`，`media_category=amplify_video`。
- X Media ID：`2087080775950733312`。
- X Post ID：`2087081262754169202`。
- X 回读：`duration_ms=763938`，证明发布的是原片而非 599 秒裁剪版。
- 终态：`published`，`unknown_outcome=0`，Post URL：<https://x.com/_shaniyalanae/status/2087081262754169202>。

## 修复

- 自动素材池继续只选择 `1..600` 秒来源。
- 仅人工明确选择的手动批次允许正时长的超长来源进入完整合规、映射和媒体预检。
- 只有当前 token 确认为 Premium 的账号可接收超过 140 秒的原片。
- Premium 时长门禁按 X 当前产品合同设为 4 小时；v2 `amplify_video` API 继续执行更严格的 512 MiB、本项目既有 H.264/AAC、尺寸、帧率和逐行扫描门禁。
- 符合媒体合同的原片不得仅因超过 600 秒而触发 GPU 裁剪；其他编解码或尺寸问题仍沿用既有受控修复链。
- 无 Premium、超过 4 小时、超过 512 MiB 或其他合规/映射失败时，整批仍在建队列和 X 写入前失败关闭。

## 安全边界

生产批次 `#3` 保持原终态且未被重放。用户明确授权后，另建全局去重 canary queue `151`，仅调用一次并成功发布；素材 `5286820` 已由全局账本占用，不允许自动重试或再次发布。

发布前备份位于 `/mnt/data-disk/x-post-automation/backups/20260811T073629Z-raw-763s-canary`；备份包含在线 SQLite 快照、15 个令牌文件、运行环境配置和原 release 链接。
