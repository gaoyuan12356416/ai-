# BUG-003 部署补丁回退观察日志模式

## 状态

已修复，P0（发布阻断）。

## 现象

主工作树最初的列表回归可通过，但把真实部署补丁应用到临时 `app.py` 后重跑同一套测试时，`test_observe_log_is_not_labeled_as_dry_run` 失败：观察日志的 `audit.mode` 从预期 `observe` 变成 `real`。继续审计还发现“展开目标明细”使用的 `ad_control_action_audit` 同样只区分 dry-run/real，即使列表修复，明细仍会误标成正式执行。

## 根因

`deploy/apply_ad_control_execution_log_fix.py` 的 `LIST_ACTIONS_FUNCTION` 仍使用旧审计模板，只根据 `dry_run` 生成 `dry-run/real`，没有读取 `criteria.run_mode=observe`。同时主应用及 current-live 的 `ad_control_action_audit` 也缺少 observe 分支，部署补丁原先没有修补该函数。两条查询路径因此可能分别回退或误标“只观察/观察完成”语义。

## 修复

- 列表模板与主应用明细审计同时对齐：先计算 `observe_mode`，观察执行状态使用 `observed/观察完成`，审计模式使用 `observe/只观察`；copy/mixed 动作标签在明细中保持完整。
- 扩展既有部署模板静态回归，锁定上述四个字段/分支。
- `validate_ad_control_deploy_patch.py` 区分两类合法首次应用：当前 merged app 已对齐时必须 `unchanged`、零备份且字节不变；需要变更的输入必须生成唯一字节一致备份。第二次应用均必须 `unchanged` 且不新增备份。
- current-live 专用验证器继续证明真实线上基线的 changed+写前备份路径，并分别抽取 `list_ad_control_actions` 与 `ad_control_action_audit` 检查观察契约，避免因 merged app no-op 或只检查列表而产生假阳性。
