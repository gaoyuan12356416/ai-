# BUG-008：瞬时 schema 读取失败被误报为真实缺列

## 级别

P1。失败关闭有效，但可能让一个到期调控 tick 被跳过，并产生误导性告警。

## 发现方式

2026-07-15 19:40，BUG-007 热修后的连续自然 tick 中，runner 返回 `insight start table missing required fields`。该事件没有 preview_id/action_id，requested/success/error 均为0，SQLite action保持17，对象状态未变化，未调用Meta写接口。

日志显示真实失败发生在：

```text
SHOW COLUMNS FROM `kunlunads_dev`.`ads_facebook_hours_insights`
subprocess.CalledProcessError: mysql client exit 1
```

同一表在19:25、19:30、19:35和19:45 tick均读取成功；19:41人工只读复查返回54列，`campaign_id`、`dt`、`ad_account_id`全部存在。因此这不是schema漂移。

## 根因

`mysql_table_columns()` 是供多个后台模块使用的best-effort helper。它捕获任意查询异常后返回空集合；`ad_control_validate_insight_start_schema()` 无法区分“SHOW COLUMNS读取失败”和“读取成功但确实缺字段”，把前者错误转换为 `invalid_insight_start_schema`。

runner还在创建preview前无条件预读schema。即使所有账号都未到执行时间、不会查询campaign start，也会多做一次远端MySQL调用。

## 修复

- 仅在 `ad_control_validate_insight_start_schema()` 中使用既有 `ad_control_run_critical_mysql()`；不改变全局 `mysql_table_columns()` 的兼容语义。
- 单次 `CalledProcessError` 按现有策略最多重试4次。
- 全部读取失败时返回独立 `insight_start_schema_unavailable`，只记录表名和异常类型；读取成功后真实缺少 `campaign_id/dt` 才返回 `invalid_insight_start_schema`。
- runner改为每tick线程安全的lazy singleflight：只有实际campaign-start查询才触发schema读取；同一tick的所有账号共享一次成功或失败，结束后在 `finally` 恢复原函数。
- 空白名单、无账号到期、无active交集或Redis已命中时不再探测schema。

## 回归

- `CalledProcessError(exit=1)` 后第二次成功。
- 连续失败只执行配置的重试次数，错误码为unavailable且不带missing。
- 成功读取但缺 `dt` 仍严格失败关闭。
- `no_accounts_due` 对schema探测为0次。
- 并发8次schema请求只调用底层validator一次，成功/失败均在当前tick内缓存。
- runner的monkeypatch只存在于独立短进程并在 `finally` 恢复，不进入长驻API进程。
- 聚焦 large-pool 13/13、runner-state 14/14；ad-control fresh-cache 全量180/180、Python编译、JavaScript语法和 `git diff --check` 通过。

## 已知边界

底层 `run_mysql()` 当前没有 subprocess timeout；权限/语法等确定性错误也会按关键查询策略重试。此次热修保持窄范围，超时治理另行处理。
