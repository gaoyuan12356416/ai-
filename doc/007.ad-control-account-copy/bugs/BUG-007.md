# BUG-007：空 Campaign 白名单导致自然 runner 每五分钟误报阻断

## 级别

P0，阻断恢复生产 ad-control cron。

## 发现方式

2026-07-15 18:50，在完成 V2 生产部署并恢复原 crontab 后，首个自然 tick 对规则组 `frg_plus8_non_asian_lang_10am_dramawave_binding` 生成 `live_preview_blocked`。结果为 0 个请求、0 个成功、0 个 Meta 写、108 个 preview 错误。发现后在下一 tick 前再次暂停仅 ad-control cron；API 和任务 Worker 保持运行。

## 根因

规则组包含 245 个账号，其中 108 个当前没有 Dramawave created-data Campaign 白名单。旧线上实现把空白名单视为正常的“0 候选”；V2 的 `ad_control_collect_live_account` 在账号时区排期、Token 和 Graph 之前把空白名单改成 `no_product_campaign_whitelist` 错误。

因此这些没有可扫描 Campaign 的账号绕过了正常的账号时区排期，每个五分钟 runner tick 都会产生 preview 错误；当全部实际 Campaign 账号又不在执行时间时，preview 形成 `error_count=108, execution_count=0`，最终被 runner 记录为 `live_preview_blocked`。

## 修复

- 空白名单直接返回 `items=[]`、`errors=[]`、三个计数为 0。
- 返回发生在排期、Token 和 Graph 之前，保证没有可扫描 Campaign 的账号不会读取凭据或访问 Meta。
- `ambiguous_source_product`、Token、Graph、时区和规则评估错误仍保持原 fail-closed 语义。

## 回归

- 新增 `test_account_without_campaign_whitelist_is_a_benign_zero_candidate`，并用异常 spy 证明 Token/Graph 调用均为 0。
- focused 1/1 通过。
- ad-control fresh-cache 全量 172/172 通过。
- Python 编译与 `git diff --check` 通过。

## 生产边界

18:50 的失败 action 只写入既有执行审计，`requested_count=0`、`success_count=0`，没有 Campaign 状态变化，也没有 copy 或 copied created_data/lineage/intent 写入。热修必须按 GitHub-first、exact-source、独立 staging、增量备份、API 重启和自然 tick 复验流程发布；复验通过前 cron 保持暂停。
