# BUG-002 旧 Preview 与 Enable TOCTOU 可越过最新规则状态

## 发现阶段

2026-07-15，第二轮 SA 代码评审与执行安全回归阶段发现。问题位于尚未生产部署的本地工作树，不是线上事故。

## 现象

- 规则组完成试算后，如果规则、运行模式、账号、enabled 或急停状态发生变化，旧 preview 仍可能被提交执行。
- 正式 pause 含多个对象时，规则组在执行过程中被禁用、急停或修改，后续 Meta POST 可能继续沿用旧 preview。
- 启用流程先在 SQLite 锁外校验 Token，再写 enabled；两步之间若规则配置被并发修改，可能把未按新配置校验的规则组启用。

## 复现步骤

1. 保存一个 Campaign live pause 规则组并生成有效 preview。
2. 修改规则动作/条件或将规则组禁用、急停，使当前配置与 preview 不一致。
3. 使用旧 `preview_id`、`preview_hash` 调用正式 execute。
4. 对多对象 pause，在第一条执行后修改规则组状态，观察后续对象。
5. 对 enable，在 Token 校验返回前并发修改行为字段，再让启用流程继续写入。

## 期望结果

- 行为配置变化立即清空旧 preview 并自动禁用规则组。
- execute 必须把 preview 绑定到当前规则组 owner、当前 scope hash、最后 preview ID/hash、enabled 和急停状态。
- 每次 Meta POST 前都在跨进程 SQLite 写锁内重新读取并校验最新状态；不一致立即失败关闭。
- enable 在 Token 校验后进入最终写事务时，必须重读对象层级、运行模式、确认信息、行为字段和 preview hash；配置变化时保持禁用。

## 实际结果

修复前主要依赖请求中的 preview hash 与 preview 记录互相匹配，没有完整证明该 preview 仍对应当前保存的规则组。Token 校验与 enabled 更新之间、以及多对象 Meta POST 之间缺少最终状态重检窗口，形成 stale preview 和 TOCTOU 风险。

## 根因分析

- preview 的确认 hash 未在执行时与规则组当前行为字段重新计算并比较。
- 保存行为变化时没有统一清理最后 preview 并禁用规则组。
- enable 的外部 Token 校验无法放在长 SQLite 写事务内，但校验后缺少事务内 snapshot 对比。
- 正式 pause 只在批次入口校验，未在每个不可逆 Meta POST 前获取最新状态。

## 修复说明

- 行为字段变化时强制 `enabled=0`，清空 `last_preview_id/last_preview_hash`。
- 统一计算 `current_preview_hash`，新增 preview 与当前规则组的 owner、最后 preview、scope hash、enabled/急停校验。
- execute 在解析 preview 后先做顶层门禁；正式 live 执行前再次要求规则组 active。
- 每个 Campaign pause 在 `BEGIN IMMEDIATE` 保护下重新校验 freshness/active，再读取 Meta 状态并执行 POST；状态变化时回滚并停止该对象写入。
- enable 在 Token 校验完成后重新获取写锁、读取当前 snapshot 并比较 preview hash，解决校验与启用写入之间的 TOCTOU。
- 同轮补强 Ad execute 顶层 `phase_not_enabled`、observe pause 零 Token，以及 mixed 规则中 copy 提前隔离且不阻断 pause。

## 回归结论

已修复并通过 90/90 fresh-cache 本地回归。旧 preview 无法在规则变化后执行，正式 pause 在每次 Meta POST 前重新确认规则仍为最新且 active；enable 的最终事务会拒绝并发变化配置。真实 Meta copy、Ad 执行和生产部署均未开放，本结论不替代上线后的观察 smoke test。
