# BUG-001 旧聚合规则组编辑迁移与部分启用状态不一致

## 发现阶段

2026-07-15，账号维度规则组升级的代码评审与旧数据兼容回归阶段发现。该问题发生在本地实现工作树，尚未生产部署，不是线上事故。

## 现象

旧版按产品 fan-out 的多个底层规则组，在新版账号维度页面聚合为一个规则组后，若底层组只有一部分启用，页面可能把整组显示为“已禁用”。编辑保存时若没有显式迁移全部旧底层组，新组与旧组可能同时保留，形成重复扫描或状态不一致风险。

## 复现步骤

1. 准备两个 `frontend_rule_group_id` 相同的旧底层规则组，分别设置为 enabled 和 disabled。
2. 在新版“规则组管理”打开该聚合规则组。
3. 观察状态，并编辑后保存为账号维度规则组。
4. 检查页面状态、新规则组和两个旧底层规则组的 enabled/deleted 状态。

## 期望结果

- 页面明确显示 `partial_enabled`/“部分启用”，不能误报“已禁用”。
- 编辑请求显式携带除新 `group_id` 外的全部 `migrate_from_group_ids`。
- 后端校验迁移源属于当前用户、同一前端聚合组且行为配置一致。
- 新组保存与旧组禁用、软删除在同一 SQLite 事务完成；任一步失败时全部回滚，旧组保持原状态。

## 实际结果

修复前的实现只按单一布尔值聚合 enabled 状态，且编辑保存没有完整、原子的旧组收敛契约，存在部分启用误报和新旧规则并存风险。

## 根因分析

- 前端聚合模型没有保留 `enabled_count`、`target_ids` 和 `partial_enabled`。
- 保存 payload 没有明确区分新 `group_id` 与旧 fan-out 迁移源。
- 后端缺少对迁移源 owner、前端聚合 ID、行为配置一致性的事务内最终复核。

## 修复说明

- 前端聚合时保留所有底层 `target_ids` 和 enabled 数量，计算并展示 `partial_enabled`；部分启用组的操作改为“禁用全部”。
- 编辑保存时提交去重后的 `migrate_from_group_ids`，并排除新的 `group_id`。
- 后端校验迁移源所有权、`frontend_rule_group_id` 和行为签名；使用 `BEGIN IMMEDIATE` 在最终事务中再次校验并完成新组 upsert、旧组禁用和软删除。
- 任一校验或更新失败均回滚，配置分叉返回 `fanout_source_config_mismatch`，不会静默合并。
