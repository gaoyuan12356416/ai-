# X 三级收入画像与独立发布

此文记录历史三级规则。2026-11-10 起采用[受众与题材两级画像](20261110.x-audience-theme-profile.md)，剧类型不再参与新选材；已冻结历史任务保留当时的分类和审计。

## 本次范围

频道收入画像和新画像自动发布、画像素材池统一改为“剧类型 → 受众方向 → 题材”。AB 报表保持暂停。原发布流程的选材、计数、防重、任务和服务不修改。

分类版本：`x-hierarchy-20261109-v1`；分配策略：`revenue-hierarchy-weighted-v3`。

## 分类与统计

- 类型只读 `kunlunads_dev.ads_drama_info.resource_type`：1 本土、2 翻译。按 app_id=1479、content_id 和规范化语言定位实际版本，不使用剧名、语言或另一语言版本推断类型，也不用 resource_type_v2。
- 受众优先取明确的女性/女频、男性/男频、BL/GL/LGBTQ+、通用等标签。没有明确受众时，使用版本化语义标签规则提炼：甜宠、追妻、先婚后爱等归女性；战神、赘婿、强者归来等归男性；没有方向信号的悬疑、冒险、职业、成长等归通用。复仇、逆袭、总裁单独出现不推断男女方向。
- 同时命中男女强信号、明确受众标签互相冲突，或者证据不足，归“未标注”。明确受众标签优先于题材推导。保留 explicit、inferred、conflict、unlabeled 状态及原标签、命中依据、规则和分类版本；推导受众是内容分类，并非用户人口统计。
- 题材归并为豪门总裁、甜宠恋爱、婚恋纠葛、萌宝家庭、逆袭复仇、古装权谋、奇幻穿越、悬疑冒险、生活成长。同剧多个标签命中同一大类先去重，再平均分摊收入。没有识别到大类时进入未标注；部分未识别标签不单独增加分摊份额。
- 历史收入从既有归因账实按剧重建，不合并旧标签汇总。分币尾差逐层分配，类型、受众、题材、叶子剧目金额分别守恒。类型占频道，受众占对应类型，题材占对应类型及受众；组合另展示占频道比例。
- 历史统计按当前剧元数据和分类规则回算。实际发布选择记录冻结当时版本及分类，后续标签更改不会覆盖已保留任务的选择记录。

## 分配与兜底

先执行原流程的语言、模板筛选、时长、文件、账号资格及本流程防重等资格检查，再使用三级画像排序合格候选。每层按正收入权重产生可重放的随机顺序，类型排序始终高于受众和题材，同组合继续原有挑选顺序。

优先匹配类型+受众+题材；缺少题材时先选同类型同受众的其他题材；缺少受众时在同类型内改选其他受众并使用其题材偏好；整个类型没有合格素材时才切换类型。某层缺少有效画像时保留上层偏好，该层及其下层按原顺序。频道无历史或正收入时完全沿用原顺序。元数据查询失败局部降级并记录原因，不阻断其余合格候选。

未知类别不构成主动偏好；已知、可匹配且有正收入的类别权重重新归一。统计仍展示未知部分的真实收入。总收入非正或同层有负收入时，该层不生成概率。权重用于概率而非固定配额。

选择记录包括初选路径、实际路径、全部实际题材、画像版本、分类版本、原标签与受众依据，以及是否兜底、在哪一层兜底和原因。原先已经选定/保留的任务重入时使用原记录，不重新抽样或占用新素材。

## 验收证据

本地 300 项测试通过，包含 16 项新增层级用例、17 项原收入接口用例、30 项画像发布用例和继承流程回归。覆盖精确分摊、条件比例、5,000 次概率抽样、逐层兜底、缺层画像、负收入、未知分类、实际版本、ACL、候选元数据故障、普通/会员容量分配、隔离、防重和任务重入。

实际执行路径复核发现：执行器为绑定任务 claim_token 会重新创建普通 TwoStageSelector，丢失传入的 ProfileSelector，导致画像排序和审计均未进入真实自动任务。补充的执行阶段回归先在旧 runtime 中失败（应选 C2 却选 C1），再在独立 runtime 中改为保留传入选择器的实际类型；验证了偏好剧目、租约传递、审计冻结和重入不重选。修复后完整回归为 301 项。用 `scripts/deploy_x_tag_executor.py install` 仅切换独立 runtime 和画像自动 API，不重启原发布、画像发布父进程、画像网关或素材池。回滚用同脚本 `rollback --backup <executor-profile-backups 目录>`，保留全部任务账实。

浏览器使用受控数据和真实频道页面进行点击验收：70% 本土 → 80% 女性 → 50% 甜宠，组合为 28%；桌面与窄屏可展开贡献剧目及原标签依据；发布解释展示实际组合及跨类型兜底。未执行测试发帖。

另用既有历史样本与只读 drama_info 重算，原收入总额与三级树一致。上线阶段再以最新已验证仓库快照重算，并逐频道验证各层金额和比例守恒。

## 部署与回滚

先提交并推送 GitHub，再在 CPU 43.166.187.96 从对应提交建立只读源目录。使用 `scripts/deploy_x_hierarchy.py stage` 构建独立 runtime、执行服务器回归、预计算画像并保存文件更新计划；随后执行 `activate --backup <stage 返回目录>`。

仅切换 `/opt/x-tag-publisher/current`、画像模块、画像静态文件及频道列表画像列。共享快速启动导航内容、main API、原发布服务、原队列、账号凭据均保留。

激活前仅暂停画像自动调度/执行触发器和画像素材池触发器，等待当前相关 oneshot 自然结束，不要求清空积压或所有渠道空闲；取得这些资源已有的文件锁和画像刷新锁。只重启画像自动发布 API、画像网关和只读画像 API，恢复此前运行的相关触发器。原 X 调度状态由现有健康脚本只读采集，新流程触发器单独核对，因为该脚本当前未收录 x-tag 单元。

用户最初要求新流程为空。开发期间已观察到用户新建的 2 个模板和 90 个任务；部署必须保留实时业务配置，不把“初始为空”变成升级时清空数据库的条件。

运行前检查另确认独立目录 `media-work` 未由最初安装脚本创建，14 个现有任务记录“X Post媒体工作目录无效”。修正首次安装和升级时的目录初始化，所有者为 `x-post-automation`，权限 0700；已有目录和其中的媒体保持原样。上线后用发布服务账号验证固定存储布局和实际探针写入，不重建或手工重发任务。

目录修复后，原批次实际继续执行暴露画像网关的 SQLite WAL 读者协调文件权限问题。相同归属解析在服务外成功、服务挂载命名空间内报 `OperationalError: unable to open database file`，定位于 `Resolver.users()`，真实内部接口返回 503。`deploy/x-tag-gateway-sqlite.conf` 仅给该网关开放用户库父目录的写权限，供 SQLite 创建和维护 WAL 共享内存协调文件；用户库连接仍为 mode=ro + query_only，不写用户业务记录。目录必须解析到实际数据盘路径，不能只开放 `/root` 下的迁移别名，否则只读 URI 使用实际路径时仍会间歇失败。用 `scripts/deploy_x_tag_gateway_storage.py install` 发布此单独配置，只重启画像网关；其回滚为同脚本 `rollback --backup <gateway-storage-backups 目录>`。历史失败回执保留，不以重发任务作为验证手段。

备份位于 `/mnt/data-disk/x-tag-publisher/hierarchy-backups/<timestamp>`，包括修改前代码、画像快照、业务数据库副本和运行状态。回滚命令：

```sh
python3 /mnt/data-disk/x-tag-publisher/sources/<commit>/scripts/deploy_x_hierarchy.py rollback --backup /mnt/data-disk/x-tag-publisher/hierarchy-backups/<timestamp>
```

回滚只恢复本次代码、静态内容和可重建画像；不恢复业务数据库副本，不撤销任务、租约、素材保留、回执或用户配置。检测到后续同文件改动时先人工合并，避免覆盖其他工作。
