# X Auto 执行与回执核对公平领取

原生发布模式下，旧队列的观察任务每 30 秒再次到期，并始终排在新选剧前。一个每分钟最多执行 20 项的 runner 会反复核对旧任务而无法推进新任务，甚至较晚的旧任务也轮不到核对。

现在在同一 SQLite 领取事务内读取最近一次领取事件，轮流优先处理「选剧/准备」和「回执核对」。任一类没有符合条件的任务时，另一类继续使用全部执行额度。回执类内部按下次检查时间、过期租约时间排序，刚检查过的旧任务不会一直占据队首。最近领取事件已经持久保存，因此多个 worker 和进程重启共用同一轮次，无需新增调度表或扩大并发。

只有 `publish_delegated=True` 且执行开关开启时启用公平领取。关闭开关仍仅核对原执行，非原生发布沿用旧顺序。未来发布时间、重试时间、租约、人工暂停、历史处理边界、身份、素材防重和未知写入保护保持不变。未知发布始终进入核对，不增加发布尝试。

```sh
python -B scripts/test_x_auto_fair_claims.py
python3 -B scripts/test_drama_launch_range.py --platform x

```

专项使用真实 SQLite，构造 25 个旧回执及 25 个新任务跨三轮执行，验证两类交替、旧任务逐个轮转、每次重开 store、并发不重复领取、空类不浪费额度、未知写入和关闭开关、未来排期、backoff、有效租约、hold/cutoff 和旧模式优先级。完整运行时专项共 14 项。

首次本地运行误将导入的旧 store 测试类也自动发现；其中两项冷却测试沿用已废弃的跨账号冷却约定，本分支此前即不兼容。没有为其修改生产冷却规则，专项改为按模块导入夹具。
