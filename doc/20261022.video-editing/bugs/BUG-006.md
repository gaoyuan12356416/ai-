# BUG-006 同项目同版本跨刷新重提生成重复批次

## 发现与影响

2026-10-22，主实施确认P1缺口：同一个项目版本在页面刷新后重新提交，前端生成新的operation_id；后端仅按owner + operation_id查找已有批次，因此会创建新批次和新的逐剧任务。已有成片记录虽未被覆盖，但同一冻结内容可能再次占用GPU制作并生成重复成片，违背成功任务不重复制作的要求。

## 复现条件

1. 提交项目的某一固定version，保存返回的batch_id、task_ids与project_version_id。
2. 不编辑项目，刷新页面或使用新的operation_id再次提交相同project_id和expected_version。
3. 返回新的batch_id及逐剧任务，而不是已接受的原批次。

同一operation_id重放、原GPU job重复POST缓存、完成态独立listener停启后的缓存恢复分别有既有通过证据；它们都不能证明跨新operation_id的同版本提交不会重复。这是本次遗漏的边界。

## 根因与修复

原操作幂等范围是一次客户端请求的operation_id，稳定项目版本没有对应的服务端批次复用规则。修复在 `service.py` / `store.py` 中按项目和冻结版本识别已接受制作，并持久保存调用者操作映射：

- 新增 `ve_render_operation`，以调用者owner + 外部operation_id为主键，保存project_id、project_version及batch_id；相同调用操作跨项目或版本返回 `operation_conflict`。
- 先查已保存映射和历史原操作号，再按project_id + version复用最早接受的批次；queued、running、unknown、failed、completed等状态均不重建或重置。新版本仍可提交新批次。
- 历史重复批次保留，各原operation_id仍返回自己的原批次；只附加表和索引，不删除任务、配方、批次或COS对象。
- 新批次 / 任务 / 成片归项目owner，batch和task保存实际提交者 `submitted_by`。新内部操作号包含调用者身份摘要，避免不同管理员的同名外部操作相互冲突。
- 历史管理员任务保持原owner；无权项目owner请求复用时返回409 `batch_task_permission_conflict`，不泄漏原任务，也不新建替代批次。
- 查找、映射、新版本快照、批次、逐剧任务和pending成片在同一 `BEGIN IMMEDIATE` 事务完成，并发请求串行核实，异常整体回滚。已成功任务不重制；失败仍按原task恢复。
