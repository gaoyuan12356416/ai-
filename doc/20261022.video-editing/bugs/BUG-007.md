# BUG-007 失败临时目录到期清理后的有条件恢复

## 发现与影响

2026-10-22，正式双剧完成后继续审查失败任务恢复边界，发现修复前的实现会拒绝所有已清理scratch的失败任务，包括从未开始上传的任务。当前候选已实现有条件恢复：仅无上传意图、固定COS输出经认证HEAD明确404，并绑定原expiry与新generation的scratch epoch时，允许沿原job恢复；上传结果未知继续阻挡重建。该修复不改变成功成片的缓存与身份。

## 修复前根因

原 `cleanup_failed` 在确认stopped的failed任务到期后写入 `expired.json` 并删除work；原 `can_resume` 只检查标记是否不存在，原 `execute` 遇到标记直接返回409 `gpu_job_resume_unavailable`，没有区分从未上传与上传未知。仅删除标记仍不安全：旧 `*.local.json` 指向已删除媒体，`load_completed` 会返回 `checkpoint_unverified`，也可能跳过已有上传结果的核实。该描述是修复前根因，不是当前候选的恢复规则。

## 已实现边界（真实隔离恢复通过，生产部署与独立回读通过）

实施者已修改 `features/video_editing/gpu_integration.py` 及runtime相关测试，保留同一job身份和冻结配方，仅在严格证明安全时创建新generation：

- expiry记录附带配方fingerprint和expired_generation；保留原expired / local证据，不把删除标记作为恢复手段。
- 必须没有上传checkpoint、上传意图或上传结果未知证据，并对固定输出key执行认证HEAD。render的 `material.mp4`、probe的 `thumbnail.jpg` 与 `preview.mp4` 都必须明确404；200、403、超时、身份不符、旧版未绑定expiry或损坏证据均不允许盲目重建。
- 保留原AsyncRuntime的expected_generation CAS与stopped守卫；进入真实active context后再次核实条件，再原子写入scratch epoch。新local checkpoint写入 `local-attempts/gN`，普通后续恢复沿用同一epoch；网络HEAD不持有共享runtime mutex，完成后重查active身份及本地证据。
- 有效result优先返回cached，不重制成功输出。同generation重复清理保持原expiry字节；新generation的旧expiry按SHA归档后再建立新保护记录，避免覆盖审计证据。

上述实现已纳入本地126项回归（125通过、1项可选SDK跳过），主实施、后端负责人和GPU实施者分别独立执行通过。runtime子集18项全部通过，已计入126；新增9项恢复用例的最后一项验证慢COS HEAD不会阻塞共享runtime的旧任务GET。GPU实施者完成最终旧模块215项，209通过、6跳过。独立review无阻断；下述真实隔离恢复已通过，生产窄更新及最终独立回读通过。

## 验收边界

1. 未上传失败到期清理后，经认证404和原generation CAS，仅建立一个新generation，沿原job / 配方恢复；重复或并发resume不会重复执行。
2. 上传意图、未知上传、对象已存在、HEAD权限或网络失败、损坏checkpoint均保持拒绝或核实状态；成功result继续cached且无新增制作。
3. 清理前后的expiry、历史local及新epoch证据可追溯，旧generation不能覆盖新generation；反复失败与再次清理仍受保护。
4. 独立代码审查、旧模块回归及下述隔离验证已完成；生产更新按确切提交执行，并保存账本和成片身份回读。
