# Coordinator restart without waiting for long local renders

The coordinator's old ExecStop barrier paused every new claim until all CPU and
GPU tasks finished. A long CPU VP9 encode therefore left the GPU idle even when
the worker and its lease were healthy.

For a systemd **restart** of `pipeline-coordinator.service`, the helper now
separates resumable local rendering from tasks that must drain. Plain stops,
shutdowns, the X canonical services and the main API keep their existing barrier.
The helper checks the actual systemd job each time; a status preview cannot
authorize a stop or change its meaning.

A render can continue only if it is a current distributed `prepare` claim using
the existing FB, TT or X local renderer, reports `render` from a CPU/GPU node,
has a fresh worker/node heartbeat and at least 90 seconds left on its lease,
and has no external operation or cloud-job intent. Unknown/legacy executors,
stale observations and publication jobs remain blocking. In particular, an X
upload between two HTTP calls remains a publication job and cannot be skipped.

The admission hold is still installed under the coordinator's SQLite writer
lock. It blocks new claims until the replacement service is healthy **and** the
handed-off claims renew their heartbeat or record a terminal receipt. Worker
PIDs, claim generations, identities, resources, receipts, reservations and all
platform-write safeguards remain unchanged. Non-success terminal results are
reported for attention; existing job-local failure/quarantine rules continue to
apply. No task is replayed or marked successful by this helper.

This is a short restart using the workers' existing 120-second disconnected
render lease, not permission for an unbounded outage. Startup failure keeps the
admission hold. The worker's existing lease-loss cancellation and durable result
reconciliation remain in force if the authority cannot recover in time.

## Validation

`python -m unittest scripts.test_pipeline_restart_handoff scripts.test_pipeline_worker scripts.test_x_upload_continuity`

Coverage includes restart versus stop, legacy/cloud/unknown execution, expired
leases, external intent, publication between operations, unchanged identity and
resource ownership across coordinator replacement, heartbeat-confirmed startup,
failed startup retaining the hold, durable callback retries and unknown-write
quarantine without replay.

## Deploy and roll back

Fetch the pushed commit into an independent clean CPU checkout. The installer
changes only the coordinator's existing `70-upload-continuity.conf`, preserving
the scheduler-health hook and every other unit. It backs up the old drop-in and
verifies its contents before replacement. It does not restart services.

```sh
python3 ops/coordinator-render-handoff-20261120/install.py install --directory /mnt/data-disk/coordinator-render-handoff-20261120/config-backup
python3 scripts/pipeline_service_drain.py status --unit=pipeline-coordinator.service --preview-restart
systemctl restart --no-block pipeline-coordinator.service
```

Before the verification restart, snapshot the coordinator scheduler lane and
current claims. Afterwards verify the new main PID, the helper's carried-render
record, renewed original identities/leases, continued output progress, fresh
`latest-coordinator.json`, and newly claimed GPU work.

Rollback only the helper configuration using the same exact checkout:

```sh
python3 ops/coordinator-render-handoff-20261120/install.py rollback --directory /mnt/data-disk/coordinator-render-handoff-20261120/config-backup
```

Rollback needs no worker restart and must never restore an old business database
or delete a live hold. A helper already executing finishes with its loaded code;
the restored configuration applies to subsequent stop/start operations.
