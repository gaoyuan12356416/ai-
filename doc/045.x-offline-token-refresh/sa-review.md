# SA 评审意见

## 结论

通过，按“授权状态与短期 Access Token 状态分离、执行前和最终写入前双重按需刷新”的方案开发。

## 问题清单

| 编号 | 严重级别 | 位置 | 问题 | 建议 | 状态 |
| --- | --- | --- | --- | --- | --- |
| SA-001 | 高 | 状态投影 | 仅把过期改为有效会让发布继续拿过期 Token | `status=active` 只表示可续期授权，最终凭证读取仍严格拒绝过期；执行链必须先按需刷新 | 已纳入 |
| SA-002 | 高 | Token 轮换 | 刷新可能轮换 Refresh Token，错误恢复旧备份会破坏凭证 | 原子替换完整 Token，保持 owner/mode；备份仅作证据 | 已纳入 |
| SA-003 | 高 | 队列幂等 | 刷新失败不能越过预检或造成重复 Post | 预检先刷新；最终刷新位于写入前，失败时写已知失败且 X 写入为 0 | 已纳入 |
| SA-004 | 中 | X Auto | 预览若刷新会产生非只读副作用 | 预览继续读本地快照；仅真实建 Run 与执行刷新 | 已纳入 |
| SA-005 | 中 | 瞬时故障 | 限流/网络失败不应误标永久撤销 | 自动路径使用 `preserve_transient_status`，明确撤销才标记 `revoked` | 已纳入 |

## 决策记录

- 不把 Refresh Token 描述为永久；仅在未被撤销且成功刷新时持续使用。
- 不在 `publish_credentials(...)` 内做网络刷新；它继续承担最终锁内动态检查与只暴露 Access Token 的边界。
- 不新增数据库列，所有新增状态均从现有安全元数据和 Token 是否存在动态投影。
