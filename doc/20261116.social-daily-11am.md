# 社媒发布人日报 11:00 投递修复

目标群：`oc_7c683c5770aef2e6c84a456e52cad389`。

## 原因与证据

2026-11-16 北京时间 11:00 正常触发，但 2049 效果源读取失败，
完整性检查在 11:01:44 拒绝投递。11:06:44 自动重试，11:08:00 发出。
原日报运行副本吞掉了 SQL 子进程的 stderr，只留下通用“读取失败或繁忙”；
无法再从原日志区分当次是 MySQL 还是外围执行超时。

只读复现冻结了 19,335 个 campaign/Page/material 三元组、796 个 Page。
原计划强制 sd(site_id,dt)，估计读取 41,472 行，再执行大 IN、精确分组。
原查询单次进程用时 21.608 秒；单纯切换 adset_dt 的大查询复现 MySQL 3024，
耗时 22.752 秒。另一大查询约 26 秒后返回旧版通用错误。
SQL 上限是 20 秒，FIFO Gate 执行上限是 24 秒；这条查询缺乏时间余量。
仅缩小输出候选或换索引不足以解决。64 Page 索引查询样本用时 6.517 秒。

## 最终行为

- 仅独立日报的 Facebook 读取按最多 64 个 Page 分批，最多两个并发 FIFO 查询。
  使用现有 adset_dt 索引；普通列索引条件与二进制 Page 条件同时保留，
  再精确校验 campaign/Page/material，防止大小写及跨三元组混入。
  日期覆盖只读一次。任何批失败不返回部分成功，保留原 SQL/总采集预算。
- 独立准备任务每天北京时间 10:40、10:50、10:55、10:58 采集完整前一 UTC 日。
  只原子替换当日报表的完整快照；失败保留最后完整快照，不认领投递账本。
- 原 11:00 定时器和原日期/群防重账本继续使用。11:00 优先读取完整准备快照，
  无需再访问效果数据库。准备和发送使用独立锁，准备中的新版本不阻塞发送。
  卡片显示实际采集完成时间。快照不可用时保留原受限采集/重试兜底。
- SQL 错误记录安全的查询摘要、MySQL 错误码、Gate 超时分类和耗时，不记录
  SQL 原文、凭据或 stderr 原文。历史已发、sending、unknown 均不能盲目重发。
