# SA 评审意见

## 结论

有条件通过。允许实现一次性人工私密测试，但不得把现有三重正式门禁写成已通过，也不得让自动排期复用白名单。

## 问题清单

| 编号 | 严重级别 | 位置 | 问题 | 建议 | 状态 |
| --- | --- | --- | --- | --- | --- |
| SA-001 | 阻断 | CPU/GPU 门禁 | 直接把正式门禁改为 1 会伪造平台审核和 URL Property 状态 | 增加默认关闭、精确目标、固定确认短语的一次性白名单 | 已采纳 |
| SA-002 | 阻断 | 自动排期 | 账号级放开可能被每日 runner 误用 | 必须同时校验 `trigger_type=manual`，自动任务仍只认正式门禁 | 已采纳 |
| SA-003 | 阻断 | 发布可见性 | 未审核客户端不应尝试公开发布 | 服务端强制 `SELF_ONLY`，不能依赖页面传值 | 已采纳 |
| SA-004 | 高 | 幂等性 | TikTok 初始化超时后重试可能产生重复发布 | GPU 在网络调用前落幂等账本，任何首次调用结果均禁止重新初始化 | 已采纳 |
| SA-005 | 高 | 存储来源 | 绕过 URL Property 门禁不能等于接受任意 URL | 仍要求成片 URL origin 精确匹配当前 GPU 存储 origin | 已采纳 |
| SA-006 | 中 | 可观测性 | UI 若只显示正式门禁关闭，会继续禁用按钮且误导运营 | 返回独立的 `manual_canary_ready`，明确提示测试范围 | 已采纳 |

## 决策记录

- 不修改三重正式门禁的语义和线上值。
- 不修改数据库 schema，以现有 schedule run 与 queue 绑定关系识别人工测试。
- CPU 和 GPU 各自校验，避免单点配置或请求字段被误用。
- 配置白名单是临时生产控制面，测试结束后关闭并保留代码默认关闭。

## PM 修订确认

需求文档已补充一次性、人工、私密、精确目标、无自动排期、未知结果不重试和不代用户点击等验收边界。
