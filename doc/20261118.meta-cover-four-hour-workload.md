# Four-hour workload reporting

The operator changed the report contract on 2026-11-18: each four-hour report
contains only work in the preceding completed four-hour interval. Keep Beijing
01:30/05:30/09:30/13:30/17:30/21:30 and the existing recipient. Set both
`cover_report_hours` and `cover_report_lookback_hours` to 4.

Count each Ad task and old Creative by its last processing outcome inside the
half-open interval. Include review/reference waits and other deferrals processed
in the interval, but exclude untouched historical backlog and unknown outcomes.
A newly confirmed old task counts when its confirmation occurs. Report newly
queued Ads and completed/failed scans in the same interval. Omit cumulative
queues and historical queue/reference latency. Do not rewrite or resend frozen
past windows; retain notification UUIDs and unknown-send protections.

Deploy only the reporter: fetch the exact GitHub commit into an immutable
release, back up config, notification unit/drop-ins and the audit database using
SQLite backup. Stop only `meta-cover-notify.timer` and verify its oneshot idle.
Render `deploy/meta-cover-notify-release.conf.in` with the verified release into
`/etc/systemd/system/meta-cover-notify.service.d/report-release.conf`. Update only
the two report-hour config fields, reload systemd, and restore the timer. Leave
the worker/scanner release symlink and PIDs unchanged. Validate the future next
window with `notify_daily(..., at=next_boundary, dry_run=True)`; no message is sent
and no body is frozen by preview.

Rollback restores only the saved report-hour fields and previous report drop-in,
then reloads systemd and restores the timer. Preserve the current config's other
fields, live execution databases, audit database and notification receipts. A
code rollback does not undo or resend an already delivered window.
