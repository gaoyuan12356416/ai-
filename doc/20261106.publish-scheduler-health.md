# Publishing scheduler restoration and deployment verification

The November 6 audit found two additional enabled but stopped planner daemons:
`fb-group-pool-scheduler.service` (stopped November 2 20:13:58 Beijing) and
`x-video-pool-scheduler.service` (stopped November 2 19:01:37). The FB group
pool was enabled; X had 66 enabled and 29 paused personal pools. Existing
X ordinary schedule/claim/manual/Auto timers, TikTok timers, YouTube automatic
worker, coordinator and CPU execution node were operating. The older
`drama-youtube-publish-worker.service` is not the active canonical route and
must not be enabled as a substitute. X Auto's optional path wakeup is not
required for its working minute timer and is not enabled by this repair.

## Installed behavior

The FB owner now Wants its group pool scheduler; the X owner Wants the
personal pool scheduler and its already-used automatic-template sidecar.
Existing Page pool/short-link dependencies remain. No parent process restart,
account/pool enablement, historical replay or task reset is needed.

Each owning service also Wants a scoped `publish-scheduler-check@LANE.service`.
The check is ordered after the relevant services/timers and executes after
future starts, including deployment restarts. It runs independently and
never blocks or stops publishers. Failure remains visible as a failed check
unit, journal entry, and `/mnt/data-disk/publish-scheduler-health/latest-LANE.json`.
There is no recurring service-start watchdog or automatic publication retry.

Checks distinguish running daemons, timers with future triggers, currently
executing oneshots, and successfully completed oneshots waiting for the next
tick. Stale successes and inactive daemons fail. Unknown/missing units fail;
an inactive oneshot after a recent successful run is normal.

## Required deployment acceptance

For changes which restart a publishing owner, save the affected lane before
the change and check it after restoring that lane. Static/document-only work
does not restart services or require unrelated platform checks. These commands
use the independent installed tool, so old deployment working trees can use it:

```sh
TOOL=/opt/publish-scheduler-health/current/scripts/publish_scheduler_health.py
python3 "$TOOL" snapshot --lane x --output /mnt/data-disk/YOUR-DEPLOYMENT/schedulers-before.json
# Perform the scoped, drained deployment.
python3 "$TOOL" restore --baseline /mnt/data-disk/YOUR-DEPLOYMENT/schedulers-before.json --wait-seconds 25 --output /mnt/data-disk/YOUR-DEPLOYMENT/schedulers-after.json
```

Inspect an unhealthy pre-deployment baseline instead of treating it as proof
that a disabled process is intentional. Restore only previously active
daemons/triggers; never directly execute a publishing oneshot for verification.
Resolve a deliberately paused service explicitly in the lane contract instead
of silently enabling it. Preserve business schedule switches, unknown outcomes,
receipts and active leases. A post-deployment failed check prevents calling that
lane healthy; it does not roll back business facts or block other platforms.

Supported lanes: `fb`, `x`, `tt`, `youtube`, `coordinator`; `all` is for this
cross-platform audit. Periodic scheduler freshness is process evidence, not
proof that a particular platform post succeeded.

## Release and rollback

Commit/push first, fetch the exact commit, archive the two scripts, test and unit
into a new immutable data-disk release. Run `deploy_publish_scheduler_health.py
--source RELEASE --commit SHA`. It records unit files, old release pointer,
parent PIDs, before/after checks and online FB/X database snapshots. It only
starts the two explicitly audited missed daemons plus read-only check units.

Rollback: `python3 RELEASE/scripts/deploy_publish_scheduler_health.py --rollback
BACKUP`. This restores only configuration/tool pointers. Keep the restored
business schedulers running; never restore database snapshots or publication
receipts. Preserve other concurrent releases and the earlier Page pool fix.
