# X 两条发布流程共用短链编号

原流程与标签画像流程原来直接把各自日志 ID 放进网址，画像 ID 从
9000000000000 开始，使链接过长。新发布链接统一使用
`https://gy.g2flow.com/s/<编号>`，编号独立递增；内部队列、日志 ID、
长链接、收入归因和历史帖子不变。

## 分配与兼容

两条发布 Sidecar 使用同一个 SQLite `short_link` 表：自增主键负责全局
不重号，`UNIQUE(origin,log_id)` 保证同一任务重复取号不变。
`BEGIN IMMEDIATE` 串行化分配及不可变目标写入。长链接首次绑定后不能
更换；文件写完但事务未提交的中断仅允许原目标恢复。运行时禁止自动
创建丢失的数据库，避免从头分配已使用编号。

存储：`/mnt/data-disk/x-shared-short-links/links.sqlite3`，网页放在
`public/<编号>.html`。只有发布服务用户可写数据库；Nginx 只服务 public。
所有旧 `/s2l/ID.html`、`/s2l-tag/ID.html` 保持原目录和访问规则。
只有尚未生成链接的发布日志分配新编号；已冻结的内容不重写。

普通发布与统一调度均使用 `features/x_posts/service.py` 的生成/写入接口。
统一调度 `_links` 在冻结日志前持久化跳转文件，避免失败后早返回一个
文件尚不存在的短链。标签 staging 必须跳过 shared_short_links.py 的
字符串替换，两条流程共享同一份模块。

## 验证与部署

运行 `python -m unittest scripts.test_x_shared_short_links
scripts.test_x_shared_short_deployment scripts.test_x_posts -q`。覆盖多进程
抢号、重复调用、来源隔离、目标防覆盖、崩溃恢复、旧链、回滚、普通发布
及统一调度冻结顺序。所有 X HTTP 写入均使用离线替身。

提交推送后在 CPU 服务器 fetch 精确提交到独立源码 checkout，运行：

```
python3 scripts/deploy_x_shared_short_links.py stage --folder /mnt/data-disk/x-shared-short-deploy-20261111
python3 scripts/deploy_x_shared_short_links.py activate --folder /mnt/data-disk/x-shared-short-deploy-20261111
```

部署从两个当前 runtime 各自复制候选，只应用已记录的局部补丁，保留其他
发布中的版本变更。候选执行测试、备份两个账本并记录文件哈希。新增独立
路由后逐个排空发布 Sidecar 的 HTTP 请求并切换；不重启 coordinator、
CPU/GPU 节点，不重放任务。按 X 调度健康工具恢复原先运行的依赖服务。

## 回滚

```
python3 scripts/deploy_x_shared_short_links.py rollback --folder /mnt/data-disk/x-shared-short-deploy-20261111
```

回滚将 `X_POST_SHARED_SHORT_ALLOCATE=0`，停止新取号；已分配的编号、
读写兼容代码与 Nginx 路由保留，未冻结的既有分配也继续使用原号。后续
未分配日志回到各自旧短链路径。禁止删除编号表、回退 SQLite 快照或直接
恢复不认识新链接的老代码。源文件和账本备份及前后调度状态见部署目录。
