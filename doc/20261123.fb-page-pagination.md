# Facebook Page management pagination

Page management previously downloaded every tenant configuration (about 2.59 MB
decoded) before locally displaying twenty rows. Its GET now requests twenty rows,
and the sidecar filters the full tenant-local catalog by Page name/ID and creator
before slicing. Responses include matched total, actual page and creator choices.
Stable Page-ID ordering is unchanged. No database schema or task data is changed.

The existing endpoint without pagination retains its full-list contract for manual
publish selectors and other consumers. The create picker marks already-configured
Pages even when those Pages are outside the current management page. Mutation and
preflight checks remain the authority; no permission check is replaced by a cache.

The public Cookie/module/navigation/identity boundary is unchanged. Page configs
remain tenant-shared under the already deployed rule, and visible Page authorization
is checked in batches of at most eight. Unknown checks are displayed as unknown;
publication and configuration writes still perform their current live validation.
Pagination cancels superseded list requests and discards old list/authorization
responses. Language and portrait failures remain local to their auxiliary views.

Use `scripts/deploy_fb_page_pagination.py prepare --folder FOLDER` and then `apply`
from the pushed GitHub checkout. It overlays only the Page service and shared JS,
updates their asset references while preserving live HTML changes, and uses the
existing scoped owner drain and prior-active scheduler restoration. Current runtime
image hashes detect concurrent changes; independent rendering claims are preserved.
The main API is not restarted. Rollback uses the same script with `rollback` and
restores only code/assets, retaining current ledgers, receipts and configuration.
