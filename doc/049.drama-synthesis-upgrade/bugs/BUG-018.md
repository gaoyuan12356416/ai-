# BUG-018 Canary 隐私漂移后仍同步统一表

2026-08-27，P1。状态：修复并经独立 QA 复核 PASS，包含在候选 `c719bebf72be900ec3853858dc53b36b83beffd2`。此缺陷由无网络 fake 复现，不是已发生的真实平台写入。

## 最小复现与根因

第一次视频读回 processed/succeeded/unlisted 后产生 pending video/log outbox；评论前第二次读回变为 public，任务正确转 unknown，但 CLI 无条件 drain，仍将两个实体写入统一表。另一分支是视频/评论已完成、outbox 仍 pending，重复 run 的引擎 no_pending 不再读回隐私，也会直接同步。

根因是把先前视频成功或本次引擎无工作误当成同步阶段的实时授权，未对待同步任务重新验证 privacy/processing/identity。

## 修复

- CLI 仅接受严格 canary 范围、视频与评论均已确认成功且 unknown=0 的同步候选。
- 每个实体 claim 前 fresh 查询精确 video ID，必须 processed/succeeded/unlisted；可复用同 tick 已刷新且验证身份的 token，completed/no_pending 路径仍要刷新并验证目标身份。
- 不满足时持久记录 hold_youtube_canary_sync，保留原 video/comment IDs 和 pending outbox；本次零新 outbox claim，不能输出 complete=true。
- core 的 canary outbox claim 同样校验状态；普通 public 流程不增加 canary 特有门禁。修复后只能对账原视频，已成功评论不重发。

涉及 scripts/drama_youtube_canary.py、features/drama_synthesis/core.py 与对应 fake 测试。

## 独立验证

独立 QA 重新执行原故障探针：评论前 public 漂移时统一写入为 0/outbox attempt 为 0；completed + pending 在 public/private/processing/unknown 状态均 hold，既有评论不重发。恢复同视频有效 unlisted 后可以继续原 outbox，不创建替代任务。

重点回归为 test_privacy_changes_before_comment_leave_existing_outbox_unclaimed、test_completed_pending_outbox_requires_fresh_privacy_and_processing_readback、test_sync_hold_reconciles_same_video_without_reposting_comment。与 BUG-019 合计九项独立定向复核 PASS，已包含最新合并 166/166；不得将九项再次加总。真正 YouTube/生产统一表验收仍待合法 writer 权限及其他发布门禁解除。
