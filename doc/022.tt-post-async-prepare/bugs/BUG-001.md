# BUG-001 素材校验长期卡在“读取中”

## 发现阶段

2026-07-30 生产页面操作验收。素材 `5391678` 在“批量填写素材 ID”步骤长时间显示“读取中 1/1”。

## 现象

操作人只想确认素材 ID 是否有效、能否加入发布池，但页面请求持续到 GPU 完成长视频下载、去尾、片尾拼接、压缩及成片上传后才返回。34.8 分钟素材的制作与网络上传可能持续数分钟，页面表现为卡死。

## 复现步骤

1. 进入 TT Post 发布池并选择已配置账号。
2. 输入一条未预制作的长视频素材 ID。
3. 点击“批量读取素材”。
4. 观察按钮停留“读取中 1/1”，浏览器请求等待完整 GPU prepare。

## 期望结果

- 读取阶段只查询只读素材库。
- 合法素材快速返回素材信息和真实 Drama ID。
- 校验通过即可加入素材池。
- 视频下载、转码、片尾拼接与上传在后台独立执行；页面可退出并在之后查看状态。

## 实际结果

`material_preview()` 同步执行 `_resolve_and_prepare()`；入池接口也同步制作。用户请求与 GPU/COS 长链路绑定，任何下载、编码或上传变慢都会阻塞页面。

## 根因分析

旧流程把三个不同的业务阶段合并为一个同步请求：

1. 素材身份校验：只需要 resolver/MySQL。
2. 持久化入池：只需要冻结账号、Drama ID、文案、授权与制作合同。
3. 成片预制作：需要 GPU、长超时、网络上传和最终媒体校验。

由于缺少“已校验但未制作”的 durable 状态，系统只能在创建 ready pool 行之前完成全部成片字段，导致 preview 被迫承担长耗时。

## 修复说明

1. `material_preview()` 仅调用 resolver，返回 `validated/not_started`，不调用 GPU。
2. 新增 additive `tt_post_material_intake`，校验通过后立即写入 `queued`。
3. 新增独立 prepare runner，由 path 快速唤醒、timer 每分钟兜底；与到点发布 runner 使用不同进程锁。
4. runner 使用 durable lease、周期 renew 和 claim token fencing；进程崩溃后可回收过期任务。
5. 按账号严格 FIFO，避免同账号素材制作顺序错位。
6. GPU 成功且账号实时限制通过后，在同一 SQLite 事务中写 ready pool 并将 intake 置 `ready`。
7. 页面入池后立即解除 busy，轮询显示 queued/preparing/retry_wait/ready/failed。

## 回归结论

本地自动化已证明前五项代码合同，无真实发布回归；最终关闭仍需生产关闭态 canary 同时证明：

- preview 与 add 返回前 GPU 调用为 0；
- queued 不可发布；
- 独立 runner 可将 queued 变为 ready；
- 旧 token 无法覆盖新 claim；
- 原有 TT 发布 runner、定时点和手动发布逻辑无回归；
- TikTok init/post 增量均为 0。
