# Recovery batch backups

FB GET settlement and exact unpublished-task recovery now require
`--backup-batch BATCH` with `--backup-dir ROOT` when applying a verified plan.
Use the same ROOT and BATCH for every invocation in one recovery operation.
`ROOT/BATCH` contains one immutable native/dispatch SQLite snapshot pair and
`batch.json` with their checksums and source identity. Separate operations use
separate batch IDs. A missing or changed snapshot fails before any ledger write;
an incomplete first snapshot is retained for inspection.

Each application fsyncs a small transaction preimage before changing its rows.
The existing database event remains the authoritative commit receipt; the
additional `*-committed.json` is a convenience receipt. A crash after commit
must be reconciled from current rows/events, never retried blindly. Do not
restore an old whole-database snapshot over current publishing ledgers.

This changes backup storage only. GET evidence, exact identity, frozen plan,
unknown-outcome fences, and unpublished-recovery admission requirements remain
unchanged. No API POST or live recovery is part of deployment validation.

Validation: `python -m unittest tests.test_recovery_batch_backup
tests.test_fb_observed_settlement`, plus syntax compilation and diff checks.
Deploy only the three scripts to the existing recovery checkout after fetching
the pushed commit. No publisher restart is required. Roll back those scripts
to the recorded previous commit, preserving every batch and task audit file.
