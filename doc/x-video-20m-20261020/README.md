# X 发布时长策略 20 分钟

新任务统一冻结 `duration_policy_version=2`：普通账号实际时长不超过
1200 秒可直发，使用 `tweet_video`，归因 `short`。超过 1200 秒沿用会员、
会员代发或拦截规则，归因 `long`。512 MiB 文件限制、会员 14400 秒上限
和模板明确保存的筛选条件不变。

## 历史兼容

- 队列、每日/补充/手动/排程运行以及独立 X Auto 运行新增不可修改的版本列。
  已有记录与旧代码新建记录默认为版本 1；本版所有新建运行明确写入版本 2。
- 版本 1 保留 140 秒边界、原代发绑定、已准备链接、随机请求和 GPU 缓存键。
  内部运行快照透传同一版本，预检、随机制作、最终上传和归因读取该版本。
- GPU 新增 `standard_20m`，超限时沿用裁切流程，目标 1199 秒；
  合规的 1094.871 秒素材保持完整。旧 `standard` / `premium` 策略保留。
  新队列和修复策略进入任务指纹，避免复用 139 秒旧成片。
- 不恢复历史失败、不补发、不改写发布账本。未入队素材在后续候选预检中
  按新策略复检；旧错误留到复检成功。迁移本身不解除旧时长错误。
- 线上账号列表已有运营统计列，此次以线上文件为基准保留该功能。
  CPU 发布服务、主 API 和 GPU 各自按部署前 SHA256 清单合并，
  不用仓库整包覆盖线上组合版本。

## 部署顺序

1. 将源码提交 GitHub；两台服务器检出同一精确提交。
2. GPU 使用其服务 Python，CPU 使用 `python3`：
   `scripts/deploy_x_video_20m.py --host gpu|cpu --stage`。
   阶段结果写入打印出的备份目录 `manifest.json`。
   CPU 在最终组合版本运行回归，并对 SQLite 在线副本迁移两次；
   校验完整性、外键、所有旧列逐表哈希及历史版本均为 1。
3. CPU 执行 `--host cpu --deploy <CPU备份目录>`：
   保存定时器状态、等待现有工作完成、持有发布锁、停止三个相关 API。
   备份数据库和令牌，状态变成 `cpu_quiesced_waiting_for_gpu`。
4. 确认上述状态后，GPU 执行 `--host gpu --deploy <GPU备份目录>`。
   必须没有活动 GPU 请求，只重启 X 媒体修复服务。健康接口返回
   `standard_20m` 后，CPU 自动继续迁移、切换代码及静态文件、重启服务。
   GPU 兼容性等待超时则 CPU 自动恢复。
5. CPU 核对旧列账本哈希、令牌哈希及权限、主 API/静态文件哈希，
   恢复原定时器状态。维护前已在运行的发布任务不会被强制终止。

## 回滚

从该提交的源目录执行：

`python3 scripts/deploy_x_video_20m.py --host cpu --rollback <CPU备份目录>`

回滚只恢复代码、页面和链接指向；数据库、令牌与发布记录保留。
如果仍有版本 2 的待执行任务，脚本拒绝让旧代码接管，需先排空或明确冻结
这些任务。GPU 是增量兼容版本，回滚 CPU 时保留，以支持已有冻结请求。
备份目录含数据库与令牌，只保存在服务器私有目录，不进入 GitHub。
