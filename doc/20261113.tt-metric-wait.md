# TT metric readiness and unstarted daily recovery

Midnight preparation requested the previous seven complete Beijing days before
the hourly `:12` metric refresh. The native bridge incorrectly made this
temporary selection error terminal. The fix reuses the publisher's existing
five-minute `retry_wait`; the coordinator defers only a TT automatic preparation
whose canonical readback is waiting with no publication evidence. Any central
operation still prevents this deferral. Appointments and daily plans are unchanged.

The three affected files exactly matched production at source baseline
`c25645a8` before editing. Deployment copies each current runtime and overlays only
the changed files, retaining unrelated production overlays. The separately reviewed
X report fix can be included in the coordinator candidate. Its files remain in the
TT-only rollback candidate. Only TT owner and coordinator restart, with scoped HTTP
drain and before/after scheduler snapshots. No publisher node is stopped.

`scripts/recover_tt_unstarted_daily.py` previews exact dates and freezes a SHA256
plan with a two-hour application window. Apply revalidates both locked ledgers,
excludes any material/binding/operation/receipt/unknown/live lease evidence, and
reopens original failed tasks and jobs with audit events. It never calls a platform
or changes run dates, task IDs, schedules, ownership, templates or daily plans.
An empty account snapshot can be filled only from unanimous same-day frozen
siblings of the same account/template version, with donor IDs in the audit.
The scope for this incident is November 12–13, 2026, tasks 5116–5243. It does not
include earlier failures. Existing account eligibility is checked again by the
normal publisher. Future appointments still wait for their saved publication time.

Validation: `python -m unittest scripts.test_recover_tt_unstarted_daily
scripts.test_pipeline_tt_metric_wait scripts.test_pipeline_tt_readback` (17 tests),
plus affected Python compilation and `git diff --check`. The tests cover repeated
metric waits followed by one selection, no new tasks/runs, immutable appointment,
unknown/ID/attempt/operation rejection, approved recovery, changed-scope rejection,
and expired/repeated application rejection. All remote collaborators are fake.

Rollback uses the generated deployment `rollback.sh` and changes code only.
SQLite backups are evidence, never a restore path after publishing has resumed.
Recovered tasks must be observed to their real terminal receipts; enrollment alone
does not establish successful publication.
