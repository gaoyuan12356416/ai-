# X media preflight directory

Both X owners used `ProtectSystem=strict`, but the scheduled-media release set
`PIPELINE_MEDIA_PREFLIGHT_TMP` outside their `ReadWritePaths`. Deferred source
validation therefore could not create a temporary directory. The media-decision
handler returned `media_preflight_unavailable` and retained the queued task.

The release generator now grants write access to its configured scratch path.
For the already running release, install `x-preflight-write.conf` from
`ops/social-scheduled-media-20261119/` as
`/etc/systemd/system/{x-post-automation,x-tag-post}.service.d/zzzzzzz-x-media-preflight-write.conf`.
This adds one directory and preserves the remaining filesystem restrictions.

Before activation, freeze the affected source keys, back up both owner ledgers
with the SQLite backup API, and snapshot the X schedulers and tag dependencies.
Reload systemd and restart only these two owners using their existing ExecStop
drain barriers. Restore previously active dependent daemons and triggers; leave
deliberately stopped triggers stopped. Do not replace queues, reservations or
publish receipts. Pending media decisions retry automatically with their
original tickets.

Verify that the configured directory is writable from each owner's actual
mount namespace and service UID, both HTTP health checks succeed, and the
previous scheduler state is restored. Reconcile every frozen source key against
native queue/publication receipts, including explicit failures and unknown
outcomes. A cleared preparation hold alone is not publication acceptance.

Rollback: restore/remove only the added drop-ins from the deployment backup,
run `systemctl daemon-reload`, restart the same owners through their drain
barriers and restore the saved scheduler state. Keep all current databases and
receipts. Reverting permissions reinstates the preflight problem.

## Additional recovery findings

Restoring scratch access exposed overdue originals whose codecs or dimensions
still require normal preparation. A `deadline_original` decision now returns
`native_media_repair_required` for these two repairable validation outcomes.
The existing media gate selects the native preparation path, preserving the
frozen source, recipe and publishing identity instead of recording a terminal
failure. Other validation errors retain their existing behavior.

Concurrent monitor refreshes were also accumulating full accounting scans after
the gateway timed out. The monitor now runs at most one scan for the same view,
actor and filters. An overlapping request receives `monitor_refresh_in_progress`
and can use the completed short-lived cache on its next refresh. Different
authorization scopes remain separate. Safe native exception logging records
only the exception type and stack locations.

Recovery is explicit and scoped to frozen source keys. The
`recover_x_unstarted_media.py` plan requires failed native and canonical rows,
zero publishing attempts, no platform operations, no publications, no unknown
outcomes and no retained resources. Its apply step requires admission to be
held, backs up the databases and stores the complete prior proof before
rearming the same queue. It never calls a platform API.

Interrupted media uploads use `recover_x_media_interrupted.py` instead. Every
registered node's durable outbox must be reconciled with native and central
operation ledgers. Any Post or upload-finalize operation rejects recovery.
Selected original/reused media must match its exact applied native selection;
rendered media keeps the existing frozen-recipe proof. Recovery preserves the
original operation history and arms only one next generation.

Validate the media gate and fallback, monitor authorization/snapshot behavior,
duplicate-scan handling, failure cleanup and both recovery validators. Business
acceptance separately counts matching native/canonical publication receipts,
currently executing preparation/publication, queued work, explicit account
restrictions and unknown outcomes. Do not describe queued work as published.

The code-only rollback restores the five changed runtime files from the
deployment's `code-installed.json` backup mapping, then restarts only the two
X owners and coordinator through their normal stop barriers. Preserve the
scratch permission fix unless intentionally reverting it too. Never restore a
database backup over newer publications or erase recovery audit history.
