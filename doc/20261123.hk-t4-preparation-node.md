# Hong Kong T4 preparation node

The additional node `hk-gpu-02` adds preparation capacity to the existing coordinator. It does not replace either existing node and advertises only `x_preflight,x_random,x_repair,fb_prepare,tt_prepare`. Publication remains with the existing workers and authoritative services.

## Provisioning

- Tencent Cloud Hong Kong zone 2, GN7.2XLARGE32: one T4, 8 vCPU, 32 GiB RAM.
- 256 GB CLOUD_HSSD system disk; all worker data under `/data/pipeline-dispatch` on that disk.
- One month prepaid, manual renewal notification, 200 Mbps public outbound cap with traffic billing.
- Same VPC/subnet as the existing Hong Kong node; resource team `ads_ai`.
- Ubuntu 22.04, Python 3.10, packaged NVIDIA server driver, existing verified FFmpeg builds and immutable asset catalog.

## Source and deployment

This branch reconciles the existing Hong Kong worker's deployed preparation files onto the 480p release `2a40e97d42ad6c8be129af18b007f2d604ba6b05`. These retain GPU affinity, CPU SHA-256 calculation, malformed-audio compatibility, retained qualified FB output/reconstruction receipts, receipt retry backoff, and explicit video color range. Existing production hosts are not changed.

Push the exact commit, fetch that commit from GitHub on the deployment host, and deploy its verified Git archive to the new node. Keep the commit and SHA-256 manifest with the node. Install `deploy/pipeline-gpu.requirements.txt` in an isolated Python environment. Copy only approved assets, FFmpeg binaries and required COS renderer configuration over the existing Hong Kong private network. Never copy old queues, worker identities, publication credentials, tokens or Codex authentication.

Create a dedicated SSH key on the new node and authorize only forwarding to the coordinator's loopback port 18846. Keep the worker's environment and enrollment/identity files private. Generate local placeholder renderer authentication secrets where the imported renderer requires them; do not copy old service authentication keys.

Run the full `scripts/pipeline_node_check.py --encode --cos-check` as `pipeline-worker`, then enroll with a fresh one-time enrollment token. Verify native 480p GPU output, object storage and the registered capabilities before activating the node. Start with one preparation slot and raise to four after a successful real preparation receipt. Set its publication capacity to zero. Preserve existing node capacities and channel settings.

## Acceptance and rollback

Verify the T4, 8 cores, memory and disk; GPU encoding/decoding and OpenCL; asset hashes; COS access over a same-region endpoint; service user permissions; dedicated coordinator tunnel; fresh heartbeats; real assigned preparation jobs and their completed artifact receipts. Systemd service health alone is insufficient.

Rollback affects only `hk-gpu-02`: set its preparation and publication ceilings to zero using the existing versioned capacity endpoint, wait for its active preparation claims and durable receipts to finish, then `systemctl disable --now pipeline-node-hk-gpu-02.service pipeline-node-hk-gpu-02-tunnel.service`. Preserve its credentials, state and produced artifacts. Do not restore an old coordinator database, clear leases, replay tasks or terminate the prepaid instance as part of service rollback.
