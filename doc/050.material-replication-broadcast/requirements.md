## 背景

上游需要按剪辑师汇总“自动复刻任务已发起”和“自动复刻失败”，并通知对应飞书用户。现有 `/api/integrations/v1/material-task-status-events` 服务的是素材任务最终状态，字段、消息和重试行为均不能被新需求改写。

本需求新增独立批次事件接口和独立持久化投递队列，复用现有收件人映射能力与既有兜底群配置，不接管复刻任务本身。

## 目标

1. 上游每次提交一个剪辑师、一个事件类型的已汇总批次；服务持久化接收后尽快异步发送一条消息。
2. 用严格整批校验、幂等键、冻结消息和持久化投递状态，避免重试产生额外播报。
3. 精确匹配剪辑师私聊；空用户名、无法映射或明确私聊失败进入既有兜底群。结果不确定时停止盲目切换目标。
4. 提供可独立交付的中文 HTML、Markdown、OpenAPI 3.0.3 和两份 JSON 示例，不包含真实凭据、群 ID 或内部数据库地址。

## 范围

### 包含

- 新增 `POST /api/integrations/v1/material-replication-events`，使用本接口专属 Bearer Token，不复用旧接口 Token。
- 严格区分 `replication_started` 与 `replication_failed`；每批 `items` 为 1–50 条并保留原顺序。
- 精确映射 `editor_username → admin_users.username → admin_users.id → admin_user_group.sub_user_id → 有效 email → 飞书邮箱查询得到 open_id`。复用的是既有用户名/邮箱映射缓存；用户组映射仅接受有效状态 `status=0`。新批次的 open_id 在首次解析后随发送目标冻结，不声称另有 open_id 缓存。
- 独立持久化 outbox，原子接收与唯一幂等约束、投递认领/恢复、冻结目标/正文/UUID、有限重试与审计。
- 返回当前批次的接收/投递状态；用相同幂等键和相同内容重提即可读取当前状态，本期不需要 GET 查询接口。
- 私聊失败时按已确认规则通知现有兜底群；群消息必须表达“兜底送达”，不能当作剪辑师私聊送达。

### 不包含

- 不读取、轮询或写入素材/复刻业务表；上述身份映射查询和本功能自身 outbox 持久化是必要且仅有的相关数据访问。
- 不新增“资源 20 分钟”提醒，不创建实际素材、不发起复刻、不生成复刻重试。
- 不更改旧最终状态接口的字段、Token、消息模板、投递状态机或重试队列。
- 不接收 `task_id`、产出素材、最终状态、手机号、邮箱、飞书 `open_id` 或调用方指定的群/私聊目标。
- 不实现接收端按小时聚合、跨批次业务去重、自动拆批或对外“严格 exactly-once”承诺。
- 不把相同复刻失败同时调用新接口和旧接口；上游须避免双路播报。

## 用户故事 / 业务规则

### 汇总和增量边界

上游负责“发起每 2 小时、失败每 1 小时”的汇总周期和跨批次只推新增的去重。接收方不再等待额外周期，也不重新扫描上游数据。每次请求只能包含同一个 `editor_username` 和同一种 `event_type`；多剪辑师、多事件类型须由上游分开请求。

同一资源可以拥有多条不同原始素材，上游通过每条 `resource_id` 与 `original_material_id` 描述它们。接收端不重排 `items` 或 `failed_languages`，不跨批次合并，也不擅自去掉调用方提供的重复条目。上游为真正的新批次创建新键；已接收的批次不得仅为“再发一次”更换幂等键。

### 接口合同

请求头必须为 HTTPS、`Content-Type: application/json`、`Authorization: Bearer <专属Token>` 和 `Idempotency-Key`。Token 至少 32 个无空白 ASCII 字符，仅通过安全渠道单独提供。幂等键为 8–128 个 ASCII 字符，正则 `^[A-Za-z0-9][A-Za-z0-9._:-]{7,127}$`。HTTP 客户端提供唯一合法的 Content-Length，不支持分块或压缩请求体；重复 JSON 对象字段和非 JSON 数值整批拒绝。

顶层恰好三个必填字段：

| 字段 | 规则 |
| --- | --- |
| `event_type` | 字符串，只能为 `replication_started` 或 `replication_failed` |
| `editor_username` | 单行可显示字符串；去除首尾空白、NFC 规范化后至多 100 个 Unicode 字符；空字符串允许，直接走兜底 |
| `items` | 数组，1–50 条，同类型、同剪辑师，保持顺序 |

每条素材的公共必填字段：

| 字段 | 类型 / 规范化后长度 | 业务含义 |
| --- | --- | --- |
| `resource_id` | 非空单行字符串，1–128 | 资源 ID；数字 ID 也必须以字符串发送 |
| `resource_name` | 非空单行字符串，1–255 | 资源名 |
| `original_material_id` | 非空单行字符串，1–128 | 原始素材 ID |
| `original_material_name` | 非空单行字符串，1–255 | 原始素材名 |

以上字符串去除首尾空白并进行 Unicode NFC 规范化，不改变大小写；拒绝控制/格式/代理码点/行段分隔类别 `Cc/Cf/Cs/Zl/Zp`，首尾出现也不能修剪后接受。`replication_failed` 的每条素材还必须有 `failed_languages`：1–32 个非空单行字符串，每个规范化后 1–100 个 Unicode 字符；`replication_started` 必须省略该字段，传空数组也不允许。

拒绝额外字段、类型强制转换、缺失字段、`null`、空条目或不合法项。任一项不合法均整批拒绝，不部分接收、不创建部分 outbox。请求体 UTF-8 字节数上限 32 KiB（32,768 字节）；最终飞书请求 JSON 的 UTF-8 字节数上限 128 KiB（131,072 字节），必须包含兜底包装、消息正文和 JSON 转义的开销。超限分别返回 `413 payload_too_large` / `413 message_too_large`，不截断或自动拆批，由上游缩小批次并为各新子批次分配新键。

### 接收、幂等与对账

- 新批次先完整验证与消息尺寸预检，再在同一持久化事务中记录规范化请求、内容指纹和唯一幂等键。落库成功后才可返回 `202`。已接收的同键同内容重放返回原批次状态，不因未来模板文案扩大而重新触发最终消息尺寸拒绝。
- 首次接收返回 `code=accepted`、`duplicate=false`、批次号 `MRB-0000000001` 格式及 `item_count`。
- 同键、相同规范化内容返回 `202 duplicate_accepted`、原 `batch_id` / `received_at` 与当前投递状态，不新增批次或重置终态。JSON 对象字段顺序不影响等价；数组元素顺序有意义。
- 同键变更类型、用户名、内容或数组顺序返回 `409 idempotency_conflict`；不得通过改键掩盖不确定的历史结果。
- `202` 仅表示可靠接收，不代表私聊/群消息已送达，更不代表复刻成功。

### 收件人与结果不确定

用户名做大小写敏感的精确匹配，不做模糊匹配或别名猜测。通过既有用户名/邮箱映射缓存取得唯一有效的 `status=0` 身份映射，再按邮箱查询飞书 open_id；空用户名或映射失败使用既有兜底群。首次发送前冻结解析后的目标，重试不再次选择收件人。调用方不能覆盖目标。

准备发送时，持久化冻结目标、消息正文与该次投递 UUID。已冻结请求的重试不得改正文、改目标或换 UUID。明确私聊失败可以按规则进入兜底群；网络超时、连接中断等不能确定对方是否已经接收的情况，必须在最多 3,300 秒的安全重试窗口内，仅对同一冻结请求重试，最多 5 次投递尝试；仍不能确定或窗口已过则进入 `delivery_unknown`，不盲目兜底、不自动补发。

`delivery_kind` 仅在确认 `delivery_status=delivered` 时为 `private` 或 `fallback`；其余状态均为空字符串。明确不可恢复失败可进入 `dead_letter`。新队列与旧接口重试隔离。

### 固定消息模板

已发起：标题 `【自动复刻任务已发起】`；引导语 `以下素材已自动发起复刻任务：`；按请求顺序编号，每项显示“资源ID、资源名、原始素材ID、原始素材名”。固定说明以 `素材语种包含：` 开头，列出以下 17 种语言：

西班牙语、法语、阿拉伯语、俄语、葡萄牙语、日语、繁体中文、泰语、印度尼西亚语、德语、越南语、意大利语、土耳其语、波兰语、罗马尼亚语、捷克语、韩语。

该固定语言说明只表示发起范围，不代表这 17 种语言已全部成功。

失败：标题 `【自动复刻失败】`；引导语 `以下素材自动复刻失败：`；每项显示同样四个字段，再显示“失败语种”，按上游顺序用“、”连接。末尾固定为 `备注：复刻失败一般是算法失败，重试基本也不会成功。`，这是业务提示，不是对单次失败原因作算法诊断。

两类消息均含“批次编号”页脚。兜底消息保留同一批次业务正文并附中文原因；不暴露 Token、内部数据库地址或调用方不可配置的群标识。

## 交互与流程

1. 上游按自身周期完成汇总与新数据筛选，持久化业务批次、幂等键和完整请求内容。
2. 调用新接口；接收方验证鉴权、HTTP/JSON、整批字段；对新批次执行最终消息大小预检，同键同内容重放复用原批次。
3. 原子落库后返回 `202`，异步处理器尽快处理，不增加小时级等待。
4. 映射目标并冻结发送请求，向对应剪辑师私聊；映射/明确私聊失败才走既有兜底群。
5. 持久化确认送达或有限重试/未知/死信状态。上游如需对账，原键原内容重提读取当前状态。
6. 网络超时或 `5xx`，上游按 1、5、30、120 秒间隔使用原键原内容重试；收到 `202` 后停止接收重试。`4xx` 先修正，`409` 先核对原批次。

### 数据结构

独立 outbox 保存批次号、唯一幂等键、规范化请求与指纹、条目数、首次接收时间、投递状态、尝试数、冻结目标/正文/UUID、重试窗口、下次重试时间和安全错误摘要。创建与同键争用必须具有事务/唯一约束；进程重启仍可恢复，不能依赖内存队列作为接收凭据。

不在响应中暴露收件人邮箱、open_id、群 ID、访问凭据、数据库连接信息或内部异常栈。日志和审计也不得记录 Bearer Token。

### API / 接口

详见 [接口 Markdown](api-doc.md)、[独立 HTML](api-doc.html)、[OpenAPI 3.0.3](openapi.json)。响应字段固定为 `code`、`message`、`batch_id`、`duplicate`、`item_count`、`delivery_status`、`delivery_kind`、`received_at`。

### 异常与边界

HTTP 错误集合：`400 invalid_request/invalid_json/idempotency_key_required/invalid_idempotency_key`、`401 invalid_token`、`409 idempotency_conflict`、`413 payload_too_large/message_too_large`、`415 unsupported_media_type`、`422 invalid_payload`、`503 service_unavailable`。

对外消息中的固定文字和换行同样占用最终请求字节预算。已有 `202` 的原批次不能因后续映射变化或重提而重写已冻结投递；未知结果不等同失败，无外部事实不得自动创建替代发送。

## 风险与待确认

业务范围已确认，代码已上线并通过本次隔离回归与非发送部署检查，无新增产品选择。专属 Token 仅在服务端以 root 所有、0600 权限保管，调用方通过安全渠道取得；不得放入文档、日志或截图。后续发布继续核验身份映射/兜底配置、持久化目录权限和回滚保留新旧 outbox。真实飞书送达尚未试发验收，须使用首个获准业务批次核验，不得擅自创建测试消息或生产素材任务。

字段均合法不保证一定能放入 128 KiB 最终请求；超限拆分责任在上游。上游跨批次漏去重、把失败同时发给两个接口或换键强行补发，会突破接收端同键去重边界。

外部依据：2026-08-27 核对的 [飞书官方 SDK v3.10.0 CreateMessageReqBody](https://pkg.go.dev/github.com/larksuite/oapi-sdk-go/v3/service/im/v1#CreateMessageReqBody) 说明文本消息请求体为 150 KB、相同 UUID 的防重窗口为 1 小时。本需求采用更保守的 128 KiB 和 3300 秒，并非把这些我方数值声称为官方原值。
