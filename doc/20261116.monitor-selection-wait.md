# 等待选材的监测分类

X Auto 与 Tag Auto 的前置选材由各自 runner 推进。原始选材记录在统一调度器中使用
`control_only`，因此其 `adapter_unavailable` 只是该阶段不由分布式 worker 领取。
选材后创建原发布队列，成片制作仍由统一调度分发至 GPU。

只读监测把 `x / auto / prepare`、原状态 `pending` 或 `retry_wait`、无已记录错误、
调度状态 `queued` 或 `ready` 的此类技术等待计入待执行，未到预约时间的仍计预约中。
待执行下显示“等待选材”数量，任务明细显示“等待选材，选材后进入统一调度制作”。
不改变调度占用、租约、发布回执或任何业务状态。真实暂停、其他适配器不可用、
缺失身份、未知账号结果和已记录错误仍使用原异常处理。

验证：`python -m unittest scripts.test_pipeline_queue_states scripts.test_pipeline_monitor`
与 `node scripts/test_pipeline_selection_wait_ui.js`，覆盖汇总、明细、权限、预约、
未知结果隔离及只读性。

部署脚本 `scripts/deploy_monitor_selection_wait.py` 从确切 GitHub checkout 复制当前
协调器版本，仅覆盖两个监测模块和两个静态资源。先备份公开资源和原版本指针。
协调器切换保留已有 ExecStop 接单与在途任务保护，制作/发布 worker 不停止、不重置任务。
X 分片上传会在相邻 HTTP 请求之间持续申请下一段许可；HTTP 暂时空闲不能证明
协调器可以安全停止。实际短时切换已经观察到单条分片上传进入
`coordinator_unavailable`，因此本脚本禁止绕过正常停止保护，回滚同样适用。
任务中断只能按双边操作账本与节点已确认的终止回执核对；未进入 FINALIZE 或发帖
阶段的原任务，才可通过已有审计恢复工具给予唯一下一代恢复，不盲目重发。
核对依赖调度器和其他进程 PID。

运行前先 fetch 精确提交并创建只读源码 checkout；`--previous-sha` 是包含当前公开
资源及两个监测模块的维护基线 `fd56a5e6` 的完整提交。先 `prepare`，在 candidate
运行相同检查后再 `activate`。部署目录的 `deployment.json` 保存原版本、备份、
实际服务切换时间和结果。回滚命令：

```sh
python3 SOURCE/scripts/deploy_monitor_selection_wait.py rollback --directory DEPLOYMENT
```

回滚仅恢复代码指针和两个静态资源，保留当前全部业务账本、租约、回执及凭据。
