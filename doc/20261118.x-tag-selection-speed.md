# X tag selection read reuse and four workers

The tag control lane used one worker and reconnected to MySQL for each candidate
query. A live read-only sample spent about 1.3 seconds opening/checking each
connection and 4.4 seconds listing eight drama rows. Successful selection took
18–20 seconds, before the 2–3 second canonical queue handoff.

The independent entrypoint `scripts/x_tag_selection_service.py` pins the existing
composite tag runtime and replaces only its source-read dependencies before
building the control service. Other publishers retain their existing runtime.
It uses at most four source connections per configured source, never shares a
connection between threads, pings without implicit reconnect, expires idle/old
connections and discards a connection after query failure. A failed query is
not automatically retried by the pool. Existing replica and read-only session
validation runs on every newly opened connection.

Identical candidate drama/material reads and catalog classifications are
coalesced and reused for at most five seconds, bounded to 128 small entries.
The cache key includes exact language, query bounds, product and explicit future
release scope. Cached objects are copied for each caller; failed queries are
not cached. Blacklists, metric readiness, account state, cooldowns, reservations,
publication history and strict final source validation remain live. Both
runner and API concurrency change from one to four. Existing atomic claims,
material uniqueness, heartbeat and independent recovery proofs are unchanged.

After pushing the commit, fetch it into a clean release under
`/mnt/data-disk/x-tag-selection-speed-20261118`. Run the new IO tests, existing
claim/selector/publisher tests against the pinned runtime, and a read-only
before/after candidate parity/timing check. No test Post or historical replay.

Deployment (use the exact fetched source and an unused deployment directory):

```
python3 SOURCE/scripts/deploy_x_tag_selection_speed.py prepare --deployment DEPLOYMENT
python3 SOURCE/scripts/deploy_x_tag_selection_speed.py drain --deployment DEPLOYMENT
# Wait until BOTH x-tag-auto.service and x-tag-auto-runner.service MainPID are 0.
python3 SOURCE/scripts/deploy_x_tag_selection_speed.py activate --deployment DEPLOYMENT
python3 SOURCE/scripts/deploy_x_tag_selection_speed.py verify --deployment DEPLOYMENT
```

Preparation backs up the auto SQLite snapshot, drop-ins, trigger states and
protected PIDs. Drain stops only runner timer/path triggers and asks the control
API for its existing graceful shutdown with infinite stop timeout. Its request
threads finish naturally. Do not force-stop the runner or a handler. Rendering,
posting, coordinator and COS bridge processes must retain their PIDs. The two
runner triggers are restored to their recorded states; preserve intentional
pauses. Also save/restore the scoped X scheduler health baseline and explicitly
verify tag scheduler/watchdog timers and successful natural runner cycles.

Rollback uses the same `drain` command, waits for both PIDs to reach zero, then
uses `rollback` in place of `activate`, followed by `verify`. Only the two scoped
drop-ins are restored; databases, claims, reservations and publication receipts
are never rolled back. Hash drift requires reconciling concurrent edits instead
of overwriting them. The minute-level `selection_io` log reports read/cache reuse
and connection counters without source identities or credentials.
