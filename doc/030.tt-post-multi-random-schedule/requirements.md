# 030.TT 自动发布多时间与随机排期需求及技术设计

## 背景

当前页面只允许保存一个固定发布时间。底层已支持固定时间数组，但服务层和页面仍限制为单值；同时没有按账号、按自然日持久化的随机计划。

## 目标

- 固定模式支持每天 1 至 24 个互不重复的北京时间点。
- 随机模式只填写每天发布次数，各账号每天独立生成时间表。
- 随机时间覆盖北京时间 `00:00-23:59`，分钟不为 `00`，同账号同日相邻时间至少间隔 60 分钟。
- 随机计划按“账号 + 北京日期”持久化；服务重启、重复领取和多进程执行不得改变当天计划。
- 同一账号相邻两天的完整随机时间表不得完全相同。

## 范围

### 包含

- 自动发布统一配置、每账号镜像排期、随机日计划表、领取校验、页面配置和展示。
- 旧单时间配置自动按固定模式兼容，不要求人工迁移。
- 首次启用随机模式时从下一个北京时间自然日生成随机计划，当天不补发；已处于随机模式时修改次数，当天已有随机计划继续执行，新次数从次日生效。

### 不包含

- 不改变立即发布测试、素材准备、账号能力校验、发布门禁和 TikTok 网络发布协议。
- 不自动触发真实 TikTok 发布作为验收手段。
- 不重写历史运行、队列或已发布记录。

## 业务规则

1. `schedule_mode=fixed` 时，`publish_times` 必须含 1 至 24 个严格 `HH:MM` 时间；保存后排序去重校验。
2. `schedule_mode=random` 时，`random_daily_count` 必须为 1 至 24，`publish_times` 必须为空。
3. 随机计划中的时间分钟值必须为 `01..59`；计划内任意相邻时间差不少于 60 分钟。
4. 每个账号独立生成并持久化计划；不同账号允许偶然出现相同时间。
5. 随机计划一旦进入生效日即不可变；配置变化只替换尚未生效且尚无运行记录的未来计划。
6. 关闭自动发布立即阻止新的自动任务，但不删除计划历史和素材池。
7. 固定模式与随机模式互斥，历史配置默认视为固定模式。

## 技术设计

### 数据结构

- `tt_post_auto_publish_config`、`tt_post_daily_schedule` 增加：
  - `schedule_mode TEXT NOT NULL DEFAULT 'fixed'`
  - `random_daily_count INTEGER NOT NULL DEFAULT 0`
  - `random_effective_date TEXT NOT NULL DEFAULT ''`
- 新增 `tt_post_random_daily_plan`：`account_id + shanghai_date` 主键，保存 `config_version`、`publish_times_json`、创建时间。
- 迁移仅做加列和建表，不删除或重建现有表。

### 生成算法

在 0 至 1439 分钟内抽取有序时间，使用间隔变换确保相邻值至少相差 60；拒绝分钟为 `00` 的候选，并与该账号前一日完整计划比较，完全相同时重新生成。随机源使用系统安全随机数；最终结果以数据库快照为准。

### 执行

- 自然调度器每分钟先确保当天及次日随机计划存在，再扫描当前和前一日的 10 分钟安全窗口。
- 固定模式从配置时间数组取槽位；随机模式从日计划表取槽位。
- 自动运行认领时再次校验槽位属于对应固定配置或随机日计划，防止伪造和配置漂移。

## 验收标准

- 页面可添加、删除并保存多个固定时间。
- 随机模式仅要求每天次数，保存后按账号展示次日计划。
- 自动测试证明 1/24 次边界、非整点、60 分钟间隔、账号隔离、跨日不同、重启稳定、幂等和旧配置兼容。
- 全量 TT 自动化通过，生产迁移与 SQLite integrity check 通过，发布请求计数在部署验证期间保持不变。
