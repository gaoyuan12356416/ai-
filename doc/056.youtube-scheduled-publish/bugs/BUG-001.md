# BUG-001：准备事务与发布存储锁顺序冲突

- 级别：P1；发现方式：独立代码评审。
- 场景：schedule/review/_claim 持有 preparation 的 SQLite BEGIN IMMEDIATE，再调用 _ledger 进入 engine_store._lock；同时其他线程持有 _lock 并等待 SQLite 写锁。
- 影响：互相等待至 busy timeout，用户操作失败，worker 延迟。
- 根因：同一数据库混用两个连接、相反的锁获取顺序。
- 修复：_ledger(body,c) 在既有写事务中直接 SELECT reviewed ledger；事务外继续使用原 store getter。schedule 请求向 engine 提交变更前结束 preparation 事务。
- 文件：features/youtube_auto_publish/service.py。
- 状态：已修复并回归。`python scripts/test_youtube_schedule_service.py` 14/14 通过；`test_preparation_transaction_ledger_lookup_stays_on_same_connection` 使用真实共享数据库确认写事务内不调用其他连接的 store getter；`test_competing_preparation_commands_have_one_cas_winner` 用两线程、两个 SQLite 连接确认只有一个版本竞争者成功。

本问题没有通过真实生产并发复现；风险由 SQLite 写锁与 Python 锁的相反顺序确认。
