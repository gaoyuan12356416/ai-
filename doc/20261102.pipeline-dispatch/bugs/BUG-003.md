# BUG-003 X 全局控制锁阻塞其他来源的回执

- 级别：P1；发现日期：2026-11-03。
- 状态：本地修复及回归通过；尚未上线。
- 修复提交：`2793af2`；真实多进程保护测试：`575b08a`。

## 现象与根因

`XNativeBridge` 原来用一把全局 RLock 包住所有来源的 reserve、checkpoint、complete 等操作。一个账号的慢身份核验会阻塞其他队列的已完成回执，节点短请求超时后再次投递，又继续排队。2026-11-03 02:06:27Z 的 `collect_x_bridge.json` 保存了原生进程 1,012 个线程，并有大量 `x_preflight_publish_already_started` 与 BrokenPipe；这是全局锁、短超时和 BUG-005 多进程重复投递的叠加，不能仅归因于 GPU 不足。

## 修复范围

`2793af2` 改成弱引用 source_key 锁：同 source 的阶段、代次和迟到回执保持互斥，不同来源不再共用控制锁。原账号互斥、中央资源锁、写 intent、素材去重和原生发布 guard 均保留；没有取消账号身份/权限检查。

同提交允许精确、无发布证据的迟到 preflight 保存原事实，但不把已经 failed 的队列改回 ready；存在原生 intent、attempt 或 unknown 时继续拒绝。不得借补收回执重开旧任务。

涉及 `features/pipeline_dispatch/x_native.py` 和 `scripts/test_pipeline_x_recovery_concurrency.py`。

## 验证与剩余验收

真实 SQLite 用例证明慢账号核验期间，另一来源 checkpoint/complete 能独立完成；六个并发同源 reserve 只生成一份 claim/原生日志。另有真实 OS 进程测试验证八个 claimant 仅一个胜出、制作/发布共享账号互斥、写 intent 后进程崩溃不重新分配发布。

