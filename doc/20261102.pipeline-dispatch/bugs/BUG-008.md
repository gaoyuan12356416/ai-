# BUG-008 TT 原生同账号占用被中央记为永久失败

- 级别：P1；发现日期：2026-11-03。
- 状态：已确认并本地修复；尚未上线。
- TT 证据分类提交：`6045458`；中央局部等待提交：`2f9e60c`。

## 现象与根因

TT 4557/4559/4562/4566/4567/4572/4573/4574 仍为原生 pending，无 claim/平台操作，分别被 BUG-007 八条同账号 preparing 前驱挡住。原 native 空 claim 统一返回 `canonical_task_not_claimable`，中央将暂时的账号互斥误记为 failed。FB 后序 1759/1760/1762 也仍 queued/ready，无 claim/attempt，受同批同 Page unknown 前驱保护；不能通过跳过前驱修复。

证据为 `tt-native-diagnosis.json`、`tt-selection-recovery-analysis.json` 和 `fb-native-diagnosis.json`。已有账号保护本身正确，错误在把可等待的入队冲突与不可执行故障混为一类。

## 修复范围

TT 仅在当前任务为未领取 pending、无 unknown/attempt/publish ID/hold，并通过原生同账号状态和 cutover 边界 SQL 找到确切未暂停前驱时，返回 `canonical_account_busy`。没有证据仍保留原错误，不猜测所有 not_claimable 都能重试。

中央对已明确分类的占用只做 30 秒局部等待，保留原预约时间及队列身份，不消耗原生材料、平台 attempt 或修改前驱。该次新增的原生 busy 分类仅针对 TT 的上述精确证据，不把 FB 或其他 `canonical_task_not_claimable` 一律改成可重试。failed/native unknown 的监控差异按原生事实单向提升为 unknown 并保持资源锁，不能反向清未知锁。

涉及 `tt_native.py`、`core.py`、`service.py`、`test_pipeline_tt_selection_recovery.py` 与 `test_pipeline_claim_handoff.py`。
