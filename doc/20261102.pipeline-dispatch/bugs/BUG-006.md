# BUG-006 X 随机制作投影可能把预检原片当作最终成片

- 级别：P1；发现日期：2026-11-03。
- 状态：生产只读账本与真实 SQLite 复现确认，本地修复通过；尚未上线。
- 修复提交：`2793af2`。

## 根因与影响边界

X 的 `pipeline_x_artifact` 保存 preflight 输入视频；启用随机模板时，真正最终成片在 `x_post_random_template_preparation` 的 ready receipt。旧 adapter 先把前者写为 `_dispatch_artifact`，即使随后读取随机制作结果也没有替换该优先投影。中央原生完成恢复和下游发布 offer 因而可能携带原片 URL/SHA/size，与原生发布实际选用的随机成片不一致。

生产样本中央 31592 / `x:queue:5395`、31595 / `x:queue:5398` 在 gen2 已 completed，但中央 artifact profile 为 source；节点原 gen1 回执为 libx264 随机成片，最终 SHA 与原片不同。证据为 `business-full.json`、`cpu-pending-receipts.json` 和 `worker-system-tests.md`。真实 SQLite fixture 也复现了这两种 artifact 指纹差异。

原生实际发布仍从随机制作账本读取经过 validate 的最终结果。因此已确认的是中央恢复/监控投影错误，没有证据证明实际发错视频。预检存在不等于随机制作完成。

## 修复范围

`2793af2` 对 random 任务不再投影原片为最终产物；只有随机制作 ready 且 `validate_receipt` 对原 frozen request 验证成功时，才使用最终 output URL/SHA/size、duration、profile、recipe。损坏/空 receipt 不退回原片。非 random 路径维持原规则，原生冻结 profile/catalog 不因新代或换节点改变。

涉及 `features/pipeline_dispatch/adapters.py` 与 `scripts/test_pipeline_x_recovery_concurrency.py`；同提交的 X 控制锁单独记录于 BUG-003。

## 验证与剩余验收

```text
python -m unittest -v scripts.test_pipeline_x_recovery_concurrency scripts.test_pipeline_process_races
```

组合 11 项通过，5.509s，证据 `x-recovery-process-tests.txt`。覆盖仅有预检不能恢复完成、真实随机 ready 回执可恢复且用成片 SHA、损坏回执拒绝、原生完成而中央 ACK 丢失时不二次制作、跨节点沿用原 profile/catalog。

上线后应选自然产生的 random 任务核对原生最终 receipt、中央 artifact 与节点发布实际输入一致。历史失败不自动恢复，已付出制作结果的保留和只读核对不等于授权重新发布。
