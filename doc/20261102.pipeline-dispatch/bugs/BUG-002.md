# BUG-002 慢原生预留超过请求超时且尚未启动任务心跳

- 级别：P1；发现日期：2026-11-03。
- 状态：最终回归通过；协调器 5b274ff、节点 95fdaa4 已部署，正常慢选材/制作验收待补。
- 修复提交：`2f9e60c`。

## 现象与证据

原 `jobs/claim` 同步完成原生选材/预留后才把任务返回节点。节点请求默认 10 秒，而真实 TT 选材到冻结事件耗时约 18–30 秒，FB 单次预检约 8–9 秒且还会排队。HTTP 超时并不撤销已经发生的原生预留；节点尚未获得任务身份，也没有启动该任务独立心跳。中央 120 秒租约过期后进入下一代，原生仍持有上一代材料、token 与阶段，导致 `canonical_identity_changed` / `canonical_task_not_claimable`。

证据为私有 `work/acceptance-20261103/business-full.json`、`tt-native-diagnosis.json`、`tt-selection-recovery-analysis.json` 与 `fb-native-diagnosis.json`。TT 4544/4546 等八条有原生 gen1 冻结记录；FB 1756–1758 中央过期后 gen2 失败而原生后来进入 unknown。这里只证明控制链超时及状态分离，不推断平台已发或未发。

## 根因与修复

控制协议把慢业务预留放在短时领取 RPC 内，并把心跳启动放在返回描述器之后。`2f9e60c` 先返回中央 claim 身份与 `reservation_pending`，节点立即启动独立心跳，再通过 `jobs/reserve` 取得冻结描述器。预留/操作/回执的请求预算为 120 秒，领取和心跳仍为 10 秒；不是单纯把所有请求超时放大。

保留旧 worker 的 inline 模式；新 reserve 校验原 job/generation/token/node/worker。凭据响应晚到时再次检查租约，失租不得进入平台写操作。原生 unknown 只能向中央单向提升并保留资源锁，不能通过失败状态释放未知平台结果。

涉及 `client.py`、`core.py`、`service.py`、`worker.py` 与 `scripts/test_pipeline_claim_handoff.py`。

## 验证与剩余验收

真实本地 HTTP + SQLite 测试阻塞原生 reserve，同时推进三个 60 秒区间，验证独立心跳保持 gen1、只预留/执行一次；另测旧模式、错误代次拒绝、请求预算和失租后晚到凭据拒绝。命令：

```text
python -m unittest -v scripts.test_pipeline_claim_handoff
```

根代理报告本轮共同 78 项回归通过，包含上述用例。上线后仍需确认正常慢选材不再丢领取响应、原身份心跳持续、没有第二次选材/平台初始化。历史失败及 unknown 不自动恢复；原八条 outbox 保留，不以重试历史任务补验收。
