# BUG-004 FB 全局控制锁让不同 Page 的慢预检阻塞回执

- 级别：P1；发现日期：2026-11-03。
- 状态：修复随 95fdaa4 原生候选部署，严格排空后切换；最终业务验证待补。
- 修复提交：`5c8f04d`；共性领取/状态收敛提交：`2f9e60c`。

## 原生事实与根因

只读 `fb-native-diagnosis.json` 显示：不同 Page 的任务 1755–1758 在 16:00:00/08/17/26Z 依次原生领取。1755 的平台凭据 intent/attempt 到 16:00:37Z 才落账，已晚于节点 10 秒等待；无 checkpoint/post ID，后续原生进入 `worker_interrupted` unknown。1756–1758 有原生 gen1 binding、无 operation/attempt，中央租约过期后 gen2 `canonical_task_not_claimable`，原生后来同样进入 unknown。

`FBNativeBridge` 全局 RLock 将素材/权限慢预检与其他来源凭据和回执串行化。控制锁范围大于业务要求的同 source/同 Page 互斥，造成跨 Page 等待。原生有 attempt 而没有最终回执时，不能声称平台没有收到写请求。

## 修复范围

`5c8f04d` 用弱引用 source_key RLock 替代全局锁；同 source 的 prepare/publish、不同代次及迟到回执共用一把锁，闲置历史锁自动回收。原 SQLite 原子 claim、Page 保护、auto/video 跨入口同 Page 互斥、审批、素材预留和冻结配方完全保留。仓库只读查询使用独立连接，没有把共享数据库连接带入新并发路径。

只改 `features/pipeline_dispatch/fb_native.py` 和新增 `scripts/test_pipeline_fb_source_locks.py`；不改原任务状态、不清 unknown、不重发。
