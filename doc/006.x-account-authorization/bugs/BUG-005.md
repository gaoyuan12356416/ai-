# BUG-005 跨Owner重新授权可能覆盖原账号归属与Token

## 状态

P0，已修复；本地 Sidecar 28/28、App 5/5、backfill 4/4、编译/静态和 Playwright 三路径通过；生产 OAuth 冲突路径待部署后验证。

## 发现阶段

V2 需求/SA 评审与 V1 callback upsert 代码复核，2026-07-14。

## 现象

V1 以全局唯一 `x_user_id` 执行 `INSERT ... ON CONFLICT(x_user_id) DO UPDATE`。如果 Owner A 已授权某 X 账号，Owner B 再用同一 X 账号完成 OAuth，callback 会先写新的 Token 文件，再覆盖记录的授权人、最近授权时间和账号资料。结果可能导致 A 的凭证/归属被 B 无提示替换，且个人 owner 隔离无法可靠建立。

## 复现步骤

1. Owner A=`t1+u1` 授权 X-A，记录 DB row、owner、Token 文件 SHA-256、首次/最近授权时间和资料快照。
2. Owner B=`t1+u2` 或 Owner C=`t2+u1` 发起授权，并在 X 使用同一 X-A 同意。
3. Callback 完成 token exchange 和 `/2/users/me`，返回相同 `x_user_id`。
4. 比较 A 原记录与 Token 文件。

## 期望结果

- Callback 返回安全错误 `409 x_account_owned_by_other` 并跳回个人页提示联系管理员。
- 原 owner tenant/user、Token SHA-256、记录 ID、首次/最近授权时间、状态与资料快照完全不变。
- 新收到的 Token 只存在请求内存，不落盘、不写日志，也不能被用来 revoke 既有 owner 的凭证。
- 同一 owner 重授权同一 X 账号仍应更新原行/Token，不新增重复记录。

## 实际结果

V1 callback 在 owner 检查前写 Token，并无 owner 冲突分支；`ON CONFLICT` 会更新授权人和 Token 元数据。V2 已在统一 `x_user_id` 锁内、写 Token 前读取并比较完整 owner，冲突即返回安全错误。

## 根因分析

- V1 需求只有“按 x_user_id upsert”，没有定义后台 owner 归属和转移策略。
- `x_user_id` 唯一约束与 owner 语义混在一个 upsert 中。
- Callback state 不含 `tenant_key`，无法比较完整 owner。
- Token 文件写入早于数据库 owner 冲突判定，失败回滚只处理普通 DB 异常，不处理跨 owner 业务冲突。

## 修复说明

已实现：

1. State 持久化 `actor_tenant_key + actor_user_id`；callback 拒绝 owner 任一关键字段缺失。
2. 完成 `/2/users/me` 得到 `x_user_id` 后，进入该 X 账号的统一锁。
3. 在任何 Token 文件/DB 写入前读取现有 row：
   - 不存在：按当前 owner 创建。
   - owner 完全相同：执行安全重授权更新。
   - owner 不同：抛 `x_account_owned_by_other`，原数据不变。
   - legacy owner tenant 为空：保持 admin-only，不允许 callback 自动认领。
4. 自动化在冲突前后比较 DB 序列化值与 Token SHA-256，而不读取/打印 Token 明文。
5. Owner 转移如未来需要，必须单独设计 admin 审批/审计流程，不能复用 OAuth callback 隐式完成。
