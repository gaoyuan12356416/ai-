# BUG-004 跨用户全局列表与按ID操作存在IDOR

## 状态

P0，已修复；本地 Sidecar 28/28、App 5/5、backfill 4/4、编译/静态和 Playwright 三路径通过；生产 Cookie 隔离验证待执行。

## 发现阶段

V2 需求/SA 评审与 V1 代码复核，2026-07-14。

## 现象

V1 `GET /api/x-accounts` 只检查 Cookie/module 权限，然后读取 sidecar 全量账号；`POST /api/x-accounts/{id}/verify` 只按自增 ID 查找和更新。任何获得 `x_accounts` 模块权限的后台用户都可能看到所有已授权 X 账号，并通过枚举 ID 校验/刷新他人的 Token。

V2 新增 logout 后，如果沿用同一按 ID 逻辑，还会允许越权撤销他人的 X 授权。

## 复现步骤

1. 创建 Owner A=`tenant t1 + user u1`、Owner B=`tenant t1 + user u2`，分别授权不同 X 账号。
2. 使用 A 的 Feishu Cookie 请求 `GET /api/x-accounts`。
3. 观察返回是否包含 B 的记录。
4. 使用 A 对 B 的记录 ID 请求 `POST /api/x-accounts/{id}/verify`。
5. V2 logout 实现后，再请求 `POST /api/x-accounts/{id}/logout`。
6. 使用 Owner C=`tenant t2 + user u1` 重复列表和按 ID 操作，验证相同 user ID 也不能跨 tenant。

## 期望结果

- A 的个人列表只返回 owner=`t1+u1` 的记录，B/C 数据不可见。
- A 对 B/C 的 verify/logout 返回 404，sidecar 不调用 X、不读取或修改目标 Token。
- Admin 只能通过 `/api/admin/x-accounts` 与 `/api/admin/x-accounts/{id}/verify` 查看/同步全量账号。
- owner 边界必须同时包含 `tenant_key + user_id`，不能只在页面过滤。

## 实际结果

V1 列表为全量查询，verify 只按记录 ID；没有 owner tenant/user 服务层过滤。V2 已改为 owner/admin 两套显式 scope，并在 sidecar 服务层联合过滤 owner。

## 根因分析

- V1 schema 只有 `authorized_by_user_id/name/email` 展示字段，没有不可变 owner tenant。
- 主 API 没有把完整 Cookie actor 传入 list/verify。
- Sidecar `list_accounts()` 使用全表查询，`find_account/verify_account` 只以 `id` 为条件。
- 模块权限被误当作数据 owner 权限，缺少 admin 与 owner 两套服务语义。

## 修复说明

已实现：

1. Schema additive 增加 `owner_tenant_key`、`owner_user_id` 及展示快照；state/audit 增 actor tenant。
2. 主 API 从服务端 Cookie 生成 actor，浏览器不得提交 owner/role。
3. Sidecar owner query/verify/logout 在 SQL 与锁内重读时都使用 `id + owner_tenant_key + owner_user_id`。
4. 越权按不存在返回 404；不产生上游请求或目标审计副作用。
5. Admin 全量 query/verify 使用独立 `/api/admin/x-accounts*`，主 API 必须 `_require_admin()`，sidecar 显式 admin 模式。
6. owner 为空的 legacy 记录仅 admin 可见，禁止按 `user_id` 兜底认领。
