# Meta 封面替换执行流水线优化

日期：2026-10-29。基线：`4c7cd30878ad46dd2908839a60dc09642ab2eda9`。

## 问题与目标

用户要求独立执行旧 Creative 清理，不阻塞广告封面替换，并减少来源查询和排队等待，完成部署验证。原实现每个广告周期结束后同步清理，来源查询与广告波次间也存在整波等待。

已核实的 27 个非空周期共 5681.999 秒，来源准备占 1478.966 秒（26.03%），清理占 2745.861 秒（48.33%）。样本仅覆盖 2026-10-29 上午至 14:15，不能代表全天或直接预测优化收益。4059 条成功任务入队到成功平均 2.33 小时，包含排队，不能当作单条 API 时延。

## 设计

1. 同一服务内一个监督器、一个独占进程锁，广告与清理分别持续循环。成功绑定与清理入队仍在同一持久事务完成，广告周期不等待清理周期。
2. 两循环共用一个 Governor：总请求并发最多 32、账户最多 2、启动速率最多 24 req/s，保留自适应降速。清理池单独有界，已实现默认 4，避免占满广告资源。
3. 两循环在同一 legacy lease 下运行。停止或旧清理优先窗口到来时停止新提交，排空两个循环在途请求并落账，最后才释放 lease。
4. inflight 与 reservation 回收仅在双循环启动前执行，不将另一循环活跃任务当作崩溃记录。未知结果只读核实，不重发创建、绑定或删除。
5. 广告按完成事件补位，保留账户公平和每账户容量。SQL 来源准备由调用线程拥有，在已有广告执行时准备后续有界小批次；提交和写入前仍检查 freshness。
6. 不跨周期缓存可变来源、凭据身份或授权，不扩大上下文 TTL。过期且未提交的任务重新准备或暂缓。
7. 保留共享对象预约、完整引用扫描、删前新鲜度和一次删除账本。局部异常按实际影响范围隔离；账本错误和不可确认写入仍需可靠落账。
8. 性能记录区分执行循环；并行循环秒数不得相加作为广告吞吐分母，历史无标记记录继续可读。

## 范围与验收

沿用 SQLite 持久队列与共享账本，不复位历史失败/未知，不改变扫描门槛、产品范围或 Meta 业务参数。当前参数校验停机须单独核对证据，不能以性能优化直接解除未知隔离。

验收须证明：清理阻塞时后续广告能完成；慢广告不阻挡其他账户补位；两循环共享总限额；引用不完整、未知结果、过期上下文不写入；停止后没有孤儿线程继续请求；来源 SQL 不跨线程；指标不重复计时。完成针对性测试、现有回归、GitHub 提交拉取部署、版本核对、备份与回滚记录。

## 已确认的附带缺陷与来源对照

当前全局暂停样本 task 9021 的内部错误是 `ad_binding_not_confirmed`：Meta 接受更新后立即回读仍返回旧 Creative。2026-10-29 19 点的只读核实已确认绑定到新 Creative `1917286539245254`，广告和 Creative 参数验证均通过。处理范围仅为：此类旧绑定读回延迟保持 task unknown 和共享 fence，交给只读核实，不触发全局停机，不重发更新；实际参数漂移仍保留原保护。详见 BUG-001。

同一批 64 个任务（64 账户）的只读来源准备对照：分两批 32 合计 12.337 秒，单批 64 为 4.597 秒；64 条均有效，准备结果完全一致。这是一次固定样本对照，不是整体吞吐保证。允许有界批次最多 64（空位加一个容量缓冲），上下文 TTL 仍为 30 秒。
## 并发清理候选协调

清理候选过滤同账户、同旧Creative尚有 pending/in_progress/waiting_review/unknown 的替换任务，待这些任务自然离开未完成状态后再进行Meta完整引用扫描。失败扫描批次中 request_sent=0、stage=queued 的废pending记录不构成永久阻挡。增加 tasks(account_id,old_creative_id,status) 索引。该筛选仅影响调度，不替代引用验证，也不更改历史waiting_references的next_check_at。
