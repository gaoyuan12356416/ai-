# BUG-004 多账号同分钟可能漏预占

## 状态 / 严重级别

- 状态：已实现候选修复，待完整回归。
- 严重级别：P0。

## 现象与根因

若 runner 按 `limit` 发现一个账号后立刻进行慢 creator-info/GPU/TikTok 调用，其余同分钟账号可能超过 grace，造成漏发。旧跨账号分钟冲突只是绕开问题，不能支持多账号共同时间。

## 实际修复方案

- 不新增 `tt_post_auto_due`，也不把 50 个 slot 放进一个大事务。
- `schedules_due` 收集全部 due slots；门禁开放时先逐项调用现有 `claim_recurring_run`。
- 每次 claim 独立原子创建 `tt_post_schedule_run(status=claimed)` 并预留该账号精确 FIFO 素材。
- 所有当前 slot 的 claim 尝试完成后，才处理旧 claimed/unbound recovery 或新 run；因此任一 `_execute_recurring_run`/creator-info 都必须晚于 preclaim 循环。
- 请求只接受 `limit`；limit 仅限制执行/响应 item。
- stable run key 防重入；claimed/unbound run 与 pool reservation 支持崩溃恢复。
- 无素材 slot claim 失败、返回 skipped 且不建空 run；不阻止其他 slot。

## 验证

S01-S10。必须用 fake creator-info 记录首调时间，并在首调点读取 run/pool；同时覆盖第 N 个 claim 失败、无素材、重入和 crash recovery。
