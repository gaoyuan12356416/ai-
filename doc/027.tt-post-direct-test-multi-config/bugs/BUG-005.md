# BUG-005 发布任务表遗漏立即测试任务

## 发现阶段

027 基线生产上线后的运营验收。

## 状态 / 严重级别

- 状态：代码与本地回归已通过；待生产只读验收和上线。
- 严重级别：P1。

## 现象

立即测试任务已经写入 `tt_post_direct_test`，也能通过 `/direct-tests` 和页面上方最近测试区看到，但页面底部“发布任务”主表、统计卡、筛选和分页只包含旧 `tt_post_queue`。运营在主审计表中看不到真实立即测试任务，容易误判为任务没有创建。

## 复现步骤

1. 使用已校验素材和明确 TikTok 账号创建一条立即测试任务。
2. 等待任务进入任意 `queued|preparing|ready|publishing|reconciling|published|failed|unknown|canceled` 状态。
3. 确认 `GET /api/admin/tt-posts/direct-tests` 返回该任务。
4. 查看页面底部“发布任务”表，或请求 `GET /api/admin/tt-posts/queue`。
5. 观察主表 items、total、summary、账号/素材/状态筛选及分页。

## 期望结果

- 主表默认统一显示自动/排期 queue 与立即测试 direct-test，并提供明确任务类型标签。
- 统计、筛选、稳定排序和分页基于过滤后的合并全集。
- queue 与 direct-test 的数字 ID 使用命名空间隔离；direct 行只读，不能调用 queue 事件、取消或核对操作。
- 旧 `/queue` 与旧自动任务展示/操作完全兼容。
- 所有统一列表查询均为只读，不创建 Post，不触发 GPU/TikTok 或 runner。

## 实际结果

- `TTPostService.queue_list()` 只读取 `store.list_queues()`。
- UI `loadQueue()` 只调用 `/queue`，因此 direct-test 不进入主表及 summary。
- `renderQueueRows()` 默认把行 ID 当作 `queue_id`；若直接在前端混入 direct-test，两个表相同数字 ID 可能把“查看事件”或 queue 写操作指向错误任务。

## 根因分析

027 基线为 direct-test 增加了独立状态机和独立最近任务区，但既有发布任务主表仍是 queue 专用读模型。当前没有一个在服务端合并两类任务、统一统计/筛选/分页并表达操作能力的只读投影。浏览器端拼接两个已分页接口不能得到可信 total、排序或分页，也无法安全处理跨表 ID。

## 拟修复说明

1. 新增只读 `GET /api/admin/tt-posts/tasks`，服务端合成 `tt_post_queue` 与 `tt_post_direct_test`。
2. 统一 item 返回 `task_key`、`task_type=automatic|direct_test`、`task_label`、`task_id`，并保留正确的 `queue_id` 或 `direct_test_id`。
3. 合并后执行账号、素材、状态、类型筛选，再稳定排序、统计和分页。
4. 主表增加“自动/排期”“立即测试”类型标记和类型筛选；direct-test 使用创建/更新时间，不伪造排期。
5. queue 行保留原事件、取消、人工核对；direct-test 行只读，不调用任何 queue action，也不新增 direct-test event 表。
6. 旧 `/queue` 路由及响应合同保持不变。

## 验收标准

1. 默认列表同时返回两类任务，且每条任务只出现一次。
2. 过滤后、分页前计算 total 与 summary；统计按任务行，不按素材去重。
3. `task_type=automatic|direct_test`、账号、素材、状态及组合筛选准确。
4. 数据不变时遍历分页无重复、无遗漏；页码越界返回空 items 和准确 total。
5. queue/direct-test 使用相同数字 ID 时仍有不同 `task_key`，不串事件或操作。
6. queue 行现有事件、取消、人工核对按钮与 `/queue` API 回归通过。
7. direct-test 行明显标记“立即测试”，展示安全详情，不出现 queue 专属按钮。
8. GET 与页面查询前后 SQLite/ledger/Post 基线 0 diff，GPU/TikTok publish 调用为 0。
