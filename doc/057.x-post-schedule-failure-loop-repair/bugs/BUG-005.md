# BUG-005 已冻结 relay 修复后低于 140 秒导致恢复事务回滚

## 发现阶段

生产 Run 274 在 14/14 validate-only 通过后的首次原子 apply 门禁。

## 现象

媒体修复和复验全部成功，但 queue 更新触发 `x_post_queue relay binding invalid`；整笔事务回滚，audit=0、修复 URL 写入=0、X 写入=0。

## 根因

历史短剧 relay 计划在媒体时长未知时使用 141 秒提示并冻结 relay ledger。生产修复后，部分真实媒体时长低于 140 秒；旧 UPDATE trigger 无条件拒绝 `premium_relay_repost + preflight_duration<=140`。离线 fixture 把 relay 修复结果固定成 180 秒，未覆盖跨越阈值的生产形态。

## 修复

- 保留冻结 target/relay 和原 ledger，不伪造 141 秒，也不改成 direct。
- 仅允许旧冻结时长精确为历史占位常量 `141`、且同一事务内已有不可变恢复 audit、剧集绑定、旧/新 URL、SHA、大小、实际时长、repair job/profile/source SHA、publish log、relay ledger、零 attempt/unknown 全部匹配时，从 deferred relay 恢复为实际 `<=140` 的 preflight relay。
- 旧冻结时长为 `142` 或 `180` 的 relay 即便具有完整 audit 也整事务回滚，防止把生产特例扩成通用绕过。
- 普通 `<=140` relay INSERT/UPDATE 仍拒绝；恢复后改时长、URL、job 或 relay 身份仍拒绝。
- 恢复 audit 冻结的 pool/content/episode/episode key/replay generation/pool created-at 也全部纳入 relay UPDATE trigger；恢复后任何剧集身份漂移都会在发布尝试前拒绝。
- SQLite 事务异常由 CLI 返回中文“已回滚、禁止自动重试”，不再输出原始堆栈。

## 验证

生产同形态负例/正例、普通 relay guard、恢复后证据防篡改及 CLI 脱敏纳入自动测试；生产首次失败已只读确认完整回滚。
