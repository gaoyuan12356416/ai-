# BUG-001 tt-featured-top-spend

## 发现阶段

发布前生产只读 SQL canary。

## 现象

FakeCursor 单测全绿，但把 SELECT alias `content_id` 再用于
`ORDER BY BINARY content_id` 时，生产 MySQL 返回 1247。

## 复现步骤

1. 在 `101.32.56.53:63350/kunlunads_dev` 设置只读事务。
2. 执行含 `GROUP BY BINARY i.data_source_id` 和
   `ORDER BY ... BINARY content_id` 的早期 Top20 SQL。
3. 观察错误 1247；FakeCursor 不解析 SQL，所以单测无法发现。

## 期望结果

SQL 在生产 MySQL/`ONLY_FULL_GROUP_BY` 下可执行，且相同花费时稳定排序。

## 实际结果

生产报 1247，无法生成排行；尚未进入线上定时任务，无用户影响。

## 根因分析

MySQL 不允许在该位置对同层 SELECT alias 再应用表达式。测试桩只按字符串
识别数据表并返回假行，没有数据库语法和 SQL mode 语义。

## 修复说明

- content ID 选择改为 `MIN(i.data_source_id) AS content_id`。
- 排序改为 `MIN(BINARY i.data_source_id) ASC`，满足完整分组规则。
- 在 `LIMIT 20` 前加入已生产验证的
  `BINARY i.data_source_id REGEXP '^[A-Za-z0-9_-]{10,32}$'`。
- 将真实只读 EXPLAIN + 连续两次执行设为发布闸门。

## 验证命令与结果

- 63350 EXPLAIN：`type=ref`、`key=as`、估算 210,394 行。
- 连续两次：20 行，1.487s / 1.408s；Top20 签名均为
  `2143235fdcee2b8a`。

## 回归结论

已修复且未上线过缺陷版本。FakeCursor 继续覆盖参数/边界，生产 SQL canary
覆盖真实语法、排序规则与 SQL mode。
