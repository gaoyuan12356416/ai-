# CTB-000101.ai-game-performance-report 需求与技术设计

## 背景

AI 游戏的产品测转化明细已经进入只读表 `ads_ai.ads_manual_daily_performance`；需求摸底快照有 431,687 行、117 个游戏、6 个渠道，日期范围为 2026-08-10 至 2026-08-25，数据会持续回补。渠道侧统一投放事实可从 `kunlunads_dev.ads_custom_source_insight` 读取，AI 游戏产品名为 `Neonarcade`。

当前缺少一个像 TT 小程序多维投放报表一样可按日期、游戏、渠道和广告层级查询、汇总、导出的页面。直接让浏览器扫描 MySQL 不可接受；`ads_custom_source_insight` 是大表，页面请求必须只读本地缓存。

## 目标

在 `https://ai.yingliangads.com/reports/ai-game-performance/` 提供飞书登录保护的 AI 游戏产品测转化报表，统一展示：

- 渠道事实：花费、渠道安装、曝光、点击、CTR、渠道 CPI；
- 产品测转化：测转安装、D1 留存数/率、平均游戏时长、D0/D1 收入；
- 综合指标：D0 ROAS、每个 D1 留存成本；
- 数据质量：渠道行/花费的游戏归属率、未归属与多归属情况、数据更新时间和当日未完结提示。

## 范围

### 包含

- 数据源仅做只读查询：
  - `ads_ai.ads_manual_daily_performance`；
  - `kunlunads_dev.ads_custom_source_insight`，固定 `product='Neonarcade'`；
- 三个视图：游戏总览、渠道明细、转化明细；
- 日期、游戏、渠道、国家/分组、Campaign、Adset、Ad 和关键词筛选；
- 今日、昨日、近 3/7/14 天快捷范围；默认昨日；
- CSV 导出；
- SQLite 日快照、每日版本化 JSON、15 分钟浏览器私有缓存；
- 最近 60 天保留，定时增量刷新今天及前两天（覆盖 D1 回补）；
- 飞书鉴权、发布前备份、精确 GitHub 提交部署和回滚说明。

### 不包含

- 不修改任何 MySQL 表、索引、数据或上传流程；
- 不补录或修正手工表中的游戏名、收入、成本、国家等源数据；
- 不把多游戏或无法映射的渠道花费猜测分摊给某个游戏；
- 不建设 ClickHouse/通用 BI 平台；
- 不提供预算、广告状态或投放写操作；
- 不改变 Codex 客户端或任务看板数据模型。

## 用户故事 / 业务规则

1. 运营打开页面后，默认看到昨天各游戏/渠道的关键结果，可快速判断留存、游戏时长和成本表现。
2. 运营可切换游戏总览、渠道明细和转化明细，并按当前筛选结果导出 CSV。
3. 渠道事实和产品测转化事实分别聚合后，才在共享维度 `日期 + 游戏 + 渠道` 上合并，禁止原始行直接 Join 后求和造成花费重复。
4. 渠道映射规则冻结如下：
   - Google：`platform=1`，通过 `campaign_id + adset_id` 映射手工表游戏；
   - Meta：`platform=0`，通过 `ad_id` 映射；
   - TikTok：`platform=3`，通过 `ad_id` 映射；
   - Unity：当前统一渠道源无事实行，使用手工表 `cost` 作为明确标注的兜底花费；
   - organic/restricted：产品转化保留，渠道花费为 0。
5. 一个渠道键只映射到一个游戏时才归属；映射到多个游戏显示“多游戏待归属”，没有映射显示“未归属”，不得按比例猜测。
6. 手工表 `game_id` 为空时，可从三个名称字段中的严格 `projectid[数字]` 提取；仍为空时显示“未标记游戏”。`1000000000000000000` 显示为“通用素材”。
7. 现网 `play_duration_seconds` 字段注释为“总播放时长”，平均游戏时长按 `SUM(play_duration_seconds) / SUM(install)` 计算；若仅存在历史 `avg_play_duration_seconds`，读取时先乘该行安装数归一为总时长。两个字段都不存在则刷新失败并保留旧快照。缓存和聚合内部继续使用秒，指标卡与表格按 `秒 / 60` 显示为 `min`，CSV 以 `平均游戏时长(min)` 导出相同分钟值。
8. D1 留存率为 `SUM(day1_retention_count) / SUM(install)`；D0 ROAS 为 `SUM(day0_revenue) / SUM(有效花费)`；每个 D1 留存成本为 `SUM(有效花费) / SUM(day1_retention_count)`。
9. Google/TikTok/Meta 的有效花费来自统一渠道源；Unity 的有效花费来自明确标注的手工兜底。手工表 `cost` 对受支持渠道只用于对账，不替代渠道源。
10. `ads_custom_source_insight.country` 显示为“渠道国家/分组”；手工表 `country` 显示为“转化国家”，两者不得混称或强行 Join。
11. 今日数据标记“进行中”；页面和 CSV 必须显示生成时间、日期范围和来源口径。
12. 当前手工表没有币种字段，页面统一显示 `$`，并明确依赖上传方保持同一币种。
13. “渠道明细”按渠道等共享维度汇总时，必须同时纳入渠道事实与产品测转化事实；两个日文件在浏览器中按事实并列追加后再聚合，禁止原始行 Join。Google/Meta/TikTok 有效花费仍只取渠道源，Unity 仅取手工兜底，organic/restricted 有转化但有效花费为 0。
14. 选择“渠道国家/分组”时，转化事实显示为“仅转化侧”独立桶，不得把转化国家冒充渠道国家；选择“转化国家”时仍使用手工表原字段。
15. 用户界面不展示“渠道行”或“转化行”：从指标卡、质量提示、表格和 CSV 中移除；底层计数字段仍用于内部完整性与无双计校验，不改变任何业务指标。

## 交互与流程

1. 页面读取 `latest.json`（`private, no-store`）获得当前版本、汇总、数据文件和质量信息。
2. 默认选择昨天与“游戏总览”；切换日期或视图时只加载所需每日 JSON。“渠道明细”为避免重复发布同一批转化数据，会同时复用 `delivery` 与 `conversion` 两类版本化日文件。
3. 浏览器在本地对已加载日文件做筛选和聚合，不访问 MySQL。
4. 切换维度/筛选后更新指标卡、趋势和表格；导出只导出当前结果。
5. 如果登录失效，页面给出中文重新登录提示；如果某个日文件失败，保留已加载数据并明确提示失败日期。

## 技术设计

### 影响模块

- 新增 `ops/ai-game-performance/ai_game_performance_dashboard.py`；
- 新增单元/契约测试、Nginx 鉴权配置和 systemd oneshot/timer；
- 新增 `doc/CTB-000101.ai-game-performance-report/` 全流程文档；
- 不修改 AI 主 API、TT 小程序报表代码或 MySQL Schema。

### 数据结构

本地 SQLite 默认位于 `/mnt/data-disk/ai-game-performance/cache/ai-game-performance.sqlite3`，包含：

- `manual_conversion_fact`：按源表 `id` 保存最近 60 天手工转化事实和标准化游戏字段；
- `delivery_fact`：按源表 `id` 保存 `Neonarcade` 渠道事实及游戏映射状态；
- `refresh_log`：每个事实类型/日期的行数、刷新时间和源时间；
- `publish_audit`：版本、日期范围、行数、质量摘要和发布时间。

所有刷新按事实类型和日期在一个事务中先删后插；任一步失败则回滚，不更新公开清单。

### API / 接口

报表是静态读接口：

- `GET /reports/ai-game-performance/`：HTML；
- `GET /reports/ai-game-performance/latest.json`：当前私有清单，禁止缓存；
- `GET /reports/ai-game-performance/data/<version>/<view>/<YYYY-MM-DD>.json`：版本化日文件，私有缓存 15 分钟；
- `GET /_tt_minis_report_auth`：复用现有飞书租户鉴权子请求，仅由 Nginx 内部调用。

详细字段见 `api-doc.md`。

### 异常与边界

- 只读端点 `@@read_only` 不是 1 时立即失败；
- 缺少表/字段、查询超时、缓存事务失败、JSON 原子写失败时保留上一公开版本；
- 空日期发布空日文件而不是沿用旧日数据；
- 多归属/未归属渠道事实独立展示，不进入具体游戏；
- 受支持渠道某日源数据缺失时不自动改用手工成本，页面显示来源缺失；
- Unity 兜底来源在页面、JSON 和 CSV 中均标明；
- 仅最近 60 天可查，超出范围在 UI 中禁用；
- 所有输出均不得包含数据库口令、命令行参数或 SQL 错误中的敏感值。

## 验收标准

1. 生产 URL 通过飞书登录可打开，匿名访问被引导登录，非授权租户被拒绝。
2. 页面默认显示昨天，并可切换今天、近 3/7/14 天和自定义范围。
3. 游戏总览、渠道明细、转化明细均可筛选、聚合和导出；中文无乱码，桌面和 390px 手机宽度可用。
4. 选定日期的渠道总花费/安装/曝光/点击与 `ads_custom_source_insight product='Neonarcade'` 只读基线一致；Unity 明确使用手工成本兜底。
5. 产品测转安装、D1 留存、总播放时长/安装派生的平均游戏时长、D0/D1 收入与手工表只读基线一致。
6. 游戏映射质量可见；多归属和未归属不被静默分摊。需求摸底时 2026-08-24 Google 为 625 条渠道行、613 条唯一归属、6 条多归属、6 条未归属；生产验收按刷新时实时数据复核，最终部署快照为 619 条唯一归属、0 条多归属、6 条未归属。
7. 普通页面请求只读取静态文件，验证过程 `mysql_calls=0`；`latest.json` 为 `private, no-store`，日文件为 `private, max-age=900`。
8. 刷新失败不替换当前公开版本；SQLite `quick_check`、Python 编译、单元测试、前端契约和浏览器回归通过。
9. GitHub 分支、提交、服务器精确提交、备份路径、服务/timer 状态和回滚命令齐全。
10. 最终由用户查看报表并在任务看板确认；Codex 不代替用户验收。
11. 2026-08-24 在“渠道明细”只选择“渠道”维度时，应显示手工表存在的 6 个渠道；Google/TikTok 渠道花费、Unity 兜底、各渠道转化合计分别与刷新时源事实一致，不发生双计；底层 838/48,088 条事实只作为内部验收证据，不在页面展示。
12. 三个视图的指标卡、质量提示、表格表头/数据和导出 CSV 均不得出现“渠道行”或“转化行”；`source_row_count/manual_row_count` 继续参与内部回归，其他字段顺序与数值不受影响。

## 风险与待确认

- 当前 `day0_revenue/day1_revenue` 实际汇总为 0；报表照实显示，不推断收入缺失原因。
- 手工表没有币种字段，跨币种上传会使金额不可比；V1 仅提示，不改表。
- Google 的渠道 `country` 可能是 `AIG-WW` 等投放分组而非转化国家，因此两类国家维度严格分离。
- 2026-08-24 的映射基线会随新增手工数据变化，生产验收按刷新时的实时质量摘要复核。
- V1 默认按上述口径落地；如用户验收时希望改变指标名称、默认维度或来源优先级，作为验收反馈修订后重新回归。
