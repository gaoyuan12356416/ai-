# BUG-006 渠道明细按渠道遗漏转化侧渠道

## 发现阶段

用户验收生产报表；日期为 2026-08-24，进入“渠道明细”后仅保留“渠道”维度。

## 现象

页面显示渠道事实 838 行并聚合为 2 行，仅有 `googleadwords_int` 与 `tiktokglobal_int`。同一天手工转化表实际还有 `unityads_int`、`organic`、`restricted`、`Facebook Ads`，运营按渠道查看时误以为大量数据丢失。

## 根因分析

原“渠道明细”严格只加载 `delivery` 日文件，即 `ads_custom_source_insight product='Neonarcade'` 的渠道事实。聚合本身没有丢失 838 条记录，但视图没有同时纳入 `conversion` 日文件，因此仅存在于手工转化侧的渠道不会进入渠道筛选和渠道汇总。

2026-08-24 生产只读基线：

- 渠道事实：Google 625 行、TikTok 213 行，共 838 行 / 2 个渠道；
- 转化事实：48,086 行 / 6 个渠道；其中 Google 46,088、Unity 1,299、TikTok 427、organic 175、restricted 59、Facebook 38 行。

## 修复说明

- “渠道明细”同时读取同日 `delivery` 和 `conversion` 两个既有版本文件，不重复发布数据；
- 两类记录转换为指标互斥的并列事实后，再由浏览器按当前维度聚合，绝不做原始行 Join；
- 渠道事实只贡献渠道花费/安装/曝光/点击；转化事实只贡献手工成本/测转安装/D1/时长/收入；
- Google/Meta/TikTok 有效花费仍仅来自渠道源，Unity 仅取手工成本兜底，organic/restricted 为 0；
- 状态区分别展示渠道事实与转化事实行数，表格/卡片增加有效花费、手工成本、测转安装和两类行数。

## 影响范围

仅修改静态前端的渠道视图装载、聚合、提示和 CSV 字段；MySQL 查询、SQLite Schema、定时刷新、Nginx、鉴权及其他两视图不变。普通页面仍不查询 MySQL。
